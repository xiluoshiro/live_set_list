# 2026-09-18 Venue 回填事故与交付教训

## 发生了什么

1. 初始位置回填错误地把 153 个实体 Venue 的位置数字从 1 增至 2，未公布场地 32 的地区补录也增至 2。本次时区补录又把 153 个场地从 2 增至 3。误把补全资料当成业务版本，并让地图有效性和 Live 来源元数据依赖这些数字。
2. 用本机 Flyway 历史整行指纹保护远端操作，连执行时间、耗时和账号也参与匹配。结果远端在业务写入之前被拒绝；后续还有同类本地业务整表指纹和本地审计状态依赖。单纯移除第一条检查并不能修复设计。
3. 给要求直接执行 SQL 的用户交付了含 `\set`、`\if`、`\echo` 的 psql 脚本，被远端执行器拒绝。移除元命令后仍以 ROLLBACK 结束，用户即使执行成功也不会提交。
4. 回填放在 `backend/db/`，导致单独的运维 SQL、甚至格式调整也套用全项目检查，重复运行不相关的前后端测试。

## 已明确的业务规则

只有正式更名新增名称历史版本；真实搬迁新建 Venue。所在地、地址、坐标、时区允许补录和录错纠正，不产生版本。并发控制和操作审计不能被当成业务版本，也不能让资料纠错无故使地图关联失效。

## 此后如何交付

- 先确认字段业务语义，再决定写哪些列。补时区只写时区及必要审计，不顺手递增修订、更新无关核验时间或重写 Live。
- 直接执行的文件应以 COMMIT 正式提交；演练版本必须单独明确标识，不能要求用户发现隐藏的提交开关或自行猜测文件用途。
- 按真实执行器验证格式。此项目远端入口只接受 SQL，已经设置遇错停止；SQL 文件不得再塞入 psql 客户端命令。
- 跨环境检查应关注所需 schema 和目标数据条件，而不是要求两个环境的执行历史完全一致。需要保护非目标数据时，在当前事务内取基线并比较执行前后。
- 支持重复执行，或者明确拒绝已执行状态。不能让失败后的重试重复审计、重复递增或造成部分写入。改版前后已有状态应有对应回归场景。
- 在测试库执行最终交付的原文件，验证提交确实生效、冲突能整笔回滚、重复执行策略正确。仅通过应用测试不能证明 SQL 可交付。
- SQL 与业务代码分开存放，验证范围随实际影响决定。独立回填不跑完整 functional；应用、API、schema 或 seed 改动仍执行规定检查。
- 文档、引用、哈希与当前脚本同步更新；明确区分历史错误脚本和当前可执行版本。不能用“保留历史记录”为理由继续让用户执行已知错误逻辑。

## 修复与证据边界

本地旧伪修订已纠正；当前 01 只补时区、02 清理旧元数据，两份均直接 COMMIT。改版通过 5 项真实 PostgreSQL 集成测试及当轮完整 functional；本次目录搬迁保持全部 SQL 字节不变，仅验证哈希和引用，不重复运行这些测试。

本地、测试库的成功不能声称为远端已成功。用户报告的远端失败也不能凭空推断为某次远端操作已提交。
