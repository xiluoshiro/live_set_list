# 乐队改名与历史阵容实现设计

## 文档定位

本文只定义乐队改名、乐队成员增加/减少/更换、历史 Setlist 录入、公开演出详情和控制台适配的技术方案。

本文同时记录已实现范围和后续设计；当前代码、FastAPI schema、Flyway SQL 和运行数据始终优先于本文。

- 乐队改名前后视为同一支乐队，保持同一个 `band_id`。
- 乐队成员改名不在本期范围内。
- 本期需要支持成员增加、减少和更换，以及同一场 Live 中旧阵容、新阵容和交接共演按歌曲交替出现。

- 本文不声明远端生产数据库的 Flyway 或数据状态。

## 范围

本期设计覆盖：

- 同一 `band_id` 下的历史名称与当前名称。
- 乐队不可变阵容版本。
- 一场普通 Live 选择一个阵容版本。
- 一场阵容交接 Live 选择两个连续版本。
- 每首 Setlist 行选择旧阵容、新阵容或交接共演。
- 按基准阵容与实际出演成员集合计算全员、非全员和特别出演。
- 公开详情、公共筛选、统计、巡演和控制台改用稳定 `band_id`。
- 现有数据迁移和新旧字段过渡。
- 开发整理期的历史版本修正与人工选择。

本期不覆盖：

- 乐队成员改名、艺名履历或同一成员的别名搜索。
- 跨乐队统一的“人物”资料页。
- 根据外部资料自动推断加入、毕业或更名日期。
- 把支持乐手、嘉宾或前成员自动认定为正式阵容成员。
- 历史资料完成后的全局锁定、按日期强制自动选择和权限收口；这些内容仅保留为 TODO。

成员名称在本期作为稳定业务值使用。拼写修正属于受审计的数据修正，不设计成员姓名版本。

## 当前实现基线与问题

### 当前数据结构

当前核心字段为：

```text
band_attrs
- id
- band_name
- band_abbr
- band_members text[]

live_setlist
- id uuid
- live_id
- song_id
- absolute_order
- segment_type
- sub_order
- band_member jsonb
- other_member jsonb
```

`band_attrs.band_members` 表示当前成员候选。`live_setlist.band_member` 使用乐队名称作为 JSON key，值是该曲实际出演成员，例如：

```json
{
  "Roselia": ["相羽あいな", "工藤晴香", "中島由貴", "櫻川めぐ", "志崎樺音"]
}
```

### 当前读取问题

公开详情查询会用当前 `band_attrs.band_members` 的长度作为 `total_count`，再以：

```text
present_count >= total_count
```

计算 `is_full`。

这会产生四类错误：

1. 修改当前名单会追溯性改变旧 Live 的满员状态。
2. 五名正式成员缺一人、再由一名嘉宾补足时，人数仍是五，但不应判定全员。
3. 五名正式成员与一名前成员同台时只能得到 `6 >= 5`，无法表达“全员＋特别出演”。
4. 同一场 Live 前后阵容变化时，单一当前名单无法解释每首歌。

当乐队名称改变时，JSON key 仍是旧名称；当前列表、详情、筛选、统计和巡演查询大量通过 `band_attrs.band_name` 与该 key 匹配，名称变化会导致历史行无法映射。

### 当前控制台问题

- `GET /api/console/bands` 只返回当前 `band_members`。
- Setlist 新增和管理共用 `band_member` JSON。
- 后端只规范化 JSON 形状并要求至少存在一个非空乐队，不严格校验乐队和成员的历史归属。
- Setlist 管理使用完整集合替换；更新时删除旧行并重新插入，因此新增关系数据必须随完整集合在同一事务内替换。
- 批量解析器按当前名单校验 `member from Band`，无法选择历史阵容。

## 核心设计

### 乐队身份、名称、阵容和出演分层

```text
band_attrs
  ├─ band_name_versions
  └─ band_lineup_versions
       └─ band_lineup_version_members

live_attrs
  └─ live_band_lineup_contexts

live_setlist
  └─ live_setlist_band_performances
       └─ live_setlist_band_performance_members
```

各层语义：

- `band_attrs.id`：乐队稳定身份。
- `band_name_versions`：该乐队在不同历史阶段使用的名称。
- `band_lineup_versions`：该乐队不同阶段的不可变正式阵容。
- `live_band_lineup_contexts`：某场 Live 使用一个阵容，或处于两个连续阵容的交接期。
- `live_setlist_band_performances`：某首歌由哪支乐队以哪种阵容模式出演。
- `live_setlist_band_performance_members`：该首歌实际登台的成员。

乐队名称变化和成员变化相互独立。THE THIRD 更名为 RAISE A SUILEN 且成员不变时，只创建新名称版本，不创建重复阵容版本。

## 数据模型

以下名称为目标结构，最终迁移可按实现时的命名规范调整。

### `band_name_versions`

```sql
CREATE TABLE public.band_name_versions (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    band_id integer NOT NULL
        REFERENCES public.band_attrs(id) ON DELETE RESTRICT,
    band_name text NOT NULL,
    band_abbr text,
    valid_from date,
    valid_to date,
    note text,
    CONSTRAINT band_name_versions_real_band
        CHECK (band_id > 0),
    CONSTRAINT band_name_versions_name_not_blank
        CHECK (btrim(band_name) <> ''),
    CONSTRAINT band_name_versions_valid_range
        CHECK (valid_to IS NULL OR valid_from IS NULL OR valid_to > valid_from)
);
```

约束和规则：

- 日期范围采用 `[valid_from, valid_to)`；`valid_to` 是不包含的结束日期。
- 同一乐队的有效日期范围不得重叠；具体使用 exclusion constraint 还是事务校验，在迁移实现时按 PostgreSQL 扩展依赖决定。
- 已被 Live 引用的名称版本不可直接删除。
- 历史 Live 显示所引用的历史名称；乐队资料页显示 `band_attrs.band_name` 的当前名称。
- 搜索当前名称和全部历史名称时都返回同一个 `band_id`。
- `band_attrs.band_name` 和 `band_attrs.band_abbr` 暂时保留为当前名称的兼容投影。

THE THIRD → RAISE A SUILEN：

```text
band_id = 6

名称版本 N1：THE THIRD
名称版本 N2：RAISE A SUILEN
```

2018-07-17 的 Live 仍引用 N1，并可在详情附注“本场宣布更名为 RAISE A SUILEN”；后续 Live 引用 N2。歌曲、统计、巡演、筛选和图标继续使用 `band_id=6`。

### `band_lineup_versions`

```sql
CREATE TABLE public.band_lineup_versions (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    band_id integer NOT NULL
        REFERENCES public.band_attrs(id) ON DELETE RESTRICT,
    version_no integer NOT NULL,
    version_label text NOT NULL,
    valid_from date,
    valid_to date,
    predecessor_id bigint,
    change_type text NOT NULL,
    note text,
    CONSTRAINT band_lineup_versions_real_band
        CHECK (band_id > 0),
    CONSTRAINT band_lineup_versions_version_positive
        CHECK (version_no > 0),
    CONSTRAINT band_lineup_versions_unique_no
        UNIQUE (band_id, version_no),
    CONSTRAINT band_lineup_versions_label_not_blank
        CHECK (btrim(version_label) <> ''),
    CONSTRAINT band_lineup_versions_change_type
        CHECK (change_type IN ('initial', 'addition', 'removal', 'replacement', 'correction')),
    CONSTRAINT band_lineup_versions_valid_range
        CHECK (valid_to IS NULL OR valid_from IS NULL OR valid_to > valid_from)
);
```

`predecessor_id` 在创建表后补充自引用外键，并由服务端校验前后版本属于同一 `band_id`。

版本规则：

- 真实成员变化不得通过原地修改旧版本表达，必须创建新版本。
- 成员增加、减少或更换时，从上一版本复制并创建下一版本。
- 开发整理期允许用 `correction` 受审计地修正历史版本成员；保存前必须展示受影响 Live 和 Setlist 行。该操作只修正资料错误，不表示真实成员变化。
- 资料集锁定后，已有历史版本不可原地增删成员；真实成员变化必须创建下一版本。
- 日期范围采用 `[valid_from, valid_to)`，只用于推荐和资料展示。
- 开发整理期内，日期用于控制台推荐，操作者仍可人工选择并固化版本。
- 同一天或同一场 Live 内发生变化时，依赖 Live 上下文和逐曲模式，不要求仅靠日期区分。

### `band_lineup_version_members`

```sql
CREATE TABLE public.band_lineup_version_members (
    lineup_version_id bigint NOT NULL
        REFERENCES public.band_lineup_versions(id) ON DELETE CASCADE,
    member_name text NOT NULL,
    display_order integer NOT NULL,
    PRIMARY KEY (lineup_version_id, member_name),
    UNIQUE (lineup_version_id, display_order),
    CONSTRAINT band_lineup_version_members_name_not_blank
        CHECK (btrim(member_name) <> ''),
    CONSTRAINT band_lineup_version_members_order_positive
        CHECK (display_order > 0)
);
```

本期不创建 `member_attrs`。同一成员是否出现在多个版本，通过相同的规范化 `member_name` 判断。

### `live_band_lineup_contexts`

```sql
CREATE TABLE public.live_band_lineup_contexts (
    live_id integer NOT NULL
        REFERENCES public.live_attrs(id) ON DELETE CASCADE,
    band_id integer NOT NULL
        REFERENCES public.band_attrs(id) ON DELETE RESTRICT,
    band_name_version_id bigint NOT NULL
        REFERENCES public.band_name_versions(id) ON DELETE RESTRICT,
    base_lineup_version_id bigint NOT NULL
        REFERENCES public.band_lineup_versions(id) ON DELETE RESTRICT,
    next_lineup_version_id bigint
        REFERENCES public.band_lineup_versions(id) ON DELETE RESTRICT,
    note text,
    PRIMARY KEY (live_id, band_id),
    CONSTRAINT live_band_lineup_contexts_real_band
        CHECK (band_id > 0),
    CONSTRAINT live_band_lineup_contexts_distinct_versions
        CHECK (
            next_lineup_version_id IS NULL
            OR next_lineup_version_id <> base_lineup_version_id
        )
);
```

语义：

- 普通 Live：只设置 `base_lineup_version_id`。
- 阵容交接 Live：同时设置 `base_lineup_version_id` 和 `next_lineup_version_id`。
- 双版本必须属于同一乐队，且 `next.predecessor_id = base.id`；该跨表约束由服务端事务校验。
- 名称版本、基础阵容和后继阵容都在保存时固化，后续修改当前 `band_attrs` 不改变历史 Live。
- 一场 Live 可以有多支乐队，每支乐队独立设置上下文。
- 开发整理期允许人工选择任一单版本，或选择两个直接连续版本。
- 历史资料锁定后的自动选择规则见后文 TODO；即使自动选择，最终版本 ID 仍需持久化，不能在公开查询时临时重算。

`base` 和 `next` 表示版本方向，不要求歌曲顺序单调。出现 `base → next → base` 是合法事实。

### `live_setlist_band_performances`

```sql
CREATE TABLE public.live_setlist_band_performances (
    setlist_id uuid NOT NULL,
    live_id integer NOT NULL,
    band_id integer NOT NULL
        REFERENCES public.band_attrs(id) ON DELETE RESTRICT,
    lineup_usage text NOT NULL,
    handover_baseline text,
    PRIMARY KEY (setlist_id, band_id),
    FOREIGN KEY (setlist_id, live_id)
        REFERENCES public.live_setlist(id, live_id) ON DELETE CASCADE,
    FOREIGN KEY (live_id, band_id)
        REFERENCES public.live_band_lineup_contexts(live_id, band_id)
        ON DELETE RESTRICT,
    CONSTRAINT live_setlist_band_performances_real_band
        CHECK (band_id > 0),
    CONSTRAINT live_setlist_band_performances_usage
        CHECK (lineup_usage IN ('base', 'next', 'handover')),
    CONSTRAINT live_setlist_band_performances_handover_baseline
        CHECK (
            (lineup_usage = 'handover' AND handover_baseline IN ('base', 'next'))
            OR
            (lineup_usage <> 'handover' AND handover_baseline IS NULL)
        )
);
```

为支持 `(setlist_id, live_id)` 外键，migration 需要在 `live_setlist(id, live_id)` 上增加唯一约束。`live_id` 在演出关系中属于有意冗余，用于把逐曲 Band 在数据库层约束到同一场 Live 的阵容上下文，避免只依赖应用校验。

规则：

- `base`：以 Live 上下文的基础阵容作为该曲基准。
- `next`：以 Live 上下文的后继阵容作为该曲基准。
- `handover`：表示同曲出现两个连续阵容的交接共演；必须另存 `handover_baseline=base|next`，明确旧阵容或新阵容哪一方是正式基准。
- 普通 Live 只能提交 `base`。
- 没有 `next_lineup_version_id` 时不得提交 `next` 或 `handover`。
- `handover_baseline` 不根据实际成员自动反推，控制台建议后仍须由操作者确认并持久化。
- `handover` 主要用于成员增加、减少或替换；以 `base` 为基准时新增成员属于 `incoming`，以 `next` 为基准时仍出演的旧成员属于 `former`。

### `live_setlist_band_performance_members`

```sql
CREATE TABLE public.live_setlist_band_performance_members (
    setlist_id uuid NOT NULL,
    band_id integer NOT NULL,
    member_name text NOT NULL,
    display_order integer NOT NULL,
    appearance_role text,
    PRIMARY KEY (setlist_id, band_id, member_name),
    UNIQUE (setlist_id, band_id, display_order),
    FOREIGN KEY (setlist_id, band_id)
        REFERENCES public.live_setlist_band_performances(setlist_id, band_id)
        ON DELETE CASCADE,
    CONSTRAINT live_setlist_band_performance_members_name_not_blank
        CHECK (btrim(member_name) <> ''),
    CONSTRAINT live_setlist_band_performance_members_order_positive
        CHECK (display_order > 0),
    CONSTRAINT live_setlist_band_performance_members_role
        CHECK (
            appearance_role IS NULL
            OR appearance_role IN ('former', 'incoming', 'guest', 'support')
        )
);
```

`appearance_role` 只补充展示语义，不参与正式阵容判断。下列分类优先由版本集合推导：

- 在 `next - base` 中：新成员。
- 在 `base - next` 中：旧成员或前成员。
- 两个版本都不包含：嘉宾或支持成员，控制台需要显式选择角色。

## 满员与交接状态计算

### 普通单版本

设：

```text
E = 该行所选阵容版本的正式成员集合
P = 该行实际出演成员集合

missing = E - P
extra   = P - E
```

返回状态：

| 条件 | `attendance_status` | 公共文案 |
|---|---|---|
| `missing`、`extra` 均为空 | `full` | 全员 5/5 |
| `missing` 为空、`extra` 非空 | `full_plus` | 全员 5/5＋特别出演 1 |
| `missing` 非空 | `partial` | 非全员 4/5 |
| 没有可靠版本 | `unknown` | 阵容未知 · 实际出演 4 人 |

不能再使用 `present_count >= total_count`。

例如正式成员 `A/B/C/D/E`，实际出演 `A/B/C/D/X`：

```text
present_count = 5
expected_count = 5
missing = [E]
extra = [X]
status = partial
```

人数相等不能抵消正式成员缺席。

### 双版本 Live

设：

```text
V1 = base 阵容
V2 = next 阵容
incoming = V2 - V1
outgoing = V1 - V2
```

每首歌必须持久化 `lineup_usage`：

- `base`：对比 V1。
- `next`：对比 V2。
- `handover + handover_baseline=base`：对比 V1；实际出现的 `incoming` 成员单列为“新成员特别出演”。
- `handover + handover_baseline=next`：对比 V2；实际出现的 `outgoing` 成员单列为“前成员特别出演”。

对于 Roselia V1 → V2 的交接场：

| 歌曲 | 实际出演 | usage / handover baseline | 结果 |
|---|---|---|---|
| 第1首 | V1完整成员 | `base` | V1 全员 |
| 第2首 | V1完整成员＋V2新增成员 | `handover / base` | 旧阵容全员＋新成员特别出演1 |
| 第3首 | V2完整成员＋V1离开成员 | `handover / next` | 新阵容全员＋前成员特别出演1 |
| 第4首 | V2完整成员 | `next` | V2 全员 |
| 第5首 | V1完整成员 | `base` | V1 全员 |

模型不要求阵容模式随歌曲单调变化，因此可以准确保留旧成员间歇返场。

若一行以 `next` 为基准且旧成员额外出演，则显示：

```text
新阵容全员 5/5＋前成员特别出演 1
```

### 自动建议与最终固化

控制台可根据实际成员自动建议逐曲模式：

1. `P == V1`：建议 `base`。
2. `P == V2`：建议 `next`。
3. `V1 ⊆ P` 且 `P` 包含 `incoming`：建议 `handover + base`。
4. `V2 ⊆ P` 且 `P` 包含 `outgoing`：建议 `handover + next`。
5. 其他情况分别计算相对 V1、V2 的 `missing/extra`。
6. 只有一个候选明显更接近时才建议正式基准；结果并列或存在缺席时要求操作者确认。

自动建议不替代持久化。保存后必须以逐曲 `lineup_usage` 为准，不能在公开查询时重新推断。

## 公开 API 与详情展示

### 详情响应

`detail_rows[].band_members[]` 目标结构：

```json
{
  "band_id": 4,
  "band_name": "Roselia",
  "lineup_usage": "handover",
  "handover_baseline": "next",
  "lineup_version": {
    "lineup_version_id": 21,
    "version_label": "Roselia V1"
  },
  "next_lineup_version": {
    "lineup_version_id": 22,
    "version_label": "Roselia V2"
  },
  "attendance_status": "full_plus",
  "expected_count": 5,
  "present_count": 6,
  "present_members": ["..."],
  "missing_members": [],
  "extra_members": [
    {
      "member_name": "中島由貴",
      "category": "incoming"
    }
  ]
}
```

旧字段过渡：

- `present_count` 可以保留。
- `total_count` 改名或映射为 `expected_count`。
- `is_full` 不足以表达 `full_plus`，只可在兼容期定义为 `missing_members` 为空；新前端使用 `attendance_status`。
- 不再使用固定五人的缺省总数。没有版本时返回 `unknown`。

### Setlist 列表

乐队图标状态扩展为：

- `full`：现有全员样式。
- `partial`：现有非全员样式。
- `full_plus`：新增“全员＋特别出演”样式。
- `unknown`：中性无状态样式。

双版本 Live 在 Setlist 上方显示轻量说明：

```text

```

每行乐队图标或状态标签显示：

```text

交接共演（新阵容基准）· 全员＋前成员特别出演1
V2 全员
V1 全员
```

不使用一次性的“从此处永久切换”分隔线作为事实展示，因为旧成员可能在后续歌曲再次返场。

- 当前乐队资料页标题显示当前名称。
- 历史名称可显示为“曾用名”，但不创建第二套统计。
- 搜索 THE THIRD 或 RAISE A SUILEN 都返回 `band_id=6`。
- 图标继续使用 `/icons/Band_6.svg`。

## 公共查询和统计改造

下列路径不再解析 `live_setlist.band_member` 的乐队名称 key，而是读取 `live_setlist_band_performances.band_id`：

- Live 列表有效乐队与 `band_id` 筛选。
- 单条和批量详情。
- Catalog 乐队搜索与乐队 Live 列表。
- 公共统计的实际演唱乐队。
- 巡演显式乐队过滤和相邻 Setlist 比较。
- 活动组候选的有效乐队。
- 跨乐队翻唱判断。

既有语义保持：

- 有 Setlist 时，实际乐队来自逐曲演出关系。
- 完全没有 Setlist 时，才回退 `live_attrs.default_band_ids`。
- `song_list.band_id` 仍表示歌曲目录归属。
- 乐队改名前后因 `band_id` 相同而连续统计。

展示名称使用 Live 上下文的 `band_name_version_id`；聚合身份始终使用 `band_id`。

## 活动出演成员

当前 `event_attendees` 用当前 `band_attrs.band_members` 判断 `full/partial`，也会发生历史漂移。

本设计要求：

- `event` 类型 Live 为参与乐队保存 `live_band_lineup_contexts`。
- 没有 Setlist 的活动成员出席，以该 Live 固化的基础阵容版本为基准进行集合比较。
- 活动出席 API 同样返回 `attendance_status / expected / missing / extra`。
- 第一阶段不为无 Setlist 活动提供逐曲 `handover`；如确有交接活动，录入 Setlist 后使用逐曲模型。

## 控制台设计

### 乐队管理

新增独立的“乐队管理”，不把名称和阵容维护塞进 Setlist 表格。

页面包含：

- 当前名称、缩写和 `band_id`。
- 历史名称列表。
- 当前阵容和全部阵容版本时间线。
- 使用该版本的 Live 数量。
- 从上一版本创建新版本。
- 变化类型：增加、减少、更换、资料修正。
- 有引用版本禁止删除。
- 开发整理期允许以“资料修正”方式编辑历史版本，但必须预览受影响 Live、二次确认并写审计。
- 历史资料锁定后，历史版本改为只读。

乐队改名操作：

1. 关闭旧名称版本的有效期。
2. 创建新名称版本。
3. 更新 `band_attrs.band_name/band_abbr` 当前投影。
4. 保持 `band_id`、歌曲归属、巡演关系和图标不变。
5. 写 `audit_logs`。

### Live 管理

Live 创建或管理中，为每支有效乐队增加“阵容上下文”：

- 有 Setlist Live 继续按 `live_date` 推荐逐曲使用的版本，并允许在开发整理期人工改选。
- 当前既有无 Setlist 活动均使用最新 Band；新增默认 Band 时直接选择当前开放名称与当前开放阵容。
- `ALLOW_HISTORICAL_DEFAULT_BAND_SELECTION=true` 时，控制台仅为资料补录临时开放无 Setlist 默认 Band 的旧名称、旧阵容人工选择。
- 资料补录完成后把该开关设为 `false`；关闭入口不删除或重算已经固化的历史上下文。
- 普通 Live 只选一个版本。
- 勾选“本场发生阵容交接”后，开发整理期允许选择两个直接连续版本。
- 双版本显示差异：
  - 保留成员。
  - 离开成员。
  - 新增成员。

开发整理期内日期只为 Setlist 上下文产生推荐；无 Setlist 默认 Band 以最新版本为默认值。保存时始终固化版本 ID。

### 历史资料锁定 TODO

历史 Live 和历史阵容资料全部整理完成后，控制台收口为：

- 已锁定的历史名称版本和阵容版本只读，不再提供普通编辑。
- Setlist 录入不再显示任意历史版本选择器；系统按 `live_date` 自动选择该日期生效的最新阵容版本。
- 无 Setlist 默认 Band 不再显示旧版本选择器，只使用当前开放名称与当前开放阵容。
- “该日期生效的最新版本”定义为满足 `[valid_from, valid_to)` 的唯一版本；若数据缺失或重叠，阻止保存并要求先修正版本时间线。
- Live 标记为阵容交接时，系统只允许使用“该日期生效的最新版本”和它的直接上一版本。
- 对交接 Live，`base_lineup_version_id = latest.predecessor_id`，`next_lineup_version_id = latest.id`。
- 操作者仍可逐曲选择 `base / next / handover`，但不能把 Live 改接到其他不相邻历史版本。
- 新发生的成员变化仍可创建未来版本；已经锁定的旧版本不因新版本创建而解锁。
- 自动选择结果继续持久化到 `live_band_lineup_contexts`，公开读取不按日期动态重算。

该收口机制当前只作为 TODO，不纳入第一阶段 migration、API 和 UI 验收。后续实现时再确定使用全局资料状态、版本 `locked_at` 字段或部署配置控制。

### Setlist 新增与管理

当前成员浮层改为：

```text
Roselia
本场阵容：V1 → V2

本曲模式
( ) V1
( ) V2
( ) 交接共演

交接正式基准（仅交接共演）
( ) 旧阵容 V1
( ) 新阵容 V2

V1/V2成员
[x] 共通成员A
[x] 共通成员B
[x] 前成员
[x] 新成员

其他成员
[ ] 嘉宾
[ ] 支持成员
```

交互要求：

- 选择整支乐队时，只填当前行所选模式的基准阵容，不能把两个版本简单合并为“正式阵容”。
- 选择 `handover` 时默认填 V1 成员作为编辑起点，但“正式基准”是独立必填项，可明确选择旧阵容或新阵容；切换正式基准不静默覆盖已勾选的实际出演成员。
- 提供“应用到选中行”和“从本行起应用”作为批量编辑工具。
- 批量应用只是编辑便利；之后每行仍可覆盖，因此支持 `V1 → V2 → V1`。
- 保存前逐行预览状态和缺席/额外成员。
- 模式建议有歧义时阻止直接确认，并定位到具体行。

现有完整集合替换继续保留。提交时在同一事务内：

1. 锁定 Live。
2. 校验 Live 阵容上下文。
3. 校验歌曲和顺序。
4. 替换 `live_setlist` 完整集合。
5. 随每个新 Setlist UUID 写入乐队演出关系和实际成员。
6. 写现有 `live_setlist_update` 审计。

### 批量粘贴解析

- 乐队名称匹配当前名称和历史名称，结果转为稳定 `band_id`。
- `member from Band` 在本场所选一个或两个阵容版本的成员并集中校验。
- 普通 Live 的整团 token 填入唯一版本成员。
- 双版本 Live 的整团 token 不自动合并两个版本；使用当前行默认模式。
- 解析后运行逐曲模式建议。
- 无法映射的成员进入现有 `other_member` 或要求人工选择 `guest/support`，不能静默成为正式成员。

## 迁移与数据过渡

### Migration 版本

当前仓库已新增：

- `V21__add_band_name_and_lineup_history.sql`：创建名称版本、阵容版本、Live 上下文和逐曲出演关系。
- `V22__add_handover_baseline.sql`：为交接共演增加显式旧/新正式基准；既有 `handover` 行一次性兼容回填为 `base`，之后由约束保证 handover 必填、其他模式为空。
- `V23__enforce_handover_baseline_not_null.sql`：在不修改已执行 V22 的前提下修正 PostgreSQL `CHECK` 的 `NULL` 三值逻辑，显式要求 handover 基准非空。

业务历史版本和 Live 映射不硬编码进 migration。绝不修改已经执行的 B1 或 V2～V22。

迁移需要：

- `SET ROLE live_project_owner` 创建对象。
- 新表、约束、索引和 identity sequence 归属 `live_project_owner`。
- `live_project_ro` 获得公开读取所需 `SELECT`。
- `live_project_super_ro` 获得控制台所需 `SELECT/INSERT/UPDATE`。
- 完整集合子表仅向 `live_project_super_ro` 授予窄范围 `DELETE`。
- 不改变 `flyway_schema_history` owner。

### 当前数据回填

用户已确认当前主库 `band_member` 尚无逐曲成员变化。常规回填可以按已确认的当前名单进行，但存在一个明确例外：

```text
当前唯一一套 2015 年 Poppin'Party 数据
=> Poppin'Party V1

当前主库内其余现存 Poppin'Party 数据
=> Poppin'Party V3
```

该例外只执行一次受审计手工修改，不为年份建立长期硬编码规则，也不推导其他乐队版本。

本地主库已按以下步骤完成数据准备；schema migration 本身仍不包含任何业务数据：

1. 首个 migration 只创建新结构，不切换公共读取。
2. 通过乐队管理或受审计脚本更新少数尚未最新的 `band_attrs`。
3. 按 Band 展示“当前名称＋当前成员”候选清单，并要求全部确认。
4. 为每个已确认的真实 Band 创建当前名称版本和初始当前阵容版本。
5. 将现有 `live_setlist.band_member` 的乐队名精确映射到 `band_attrs.id`。
6. 为涉及的 Live 建立单版本 `live_band_lineup_contexts`。
7. 为每行建立 `live_setlist_band_performances` 和实际成员。
8. 创建 Poppin'Party V1 和 V3 后，将唯一一套 2015 年数据的 Live 上下文手工改为 V1；其余现存 Poppin'Party Live 保持 V3。
9. 回填前后核对 Setlist 行数、逐曲乐队数、成员数、有效乐队集合和详情抽样。

2026-07-26 本地主库执行结果：

- 自动回填前只读预检通过，无阻断问题。
- 回填 2733 条 Setlist、2822 条逐曲乐队出演、13562 条实际成员关系和 283 条 Live/Band 上下文。
- 回填后没有未映射 Setlist，也没有缺少 Live/Band 上下文的出演。
- 唯一手工目标为 `live_id=50`，日期 `2015-04-18`，标题 `BanG_Dream! 1st Live 「春、バンド始めました！」`；12 条 Setlist 对应上下文已从 Poppin'Party V3 改绑 V1，逐曲 `lineup_usage` 保持 `base`。
- Poppin'Party V1 / V3 的阵容版本 ID 分别为 `1` / `3`；改绑后主库为 V1 1 场、V3 22 场。
- `2026-06-21`、`2026-07-18`、`2026-07-19` 三场 Live 中涉及的 millsage / 一家Dumb Rock! 上下文均已由自动回填绑定 V2，无需重复修改。

一次性手工修改需要：

- 先按明确 Live ID 展示目标 Live 日期、标题和当前版本。
- 只修改该 Live 的 Poppin'Party `base_lineup_version_id`。
- 该 Live 的逐曲 `lineup_usage` 保持 `base`，不制造交接状态。
- 写审计记录，包含旧版本、新版本和受影响 Setlist 行数。
- 修改后确认 2015 年目标数据全部使用 V1，其他现存 Poppin'Party 数据全部使用 V3。

迁移必须在以下任一情况停止，不得猜测：

- JSON 乐队名称无法唯一映射到 `band_id`。
- 成员值不是可规范化的非空数组。
- 当前实际成员无法由待绑定版本解释，且未被明确标记为额外成员。
- 同一 Live/Band 出现无法确定的版本上下文。

### 后续历史 Live 录入

录入成员变化前的历史 Live 时：

1. 先在乐队管理中建立历史名称版本和历史阵容版本。
2. 开发整理期再创建或管理 Live，并人工确认对应一个或两个连续版本。
3. 最后录入 Setlist 的逐曲模式和实际成员。

历史阵容业务数据不硬编码在 Flyway migration 中，应通过控制台或一次性受审计数据脚本录入。

历史资料锁定后的新增规则由前述 TODO 接管：普通 Live 按日期自动选择，交接 Live 只能使用当日最新版本和直接上一版本。

### 兼容期

分阶段切换：

1. 新表落地并回填，旧 `band_member` 保留。
2. 后端写接口在一个事务内双写旧 JSON 和新关系，便于对照。
3. 公共读取切到新关系，增加一致性检查。
4. 统计、巡演、活动组和控制台读取全部切换到 `band_id`。
5. 确认无旧读取后，停止写旧 JSON。
6. 是否删除 `live_setlist.band_member` 和 `band_attrs.band_members` 另行决定；本设计不要求首期物理删除。

在第4步完成前，不开放带历史乐队名称或历史阵容的 Live 正式写入。旧读取仍按 JSON 名称 key 匹配当前 `band_attrs.band_name`，过早写入 THE THIRD 等历史名称会造成临时漏数。

`band_attrs.band_members` 在兼容期仅作为当前阵容投影：

- 乐队管理创建新的当前阵容时，在同一事务更新该字段。
- 不允许绕过乐队管理直接编辑。
- 历史详情永远不读取它计算满员状态。

## 一致性、并发与审计

- 乐队名称和阵容版本创建使用 `get_write_db_connection()`。
- 创建下一阵容版本时锁定对应 `band_attrs`，防止并发生成重复 `version_no`。
- Live 更新和 Setlist 完整替换继续锁定 `live_attrs`。
- 已被引用的名称或阵容版本不可删除。
- 乐队改名、阵容版本新增、Live 阵容上下文变化和 Setlist 更新都写 `audit_logs`。
- 审计 payload 记录版本 ID、版本标签、成员差异和受影响 Live；不记录仅由查询计算的状态。

## 不采用的方案

### 直接修改 `band_attrs.band_members`

会追溯性改变历史 Live，不采用。

### 乐队改名时创建两个无关联 Band

会拆分歌曲归属、统计、筛选、巡演和图标，不采用。

### 为本期创建成员实体与姓名履历

成员改名明确不在范围内；当前只需表达版本成员集合，使用 `member_name` 足够，不采用额外人物主表。

### 双版本直接取并集作为满员阵容

会把正常旧阵容或新阵容误判为缺席，也无法表达哪一方是正式基准，不采用。

### 只保存 Live 级切换点

旧成员可能在新成员登场后再次返场；只保存单调切换点无法表示 `V1 → V2 → V1`，不采用。

### 查询时根据实际成员重新推断模式

推断规则变化会改写历史结果；控制台可以建议，但最终必须持久化逐曲 `lineup_usage`，不采用纯动态推断。
