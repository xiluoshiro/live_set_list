## 2. 设计解读与硬边界

Design Read：这是面向演出资料查询者的单场 Live 档案页全量重构，视觉语言为舞台张力与编辑档案的结合，使用原生 React 和 CSS 构建新的页面级视觉系统。

设计参数：

| 参数 | 值 | 解释 |
|---|---:|---|
| `DESIGN_VARIANCE` | 7 | 使用不对称标题区和连续舞台流程，但不牺牲资料阅读顺序 |
| `MOTION_INTENSITY` | 3 | 只保留状态反馈、展开和焦点转移，不做滚动劫持或持续动画 |
| `VISUAL_DENSITY` | 7 | 面向长歌单和复杂出演关系，使用紧凑排版、留白和分隔线组织信息 |

### 2.1 全量重构边界

本次不以复用现有可见实现为目标：

- 不复用现有详情卡片、表格、弹窗、CSS class、圆角尺度或页面 DOM 结构。
- 不要求新页面适配 `detail-page.css` 或 `detail-modal.css` 的视觉约束。
- 不以现有 `LiveDetailContent` 和 `MemberStatusTable` 的组件边界作为新组件拆分依据。
- 可以删除或替换仅服务旧详情页的可见组件和样式，但删除前必须完成调用点和测试迁移。

必须保留的只有业务与数据语义：

- `live_id`、状态、日期、时间、场馆、类型和官方来源。
- Live 与 Band、Tour、Performance Group 的关系。
- Event 出席阵容。
- 逐曲出演 Band、阵容版本、缺席成员、额外出演、翻唱和短版语义。
- 登录、收藏权限、CSRF、错误处理和返回后滚动恢复等应用级行为。

### 2.2 非目标

本轮不负责：

- 重构首页、演出列表、巡演详情或控制台。
- 用视觉推断歌单完整度、验证状态或演出时长。
- 在没有数据来源的情况下新增编辑者、证据、照片、票根或用户参加记录。
- 将 Tour 和 Performance Group 合并为同一种关系。
- 为了气氛加入自动播放音视频、大幅海报或滚动劫持。

### 2.3 成熟控件原语选型

视觉从零建立不等于从零实现复杂控件行为。新详情页选择 [Radix Primitives](https://www.radix-ui.com/primitives/docs/overview/introduction) 作为唯一的 Headless 控件原语层：

- 官方定位是无样式、可组合的 React 控件原语，适合在其上建立项目自己的设计系统。
- 官方负责常见 WAI-ARIA 语义、键盘导航和焦点管理，减少自行实现浮层与展开控件的边界错误。
- 当前官方推荐安装可 Tree Shaking 的 `radix-ui` 聚合包，避免多个独立包发生共享依赖重复或版本漂移。
- 新页面继续使用普通 CSS 和项目自己的语义令牌，不引入 Radix Themes 或其默认视觉。

实施时先检查 `frontend/package.json`，确认仍未存在同类 Headless 控件库，再安装：

```powershell
cd frontend
npm install radix-ui
```

控件使用范围：

| 页面能力 | 实现选择 | 原因 |
|---|---|---|
| 歌曲和 Event 成员原位展开 | `Collapsible` | 统一 `aria-expanded`、键盘和受控状态 |
| 分享或更多操作的轻量浮层 | `Popover` | 处理定位、焦点移入和外部关闭 |
| 图标按钮补充说明 | `Tooltip` | 支持键盘和指针触发，不代替可访问名称 |
| 移动端更多操作 | `DropdownMenu` | 使用标准菜单键盘模型 |
| 必须阻断流程的确认 | `AlertDialog` | 只用于真实破坏性确认，不用于曲目详情 |
| 普通链接、按钮、列表、标题 | 原生 HTML | 原生语义已经足够，不额外包控件 |
| 演出流程和页内导航 | `ol/li`、`nav/a` | 这不是 Tabs 或 Accordion，不误用复合控件 |

使用限制：

- 不混用 Radix Primitives、Base UI、React Aria Components 或 Headless UI。
- 不引入 Radix Themes，不导入通用主题 CSS，不接受默认圆角、阴影和配色。
- 所有原语先经过项目级薄封装，再由 Stage Ledger 页面使用，业务组件不散落库特有细节。
- 不把每首歌包装为 `Accordion.Item`。歌曲仍是连续有序列表，只有详情内容使用 `Collapsible`。
- 不使用 `Dialog` 复刻现有居中曲目详情弹窗。
- 不为纯文本或不具备操作的元素添加 Tooltip。
- 原语只能解决行为和语义，颜色对比、焦点可见性、触控尺寸和文案仍由项目负责。

## 4. 产品目标和体验指标

新页面应达到以下结果：

1. 用户在 10 秒内识别 Live 标题、状态、日期、时间、场馆和出演 Band。
2. 用户在 30 秒内找到演出流程、Event 出席阵容、所属 Tour 或活动集合。
3. 用户不需要理解数据库字段即可区分主篇、Opening、Encore、W Encore 和 Rehearsal。
4. 用户可以在 41 曲、10 Band 的页面中快速跳到某一段落或某一 Band。
5. 用户可以理解逐曲实际出演、目录归属和阵容版本，不把它们误认为同一概念。
6. 页面在 320 CSS px 下不出现页面级横向滚动或被隐藏的核心信息。

## 5. 总体设计方向

设计代号为 `Stage Ledger`，中文工作名为“舞台档案”。

视觉来源分工：

- 02 的舞台方向负责氛围、Band 色轨和现场张力。
- 06 的长文方向负责网格、字号层级、留白和连续阅读。
- 07 的链接日志方向负责 Tour、活动集合、官方来源和历史关系。

三者不做组件拼贴。页面使用一套统一的字体、色彩、形状和交互规则。

### 5.1 视觉原则

- 演出身份先于歌单，歌单紧跟在 Masthead 之后。
- 歌名先于标签，实际出演先于目录归属。
- 关系通过位置、文字和线条表达，不依赖一排药丸标签。
- Band 色用于数据编码，不作为大面积背景。
- 卡片只用于真正需要浮层层级的逐曲检查器，不用于包裹每一段元数据。
- 页面明暗主题保持同一构图，不在页面中途反转主题。

## 6. 页面信息架构

```text
全局导航
  Logo | 演出档案 | 搜索 | 主题 | 用户

面包屑
  演出档案 / Tour 或活动集合 / 当前 Live

演出 Masthead
  状态与类型
  Live 标题
  出演 Band
  日期、开场、开演、场馆
  Tour 与 Performance Group 关系
  官方来源
  收藏与分享

档案摘要
  已收录曲目数 | 出演 Band 数 | 段落数 | 阵容记录状态

页内导航
  演出流程 | 出演阵容 | 关联档案 | 资料来源

自适应正文
  演唱类 -> 演出流程 -> 逐曲检查器 -> 阵容摘要
  Event -> 出席阵容 -> 可选演出流程 -> 关联资料
  取消/延期 -> 状态说明 -> 原定信息 -> 官方资料

关联档案
  Tour | Performance Group | 同组或相邻场次

资料来源
  官方链接 | 正式改期历史
```

### 6.1 桌面构图

- 页面最大内容宽度为 1280-1360px。
- Masthead 使用 12 列不对称网格，标题区域占 7-8 列，日期与场馆占 4-5 列。
- Masthead 视觉高度控制在 360-430px，不使用全屏 Hero。
- 在 1440x900 下，用户应同时看到完整演出身份和演出流程标题或首个内容行。
- 演出流程区域使用 8+4 列。左侧为连续歌单，右侧为按需出现的逐曲检查器。
- 没有选中歌曲时，右侧显示本场阵容摘要，不显示空白灰框。

### 6.2 移动构图

- 小于 768px 时严格切换为单列，不保留桌面不对称偏移。
- 390px 和 320px 下页面水平内边距分别建议为 16px 和 12px。
- Masthead 顺序固定为状态、标题、Band、日期时间、场馆、关系、操作。
- 桌面逐曲检查器改为歌曲行下方原位展开。
- 固定操作栏只显示当前有能力完成的收藏、分享和官方来源。
- 取消场次不显示收藏操作。

## 7. 演出 Masthead

### 7.1 必显信息

- `event_status` 和 `date_phase` 组合后的用户状态。
- `live_type` 的中文名称。
- `live_title`，允许自然换行，不做两行截断。
- `band_names`，与 `bands` 按顺序映射为可访问链接。
- `live_date`、`opening_time`、`start_time` 和 `venue`。
- `tour` 和 `performance_group`，存在时分别显示。
- `url` 对应的官方来源入口。
- 登录且场次未取消时的收藏操作。
- 分享操作，优先使用 Web Share API，回退为复制永久 URL。

### 7.2 档案摘要

档案摘要是一条横向标尺，不使用四张等宽指标卡。

演唱类示例：

```text
41 TRACKS    10 ACTS    MAIN SET    逐曲出演已记录
```

Event 示例：

```text
7 BANDS    出席阵容已记录    暂无演出曲目
```

状态类示例：

```text
已取消    未形成歌单    官方资料可用
```

不得显示当前数据不能证明的“完整”“已验证”或预计演出时长。

## 8. 演出流程

### 8.1 连续流程模型

演出流程使用语义化有序列表，不使用表格和歌曲卡片。

```text
MAIN SET                                        M01-M41

RAISE A SUILEN
01  R·I·O·T
02  V.I.P MONSTER
03  OUTSIDER RODEO

AFTERGLOW
05  燦々
06  Hey-day狂騒曲

JOINT PERFORMANCE
11  えがおのオーケストラっ！
    夢限大みゅーたいぷ × ハロー、ハッピーワールド！
```

### 8.2 分段规则

| 段落码 | 默认文案 | 呈现规则 |
|---|---|---|
| `M` | Main Set | 主篇 |
| `OP` | Opening Act | 暖场或开场段 |
| `EN` | Encore | 安可 |
| `WEN` | W Encore | 二次安可或资料原始 W Encore 语义 |
| `RH` | Rehearsal | 彩排 |
| 其他值 | 原始段落码 | 不丢弃未知值，使用原值回退 |

同一段落内按 `absolute_order` 排序。连续出演 Band 集合相同的条目组成视觉区块，但不改变数据中的段落和编号。

### 8.3 Band 色轨

- 每个连续出演区块使用 3-4px 实色轨。
- 单 Band 使用一条代表色。
- 多 Band 联合演出使用并列实色段，不使用渐变混色。
- 色轨旁必须同时显示 Band 名称或图标，颜色不能成为唯一识别手段。
- 没有可靠代表色时使用中性轨道，不根据 Band 名称随机生成高饱和颜色。

### 8.4 曲目行层级

曲目行从强到弱依次为：

1. 歌名。
2. 仅在需要时显示的实际出演 Band。
3. 翻唱归属、短版和其他出演者摘要。
4. 逐曲成员和阵容版本详情。

翻唱文案应区分：

- `song_list.is_cover=true`：显示“翻唱”，不捏造原 Band。
- 实际出演 Band 不包含歌曲目录 Band：显示“翻唱自 {cover_band.band_name}”。

### 8.5 长歌单导航

满足任一条件时显示流程跳转器：

- 曲目数大于 20。
- 出演 Band 数大于 3。
- 段落数大于 2。

跳转器按段落和 Band 分组。普通 14 曲单独公演不显示无意义的目录。

## 9. 逐曲检查器

### 9.1 内容

逐曲检查器展示：

- 实际出演 Band。
- `attendance_status` 和预期、实到、缺席人数。
- `present_members` 和 `missing_members`。
- `extra_members`，类别为前成员、新成员、嘉宾或支援。
- `lineup_version`、`next_lineup_version`、`lineup_usage`。
- `handover_baseline` 对交接共演满员判断的含义。
- `other_members`。
- 翻唱归属和短版状态。

### 9.2 交互

- 桌面点击歌曲后在右栏更新检查器，不打开居中模态框。
- 移动端点击后在当前歌曲下方展开。
- 再次点击同一歌曲收起。
- `Escape` 关闭桌面检查器或移动展开，并将焦点返回触发歌曲。
- URL hash 可选地记录当前歌曲，例如 `#track-M11`，刷新后应能恢复定位。
- 切换歌曲只使用 `opacity` 和小幅 `transform`，时长不超过 180ms。
- 原位展开使用项目封装的 Radix `Collapsible`，但 DOM 仍保持在对应 `li` 内，不破坏有序列表阅读顺序。

### 9.3 阵容交接

阵容交接以实际歌曲行为准，不在整个 Live 顶部给出模糊的“阵容变更”徽章。

```text
Roselia V1 | 交接共演 | Roselia V2
正式满员基准：新阵容
```

`attendance_status=unknown` 时明确显示“阵容基准未知”，不得回退为当前默认阵容或固定人数。

## 10. Event 内容路径

### 10.1 默认顺序

Event 的正文顺序为：

1. 出席阵容。
2. 存在时的演出流程。
3. 活动集合与 Tour 关系。
4. 官方来源。

### 10.2 出席阵容

每个 Band 使用一行可展开记录：

```text
Roselia          全员出席
Poppin'Party     4 / 5
Afterglow        部分成员
```

展开后显示完整成员名单。7 Band Event 仍保持单列或两列分组，不做 7 张独立卡片。

### 10.3 Event 空状态

没有歌单但有出席阵容时，不出现“暂无歌单”大面板，档案摘要使用弱提示即可。

两者都没有时显示：

> 本页目前只收录演出基本资料，暂无出席阵容或演出曲目记录。

该状态不能使用错误图标或加载失败文案。

## 11. 取消、延期与改期

### 11.1 取消

- Masthead 使用贯穿内容列的取消状态线和明确文字。
- 隐藏收藏操作。
- 保留分享和官方来源。
- 不渲染空歌单容器。
- 即使历史数据意外保留 Setlist，公开页面也不将其作为正常演出流程展示，除非产品需求另行确认。

### 11.2 延期

- 主状态先显示当前 `date_phase`，辅助状态显示“延期”。
- `status_note` 紧邻状态，不放在页面底部。
- `schedule_history` 存在时，显示原定标题、日期、时间、场馆和修改说明。
- 仅展示实际发生变化的字段。

### 11.3 已改期并完成

- 当前日期、时间和场馆保持主信息。
- “曾改期”作为辅助状态。
- 原定信息在资料来源区域按时间顺序展示。

## 12. 关联档案

Tour 和 Performance Group 是两种并列关系：

- Tour 表示连续巡演场次，可进入场次时间线和歌单比较。
- Performance Group 表示同一活动的多日或多场集合，不默认具有连续歌单比较语义。
- 同一 Live 可以同时展示两者。

关联区使用 07 的链接档案思路，以文字链路和时间顺序组织，不使用两张外观完全相同的关系卡。

当前详情响应只有反向引用。若要显示上一场、下一场或本场变化摘要，应按需读取 Tour 或 Performance Group 详情，不在首屏阻塞主详情渲染。

所有统计文案使用“本站已收录”，不得暗示官方巡演全量覆盖。

## 13. 视觉系统

### 13.1 主题

使用页面级 CSS 变量实现浅色、深色和跟随系统。两种主题保持相同结构和层级。

- 浅色：冷白或浅灰底、近黑正文、低对比冷灰分隔线。
- 深色：蓝黑底、暖白正文、略亮的冷灰分隔线。
- 全局交互仅使用一种信号强调色。
- Band 色是数据色，不替代全局交互色。
- 取消、延期和成功状态使用独立语义色，但只出现在真实状态区域。

不使用：

- 通用紫蓝渐变。
- 大面积磨砂玻璃和 `backdrop-filter`。
- 文字外发光和霓虹描边。
- 每个区块独立切换明暗主题。

### 13.2 字体

- 标题使用支持中日文的现代无衬线字体。
- 数字、曲目编号和时间使用等宽数字字体。
- 不为了“编辑感”混入无业务理由的衬线字体。
- 桌面 Live 标题建议使用 `clamp(2.25rem, 5vw, 4.5rem)`，但以两到三行内完整显示为约束。
- 移动端 Live 标题建议为 30-38px。
- 歌名桌面 17-18px，移动端 16-17px。
- 辅助信息不得低于 12px。

### 13.3 形状

- 页面主体以直角和 0-8px 小圆角为主。
- 不使用 `999px` 作为通用标签形状。
- 圆形只用于 Band 图标、头像和明确的图标按钮。
- 歌曲行不使用独立阴影或浮层。

### 13.4 分隔与层级

- 优先使用留白、字号、字重和单侧分隔线。
- 长列表只在区块边界使用分隔线，不给每行同时添加上下边框。
- 阴影仅用于桌面逐曲检查器的浮层关系，并使用与背景同色相的弱阴影。

### 13.5 控件封装规则

在 Stage Ledger 业务组件之前建立小型无样式控件层，例如：

```text
frontend/src/components/ui/
  Collapsible.tsx
  Popover.tsx
  Tooltip.tsx
  DropdownMenu.tsx
  AlertDialog.tsx
```

该目录只负责：

- Radix part 组合和 Portal 位置。
- 公共可访问名称、焦点返回和 Escape 行为约束。
- `data-state` 到项目 CSS class 的稳定映射。
- 必要的测试辅助属性，但不包含 Live 业务判断。

该目录不负责：

- Masthead、歌单、Band 色轨或阵容文案。
- 页面布局和 Stage Ledger 视觉主题。
- 用通用 `Card`、`Badge` 或 `Stack` 抹平业务差异。

## 14. 动效与反馈

允许的动效：

- 收藏成功或失败反馈。
- 歌曲检查器展开和内容切换。
- 页内跳转后的焦点提示。
- 主题切换的颜色过渡。

禁止的动效：

- 自动滚动、横向滚动劫持和视差。
- 歌单逐行自动入场。
- 无限循环的光带、脉冲、闪烁或文字跑马灯。
- 通过 React state 监听连续滚动位置。

`prefers-reduced-motion: reduce` 下所有非必要动效必须变为即时切换。

## 16. 永久 URL、语义和 SEO

### 16.1 永久 URL

当前详情视图只在相同地址上切换 History state。新设计要求每场 Live 拥有可刷新、可复制、可恢复的地址：

```text
/lives/{live_id}
```

要求：

- 直接打开地址可读取详情。
- 浏览器前进、后退保持来源列表的筛选、页码和滚动位置。
- 分享操作复制永久 URL，而不是当前内部状态地址。
- 旧的 History state 入口迁移期仍能打开同一详情。

### 16.2 语义 HTML

- 页面主体使用 `main` 和 `article`。
- Live 标题是唯一 `h1`。
- 演出流程使用 `section`、`h2/h3`、`ol/li`。
- 页内导航使用真实锚点。
- 状态变化使用适当的 `aria-live`，初始静态状态不重复播报。
- 可点击歌名使用 `button`，不可点击歌名不伪装成交互元素。

### 16.3 结构化数据

在现有数据范围内生成 `MusicEvent` 或 `Event` JSON-LD：

- `name`
- `startDate`
- `eventStatus`
- `location.name`
- `performer`
- `url`

地址、城市和国家缺失时不填假值。补充场馆地理数据后再扩展 `PostalAddress`。

## 17. 加载、空数据和错误

### 17.1 加载

- 骨架必须匹配 Masthead、摘要标尺和正文入口的最终形状。
- 不使用全页居中旋转图标。
- 骨架预留稳定高度，避免数据返回后产生明显 CLS。

### 17.2 404

- 明确显示“未找到这场 Live”。
- 提供返回演出资料和搜索入口。
- 不保留失效标题 fallback 作为成功内容。

### 17.3 500 或网络错误

- 保留已经可确认的 fallback 标题和日期。
- 明确说明详情读取失败。
- 提供重试和返回操作。
- 不显示空歌单来伪装成功。

### 17.4 收藏失败

- 恢复操作前状态。
- 在收藏按钮附近给出可读错误。
- 不用仅颜色表达失败。
