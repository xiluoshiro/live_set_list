# 演出活动组聚合实现设计

## 文档定位

本文定义 LiveSetList 在“演出资料”中聚合关联 Live 的实现方案，覆盖多日 Live、单日午场 / 晚场以及多日且每天多场的混合日程。

- 本文是实现设计，不承载产品需求和阶段需求讨论。
- 巡演仍是独立资料实体；演出活动组与巡演关系正交。
- 单场 Live、Setlist 和收藏关系继续使用现有 `live_id`，聚合不复制或替代单场数据。
- 活动组结构由 V14 新增且不修改任何已执行 migration；仓库当前最新版本以 [Flyway 落地说明](flyway.md) 为准。

## 目标与边界

### 目标

1. “演出资料”同时展示未聚合的单场 Live 和已聚合的活动组。
2. 一个活动组至少包含两场 Live，可以覆盖一个或多个日期。
3. 单日午场 / 晚场、多日 DAY 1 / DAY 2 以及混合日程使用同一数据结构。
4. 场次始终按 Live 日期、开演时间自动排序，不维护人工顺序。
5. 不维护场次标签；页面展示名统一由“Live 名称减去聚合名称”计算。
6. 无筛选、全部场次命中或关键词直接命中组名时聚合完整活动组；部分命中按场次展示，“仅收藏”还要求组内所有 Live 均已收藏。
7. 控制台交互复用“巡演管理”的创建、编辑、候选搜索、批量添加、确认和审计流程。

### 非目标

第一版不做：

- 根据标题、日期、场地或乐队自动创建活动组。
- 人工维护 DAY 1、午场、晚场等标签。
- 人工上移、下移或拖拽场次顺序。
- 独立的活动组收藏关系。
- 活动组内跨场 Setlist 变化统计。
- 活动组删除、合并、拆分和复杂审核流。
- 用活动组替代巡演、音乐节届次或未来可能出现的通用系列实体。

## 核心概念

### 单场 Live

现有 `live_attrs` 中的一条记录，表示某个日期、开演时间和场地的一场演出。每场继续独立维护：

- Live 标题、日期、开场和开演时间。
- 场地和 Live 类型。
- 参与乐队与 Setlist。
- 来源链接。
- 用户收藏。

### 演出活动组

演出活动组表示具有同一官方活动身份的两场或更多 Live。它只提供公共列表聚合和逐场导航，不改变子 Live 的业务语义。

示例：

```text
BanG Dream! 12th☆LIVE
├─ 2026-08-08 13:00 午场
└─ 2026-08-08 18:00 晚场
```

```text
BanG Dream! Summer Festival
├─ 2026-08-08 16:00 DAY 1
├─ 2026-08-09 16:00 DAY 2
└─ 2026-08-10 15:00 DAY 3
```

```text
BanG Dream! Special 2DAYS
├─ 2026-08-08 13:00 DAY 1 午场
├─ 2026-08-08 18:00 DAY 1 晚场
└─ 2026-08-09 17:00 DAY 2
```

### 与巡演的关系

一场 Live 第一版最多属于一个活动组，同时仍可以属于一个巡演：

```text
Live
├─ 0..1 Tour
└─ 0..1 Performance Group
```

例如巡演东京站的午场和晚场可以同时关联：

- 同一个 Tour，用于巡演资料和按指定乐队统计。
- 同一个 Performance Group，用于演出资料列表折叠和午场 / 晚场切换。

## 聚合与展示分类

活动组类型不落库，由关联 Live 动态计算：

| `day_count` | `live_count` | 公共展示 | 数量文案 |
|---:|---:|---|---|
| 1 | 1 | 数据异常时退化为普通 Live | 不展示聚合数量 |
| 1 | 2+ | `单日多场` | `N 场` |
| 2+ | 等于 `day_count` | `多日活动` | `N 日 · N 场` |
| 2+ | 大于 `day_count` | `多日活动` | `N 日 · M 场` |

计算字段：

```sql
COUNT(DISTINCT l.live_date) AS day_count,
COUNT(DISTINCT l.id) AS live_count,
MIN(l.live_date) AS start_date,
MAX(l.live_date) AS end_date
```

不保存 `single_day_multi_show` 或 `multi_day` 类型，避免编辑 Live 日期后产生派生字段漂移。

## 场次顺序与展示名

### 自动排序

活动组关系不保存 `display_order`。控制台编辑数据、确认弹窗和前端本地状态按以下规范顺序排列：

```sql
ORDER BY l.live_date ASC, l.start_time ASC, l.id ASC
```

- `live_date` 是第一排序键。
- `start_time` 是同一天内午场 / 晚场的排序键。
- `live_id` 只用于日期和开演时间完全相同时提供稳定顺序。
- 不使用 `opening_time` 排序。
- 前端排序函数必须使用与后端一致的日期、开演时间和 ID 规则。

公共详情仍以 `live_date` 为第一排序键，但同一天内先显示 `event_status = 'cancelled'` 的场次，再按 `start_time` 和 `live_id` 排列；这样取消场次不会被埋在同日正常场次之后。控制台关系顺序不因状态切换而改写。

`live_attrs.start_time` 当前为非空 `time with time zone`，因此第一版不设计缺失开演时间的人工兜底字段。

### 自动展示名

不新增场次标签字段。页面和控制台确认区复用巡演短标题规则，将其抽取为通用 helper：

```ts
export function getGroupedLiveShortTitle(liveTitle: string, groupTitle: string): string {
  if (!liveTitle.startsWith(groupTitle)) return liveTitle;
  return liveTitle.slice(groupTitle.length).trim() || liveTitle;
}
```

示例：

| 聚合名称 | Live 名称 | 展示名 |
|---|---|---|
| `BanG Dream! 12th☆LIVE` | `BanG Dream! 12th☆LIVE 午场` | `午场` |
| `BanG Dream! 12th☆LIVE` | `BanG Dream! 12th☆LIVE 晚场` | `晚场` |
| `Special 2DAYS` | `Special 2DAYS DAY 1` | `DAY 1` |
| `Special 2DAYS` | `2026 Special 2DAYS DAY 1` | 保留完整原标题 |
| `Special 2DAYS` | `Special 2DAYS` | 保留完整原标题 |

只从标题开头精确移除一次聚合名称并 trim：

- 不做大小写模糊匹配。
- 不做中间字符串替换。
- 不根据日期或时间生成 `DAY N`。
- 结果为空时保留 Live 原标题。

## Flyway V14 数据结构

新增：

```text
backend/db/flyway/sql/V14__add_performance_group_aggregation.sql
```

目标结构：

```sql
SET ROLE live_project_owner;

CREATE TABLE public.performance_group_attrs (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    group_title text NOT NULL,
    CONSTRAINT performance_group_attrs_title_not_blank
        CHECK (btrim(group_title) <> '')
);

CREATE TABLE public.performance_group_lives (
    group_id integer NOT NULL
        REFERENCES public.performance_group_attrs(id) ON DELETE CASCADE,
    live_id integer NOT NULL
        REFERENCES public.live_attrs(id) ON DELETE CASCADE,
    PRIMARY KEY (group_id, live_id),
    UNIQUE (live_id)
);

RESET ROLE;
```

设计说明：

- `UNIQUE (live_id)` 保证一场 Live 最多属于一个活动组。
- 关系表没有顺序和标签字段，所有展示信息来自 Live 主数据和名称计算。
- 活动组至少两场的约束由写接口在事务中校验；普通 CHECK 无法跨行保证计数。
- `group_title` 不增加唯一约束，允许同名活动在不同年份或不同官方届次分别建组。
- 第一版不保存独立 URL；公共详情来源链接继续使用当前选中 Live 的来源，活动组头部可以取日期和开演时间最早 Live 的来源。

权限沿用巡演表模式：

- `live_project_ro`：两张表 `SELECT`，identity sequence `SELECT`。
- `live_project_super_ro`：两张表 `SELECT / INSERT / UPDATE`，关系表 `DELETE`，sequence `USAGE / SELECT / UPDATE`。
- 第一版不开放 `performance_group_attrs` 删除，因此不授予运行时角色主表 `DELETE`。

## 公共 API

### 保留原始 Live API

现有 `/api/lives`、单场详情、批量详情、控制台候选和 Setlist 写入继续使用纯 Live 响应，不改成联合类型，避免影响现有调用方。

所有公共 Live 读取路径增加可空反向引用：

```json
{
  "performance_group": {
    "group_id": 12,
    "group_title": "BanG Dream! 12th☆LIVE"
  }
}
```

没有归属时返回 `null`。与巡演反向引用相同，列表、收藏、乐队 Live、搜索、单详情和批量详情必须保持一致。

### 统一演出资料列表

新增：

```http
GET /api/catalog/performances
```

查询参数：

| 参数 | 类型 | 规则 |
|---|---|---|
| `scope` | `all / favorites` | 默认 `all`；`favorites` 要求登录 |
| `page` | int | `>= 1`，超过末页时钳制 |
| `page_size` | int | 复用现有演出资料允许值 |
| `q` | string | 匹配组名以及候选 Live 的现有关键词字段 |
| `year` | int | 任一子 Live 位于该年份即命中组 |
| `live_type` | enum | 任一子 Live 命中即命中组 |
| `band_id` | int | 任一子 Live 的有效表演乐队命中即命中组 |
| `sort` | enum | 复用现有日期升序 / 降序 |

响应项使用判别联合：

```json
{
  "kind": "live",
  "live": {}
}
```

或：

```json
{
  "kind": "performance_group",
  "performance_group": {
    "group_id": 12,
    "group_title": "BanG Dream! 12th☆LIVE",
    "start_date": "2026-08-08",
    "end_date": "2026-08-08",
    "day_count": 1,
    "live_count": 2,
    "display_type": "single_day_multi_show",
    "bands": [],
    "venues": []
  }
}
```

公共列表聚合必须在服务端完成后再分页。禁止前端取得某一页 Live 后临时合并，否则午场和晚场可能落在不同分页，`total` 和页码也会失真。

默认日期排序：

- 降序按组内最后一场的 `live_date DESC, start_time DESC`，再按 `group_id DESC` 保持稳定。
- 升序按组内第一场的 `live_date ASC, start_time ASC`，再按 `group_id ASC` 保持稳定。
- 普通 Live 使用自身日期、开演时间和 ID，与组摘要投影到统一排序列。

筛选命中活动组全部场次时继续展示完整活动组；只命中部分场次时，每个命中 Live 作为带活动组反向引用的普通项独立展示。关键词直接命中活动组名称时保留完整组。

### 活动组详情

新增：

```http
GET /api/catalog/performance-groups/{group_id}
```

返回：

- 活动组标题。
- 日期范围、`day_count` 和 `live_count`。
- 动态聚合的乐队、场地，以及每场 Live 自身的类型。
- 按 `live_date / start_time / live_id` 排序的完整 `lives`。
- 当前会话对每场 Live 的收藏状态。

组不存在返回 `404`。历史异常组只有一场 Live 时记录错误并在统一列表退化为普通 Live，不伪造多场聚合卡片。

## 收藏范围投影

收藏继续严格属于单场 Live，不新增 `user_favorite_performance_group`。

### `scope=all`

- 无筛选、全部场次命中或关键词直接命中组名时，合法活动组返回一个 `performance_group` 项。
- 部分命中时只返回命中的子 Live，不同时重复返回活动组项。
- 收藏 0 场、部分收藏或全部收藏不改变“全部”范围的聚合结构。

### `scope=favorites`

先在完整活动组上计算：

```sql
group_live_count
favorite_live_count
```

投影规则：

| 收藏状态 | “仅收藏”返回 |
|---|---|
| `0 / N` | 不返回 |
| `1..N-1 / N` | 每个已收藏子 Live 各返回一个 `live` 项 |
| `N / N` | 返回一个 `performance_group` 项 |

完整收藏判断必须基于活动组全部成员，而不是当前关键词、年份、类型或乐队筛选后的子集。

随后应用展示筛选：

- 全部收藏的组只有在全部场次命中或组名直接命中时返回完整组，其他部分命中仍按场次返回。
- 部分收藏时只返回同时已收藏且实际命中的单场 Live；组名命中时可以匹配已收藏子 Live，但不能带出未收藏场次。
- 部分收藏的单场 Live 响应保留 `performance_group` 反向引用，详情中可以返回完整活动组。

收藏变化后使查询缓存失效并重新执行服务端投影：

- `N / N` 取消一场后，聚合卡片拆为剩余已收藏的单场卡片。
- `N-1 / N` 收藏最后一场后，单场卡片合并为一个活动组卡片。
- 活动组后续新增一场未收藏 Live 时，不再满足完整收藏，收藏列表自动退化为已收藏单场。

活动组卡片第一版不提供整体收藏按钮；进入详情后继续使用现有每场 Live 收藏按钮。

## 公共前端

### 导航与列表

不新增“多日活动”主导航。“演出资料”改用 `GET /api/catalog/performances`，同一网格渲染两种项目：

- `kind=live`：复用现有 `live-card`。
- `kind=performance_group`：继续复用 `live-card` 外形；单日多场展示单个日期，多日活动展示日期范围，并展示动态类型、聚合名称、乐队图标和数量。

类型文案：

- `day_count = 1`：`单日多场`。
- `day_count > 1`：`多日活动`。

数量文案：

- 单日：`已收录 N 场`。
- 多日：`已收录 N 日 · M 场`。

### 活动组详情

详情复用 `TourDetailPage` 和 `LiveDetailContent` 的高相似结构：

1. 头部显示聚合名称、动态类型、日数 / 场数和动态参与乐队；不重复显示活动组日期范围。
2. 场次导航严格保留后端的日期、同日取消优先、开演时间和 Live ID 顺序，但视觉上复用巡演的单行短标题导航，不显示日期分组或开演时间。
3. 导航按钮文字调用 `getGroupedLiveShortTitle`；取消场次追加“（已取消）”，正常场次不拼接日期状态；相邻场次使用巡演同款竖向分隔条。
4. 已登录用户在每个短标题旁使用独立星标逐场收藏；活动组本身没有整体收藏按钮。
5. 点击短标题后在当前页面加载现有单场详情和 Setlist 表格；日期、开场和开演时间仍在选中 Live 自身详情中展示。
6. 选中 Live 若属于巡演，继续显示可操作的巡演反向入口；活动组与巡演关系互不覆盖。
7. 不显示“巡演统计”或跨场差异页签。
8. 从普通 Live 详情点击活动组名称时，打开组详情并默认选中当前 `live_id`。
9. 活动组详情始终归入“演出资料”导航域，桌面顶部导航与移动抽屉都保持“演出资料”选中；浏览器返回恢复进入活动组前的筛选、分页和滚动位置。

同一天两场示例：

```text
[午场] ★ | [晚场] ★
```

多日混合示例：

```text
[DAY 1 午场] ★ | [DAY 1 晚场] ★ | [DAY 2] ★
```

移动端允许短标题自然换行，不能依赖页面级横向滚动。Setlist 表格继续使用现有局部响应式容器。

## 控制台维护

### 入口与复用范围

控制台新增与“巡演管理”并列的“活动组管理”模式。整体结构直接复用 `TourAdminSection`、现有控制台样式和交互，不创建另一套管理页面约定。

复用：

- 已有实体下拉选择。
- “新建”按钮和表单重置。
- Live ID / 标题候选搜索。
- 分页和“一键添加筛选结果”，上限 500。
- 已选场次表格和移除操作。
- 创建 / 更新确认弹窗。
- 创建成功后的会话级新增记录表格。
- 完整目标集合替换、CSRF、`editor+` 权限和审计日志。

不包含：

- 参与乐队选择器。
- 场次标签输入框。
- 人工排序、拖拽或上下移动按钮。

### 表单字段

仅维护：

- 聚合名称 `group_title`。
- 至少两场已选 Live。

已选表格与候选表格展示：

| 日期 | 开演 | Live | 场地 | 操作 |
|---|---|---|---|---|

添加或移除后，前端立即按 `live_date / start_time / live_id` 重新排序。确认弹窗使用相同顺序，并展示由 Live 名称和聚合名称计算出的短标题，仅供确认，不提交短标题字段。

### 候选过滤

候选查询：

```http
GET /api/console/performance-groups/live-candidates
```

必须在 count 和 page 查询中同时加入：

```sql
NOT EXISTS (
    SELECT 1
    FROM performance_group_lives occupied
    WHERE occupied.live_id = l.id
)
```

因此已属于任何其他活动组的 Live：

- 不显示灰置状态。
- 不返回归属提示。
- 直接从候选总数和分页结果中排除。
- 不参与“一键添加筛选结果”。

编辑已有活动组时，其现有 Live 由编辑详情接口直接加载到“已选场次”，不依赖候选查询重新返回。

写接口仍保留并发兜底：若候选查询后某个 Live 被其他活动组占用，创建或更新返回 `409`，detail 包含冲突 `live_id / group_id / group_title`；整个事务回滚，不留下部分关系。

### 控制台 API

新增：

```text
GET  /api/console/performance-groups/live-candidates
GET  /api/console/performance-groups
GET  /api/console/performance-groups/{group_id}
POST /api/console/performance-groups
PUT  /api/console/performance-groups/{group_id}
```

写请求：

```json
{
  "group_title": "BanG Dream! 12th☆LIVE",
  "live_ids": [41, 42]
}
```

服务端不信任请求数组顺序。验证所有 Live 后，按数据库读取的 `live_date / start_time / live_id` 生成响应和审计字段；关系表只写 `group_id / live_id`。

校验：

- `group_title` trim 后非空，最长 255。
- `live_ids` 至少两个，最多 500 个。
- `live_ids` 不得重复。
- 所有 Live 必须存在。
- 所有 Live 必须未属于其他活动组；更新时允许仍属于当前组。
- 不要求所有 Live 日期不同、相同场地、相同类型或相同乐队。

更新采用完整目标集合替换：锁定主记录，验证目标集合，更新名称，删除旧关系，插入新关系，并在同一事务写审计日志。

## 查询与缓存

- 统一演出资料列表先生成普通 Live / 完整组 / 部分筛选或部分收藏单场的展示投影，再 count 和分页。
- 活动组摘要从关联 Live 动态聚合日期、乐队、场地、类型和收藏计数。
- 活动组详情在固定 `group_id` 下使用有界查询，不为每场 Live 单独查询收藏。
- Live 列表和详情反向引用使用对一或零关联，不产生 N+1。
- 创建或更新活动组后，后续统一演出资料、活动组详情和 Live 详情请求读取最新关系。
- 单场收藏同步成功后，`FavoriteProvider.projectionVersion` 递增；当前位于“仅收藏”范围时重新执行统一投影，因为返回项可能在组卡片与单场卡片之间转换。
- 空闲预读统一调用 `GET /api/catalog/performances`，只对判别联合中的 `kind=live` 批量预读详情，不能把 `group_id` 当作 `live_id`。

## 安全、权限与审计

- 公共列表和活动组详情匿名可读。
- 收藏范围使用当前 session，不接受任意 `user_id`。
- 控制台读取要求 `editor+`；写入同时要求 `editor+` 和有效 CSRF。
- SQL 值全部参数化；排序只从固定枚举映射。
- 创建和更新关系必须在单一事务完成。
- 审计 action 使用 `performance_group_create / performance_group_update`。
- 审计记录组 ID、名称、前后 Live 数和目标 Live ID；不记录 cookie、CSRF 或凭据。
