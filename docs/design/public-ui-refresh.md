# 公共端 UI 精修与易用性改造设计

## 1. 文档定位

本文描述 LiveSetList 公共端下一轮 UI 精修的设计方案，目标是在不改变“BanG Dream! Live 资料库”定位的前提下，提高页面的视觉完成度、移动端可用性、资料发现效率和无障碍体验。

本文是实现设计，不替代产品需求与阶段状态：

- 产品定位、用户视角和长期路线仍由 [社区 Live 数据库首页与个人工作台需求](../product/homepage-community-database.md) 维护。
- 阶段 1 的历史实现边界见已归档的 [社区 Live 数据库首页阶段 1 开发设计](../archive/completed-design/homepage-community-database-phase1.md)。
- 2026-07 第一轮视觉问题 F1–F20 已全部修正并完成浏览器复核，证据见已归档的 [公共端视觉走查报告](../archive/completed-design/public-ui-visual-audit-2026-07.md)。
- 本轮以 `http://localhost:5173/` 的本地页面为最新 UI 基线；线上版本仅用于部署回归。

当前状态：基础视觉、响应式、卡片键盘入口、加载/空/错状态和视觉层级收敛已完成；乐队名称搜索、可分享 URL、歌曲/场地后续路径、独立 Live 详情收藏和截图型视觉回归仍待后续阶段。

## 2. 当前结果

当前公共端已经不是单一后台表格，而是一套可使用的资料库界面：

- 首页展示搜索、Live、乐队、歌曲与场地四项统计、最新 Live 日期和最近收录。
- 支持按 Live、乐队、歌曲和场地进行聚合搜索；巡演实体分组尚未接入公共搜索。
- 支持公开乐队浏览、默认成员目录和乐队相关 Live 列表；收录场次使用与演出资料一致的有效 Band 回退规则。
- “演出资料”支持卡片、表格两种视图、全部 / 仅收藏范围切换和共享筛选器；统一投影会把有效的多日或单日多场活动组聚合为一张卡片。
- “巡演资料”已作为独立主导航，提供筛选、卡片列表、页内场次详情和巡演统计；单场 Live 可反向进入所属巡演。
- Live 详情已改为独立视图，展示基础信息、setlist、出演成员和来源链接。
- 支持浅色、深色和跟随系统主题。
- 登录用户可使用服务端收藏，`editor+` 用户可进入控制台录入资料。
- 首页、演出资料、巡演资料、数据统计、乐队浏览、联系我们和控制台已经统一使用 kicker、中文标题与描述组成的 `PageTitle` 结构。
- 乐队浏览为 Band 1~12 使用 SVG 主色的浅色按钮背景，并在右侧叠加透明度 `0.22` 的 SVG 图案；没有 SVG 的乐队保持普通按钮样式。
- 公共卡片的主详情入口已经改为真实按钮，来源和收藏保持独立操作；Live 类型统一使用克制色调的 `LiveTypeBadge`。
- 首页、列表、搜索、统计和详情已复用 `ContentState` 呈现加载、空数据和错误状态。
- 数据概览由 `GET /api/catalog/stats` 实时返回，本文不固化容易过期的本地数量。

现有颜色令牌、分文件 CSS、组件边界和公共 API 已能支撑下一轮优化，不需要重建前端技术栈。

## 3. 实施前问题与剩余项

本节保留本轮设计的原始问题背景。已经落地的项目以 `DONE` 标记；未标记项仍可作为后续精修候选。

### 3.1 响应式与移动端

- `DONE` 约 390px 宽度下隐藏横向主导航，统一从移动端抽屉访问全部入口。
- 首页“最近收录”的标题和两个操作在手机端会形成狭窄竖排文字，破坏阅读顺序。
- `DONE` 概览已拆为 Live、乐队、歌曲、场地四张卡，平板和手机使用两列布局。
- 详情页桌面表格约 920px 宽，手机内容区域约 317px，只能依赖不明显的横向滚动查看成员、其他成员和备注。
- `DONE` 详情标题允许合理换行，返回操作改为带明确可访问名的 `←`。

### 3.2 信息层级与视觉一致性

- `DONE` 首页首屏改为“查找 Live、曲目与出演记录”，完整站点名只保留在顶栏。
- `DONE` 歌曲和场地已拆为独立指标，并补充乐队指标。
- `DONE` `latest_live_date` 已改为“最新 Live 日期”，不再描述为资料更新时间。
- `DONE` 页面标题已经统一到 `PageTitle`；英文 kicker 作为辅助层级保留，中文标题承担主标题语义。个别 Emoji / 图标按钮仍可继续统一。
- `DONE` 页面底色已改为中性浅灰蓝 / 深海军蓝，品牌粉缩减为主操作、链接、选中态和低透明度光晕。
- 搜索页的“联系我们”按钮与搜索任务并列为高优先级操作，干扰当前页面目标。

### 3.3 浏览与发现效率

- `DONE` 演出资料已经具备关键词、年份、Live 类型、乐队、日期排序和全部 / 仅收藏范围筛选。
- 聚合搜索每组最多返回有限结果，但没有“查看全部相关 Live”的后续路径。
- 搜索结果固定使用四个分组区域；当歌曲或场地没有结果时，仍保留大面积空白卡片。
- 歌曲和场地搜索结果只有文字，不能继续进入相关 Live。
- `PARTIAL` 乐队浏览左栏已有 SVG 图案和代表色背景；名称搜索和移动端专用选择器仍未实现。
- 当前视图主要存放在 History state 中，刷新或分享 URL 后不能稳定恢复搜索、乐队、详情和筛选状态。

### 3.4 详情、收藏与可信度

- 独立详情页没有收藏操作，与列表收藏能力以及 README 对详情能力的描述不完全一致。
- `DONE` 标题来源与图标来源都已补充目标相关的可访问名称；图标仍保持紧凑展示。
- 元数据在桌面端被分散到左右两端，场地和类型距离日期、时间过远。
- 当前数据中可见少量疑似字符替换问题，例如曲名中的 `?`；这属于数据质量问题，视觉优化不能代替数据修复。

### 3.5 无障碍与测试边界

- `DONE` 卡片主详情入口已改为真实 `<button>`，并与来源、收藏分成独立键盘操作目标。
- `DONE` 卡片外链已使用包含目标标题的 `aria-label`。
- `DONE` 公共端已经接入统一 accent `:focus-visible` 焦点环。
- 现有 Vitest/jsdom 测试能看护行为，不能发现移动端排版、全局 CSS 和主题视觉回归。

## 4. 外部项目借鉴

本轮只借鉴成熟资料库的产品结构，不复制其视觉：

- [setlist.fm](https://www.setlist.fm/)：首页把全局搜索、Setlist/艺人/场地等实体导航、数据规模、热门内容、近期内容和最近编辑组织为连续的发现路径；高级搜索还提供艺人、歌曲、巡演、场地、城市、国家和日期范围。
- [Discogs](https://support.discogs.com/hc/en-us/articles/360003622014-How-To-Browse-Search-In-The-Database)：在结果页提供实体分类、过滤条件、排序和高级搜索，让用户能从模糊关键词逐步收敛到目标资料。
- [MusicBrainz](https://musicbrainz.org/)：在全站保持实体类型搜索，并明确展示数据许可、贡献指南、社区入口和最近新增内容，强化资料库的可信度与可维护性。

结合 LiveSetList 当前规模，优先借鉴以下能力：

1. 搜索后仍能继续筛选和浏览，而不是停在一次性结果页。
2. Live、乐队、歌曲、场地之间形成可点击的资料关系。
3. 清楚区分资料日期、来源、收录状态和真正的编辑更新时间。
4. 公共浏览优先，登录与贡献入口不阻塞匿名用户。

暂不引入热门排行、社区编辑流、评论、审核、复杂推荐和完整实体知识图谱。

## 5. 设计原则

### 5.1 保留当前品牌，减少装饰噪声

- 保留 `#f31864` 作为主要强调色，保留海军蓝标题和乐队图标。
- 页面基础背景改为中性浅灰蓝，粉色只作为顶部轻量渐变、主操作、链接和选中态。
- 深色主题继续使用当前深海军蓝体系，重新检查粉色链接、边框和次要文字的对比度。
- 不使用大幅 IP 图片或需要额外授权的素材。

### 5.2 数据库入口优先

- 首页首要任务是搜索和发现资料，不做营销式大 Hero。
- 列表优先保证可扫描、可筛选和信息密度，不把所有内容都装饰成大卡片。
- 详情优先表达可核对的数据、来源和曲目结构。

### 5.3 移动端不是桌面缩放版

- 顶部导航、筛选器和 setlist 针对窄屏采用独立交互。
- 手机端不强迫用户横向滚动宽表格来完成主要阅读任务。
- 触控目标最小高度或宽度为 44px，主要操作必须有文字或明确的 accessible name。

### 5.4 不引入新的全局样式风险

- 继续使用仓库内 CSS 和现有主题令牌。
- 图标使用本地 React SVG 组件，不引入第三方 UI 库或全局 reset。
- 公共端样式保持命名空间和组件边界，控制台只消费共享令牌，不参与结构重做。

## 6. 目标视觉系统

### 6.1 页面框架

- 顶部栏保持全宽、置顶和轻度透明；内容背景延伸到视口边缘。
- 内容区使用 `width: min(100%, 1440px)` 并居中，避免超宽屏卡片被无限拉长，但不恢复旧的外层居中大卡片。
- 页面水平间距：桌面 24px、平板 20px、手机 12px。
- 内容区主要断点：`900px` 调整多列布局，`720px` 切换移动端导航与详情，`620px` 收紧间距和操作布局。

### 6.2 令牌与组件

- 浅色基础背景建议为 `#f7f8fc`，顶部保留低透明度粉色渐变。
- 主卡片使用白色表面、12px 圆角、1px 浅边框和低强度阴影。
- 输入与小型按钮使用 8px 圆角；胶囊筛选标签使用完整圆角。
- 字体使用系统字体栈：`system-ui, "Segoe UI", "PingFang SC", "Hiragino Sans", "Yu Gothic UI", sans-serif`。
- 使用 8px 基础间距节奏，常用间距为 8/12/16/24/32px。
- SVG 图标统一为 18px 或 20px、相同描边粗细；不再依赖 Emoji 在不同系统上的外观。

### 6.3 交互状态

- 所有按钮、链接、输入、卡片主操作统一定义 hover、active、disabled 和 `:focus-visible`。
- 焦点环使用 2px 主色外框和至少 2px offset，不依赖颜色微调表达焦点。
- 遵守 `prefers-reduced-motion`，在用户要求减少动画时移除平移和弹出动画。
- 加载状态尽量保持区域尺寸稳定；失败状态提供重试或返回入口。

## 7. 页面设计

### 7.1 顶部导航

桌面端：

- 左侧保留可返回首页的 `BanG Dream! Live 资料库`。
- 中部保留“演出资料 / 巡演资料 / 数据统计 / 乐队浏览 / 联系我们”，`editor+` 增加“控制台”；收藏作为“演出资料”页内的“仅收藏”范围切换，不再占用独立导航项。
- 右侧保留用户、主题和菜单操作。

移动端：

- 顶部只显示可截断的站点名、登录或头像、主题和菜单。
- 隐藏横向主导航，完整入口统一放入侧边栏。
- 侧边栏显示当前页面选中态，并在选择后自动关闭。
- 顶部栏不得产生水平滚动或把导航压缩成不可点击区域。

### 7.2 首页

首页首屏改为查询任务导向：

- 顶部站点名继续承担品牌表达。
- 首屏标题改为“查找 Live、曲目与出演记录”。
- 副文案说明可搜索 Live、乐队、歌曲和场地。
- 搜索框作为首屏唯一主操作，桌面保持输入和按钮同行，手机上下排列。

数据概览拆为四张独立卡片：

- Live。
- 乐队。
- 歌曲。
- 场地。

`latest_live_date` 不再写成“最近更新”，改为概览区下方的“最新 Live 日期”。桌面四列，平板两列，手机固定两列，避免纵向占用过长。

最近收录区：

- 桌面使用日期、标题、乐队三列紧凑列表。
- 区域标题右侧保留“查看全部 Live”和“乐队”两个轻量入口，分别进入演出资料与乐队浏览。
- 手机每项按日期、标题、乐队图标顺序纵向排列，标题最多显示两行。

个人与贡献区：

- 匿名用户显示简短登录价值和一个登录按钮。
- 登录用户显示收藏数量与收藏入口。
- `editor+` 增加控制台入口，但不把控制台提升为公共首页主操作。
- “关于与反馈”收敛为页脚式支持区域，避免与主要发现内容竞争。

### 7.3 演出资料与收藏

演出资料使用统一工具栏：

- 列表数据来自 `GET /api/catalog/performances`，有效活动组显示为单个聚合项，普通 Live 继续独立显示。
- 全部和仅收藏共用同一接口族与筛选语义；仅收藏时，只有组内 Live 全部收藏才显示完整活动组，部分收藏则保留已收藏的单场 Live。
- 活动组详情使用短标题导航逐场切换，主导航持续高亮“演出资料”；选中 Live 的日期、时间、setlist 与巡演反向入口复用单场详情。

- 关键词 `q`。
- 年份 `year`。
- Live 类型 `live_type`。
- 乐队 `band_id`。
- 排序 `date_desc / date_asc`。
- 卡片/表格视图切换。

交互规则：

- 多个筛选条件使用 AND。
- 工具栏下方显示总结果数和当前筛选标签；标签可单独移除，并提供“清除全部”。
- 桌面使用横向工具栏，空间不足时自然换行。
- 手机显示关键词输入、“筛选”按钮和日期排序；年份、类型、乐队放入可展开筛选区。
- URL 保存筛选条件，刷新和分享后可恢复相同列表。
- 卡片模式继续连续加载，表格模式继续分页；更改筛选或排序后回到第一页并清空旧快照。

收藏页复用同一套视觉工具栏和服务端筛选参数，确保筛选后的总数、分页和卡片连续加载均准确。

卡片结构改为：

- 上部为真实 `<button>` 形式的详情主操作，覆盖日期和标题的大面积点击区域。
- 下部单独放置乐队图标、收藏按钮和来源链接。
- 不在包含链接、收藏按钮的 `<article>` 上绑定整体 click。
- 来源链接 accessible name 使用“打开《Live 标题》的资料来源”。

### 7.4 搜索结果

- 搜索页继续使用聚合搜索 API，顶部保留可修改的搜索框。
- 每个分组标题显示命中数量。
- 只渲染有结果的分组；所有分组为空时显示统一空结果和修改关键词提示。
- Live 结果是主区域，占据主要宽度。
- 乐队结果进入乐队浏览并选中对应乐队。
- 歌曲和场地结果后续可进入带 `song_id` 或 `venue_id` 的演出资料列表；当前仍停留在聚合结果。
- Live 分组达到聚合接口上限时显示“查看全部相关 Live”，进入带 `q` 的分页列表。
- 移除搜索页顶部“联系我们”按钮，联系入口保留在全局导航和页脚。

### 7.5 乐队浏览

桌面端：

- 左侧栏顶部增加乐队名称搜索。
- 乐队项展示名称和 Live 数量；有 SVG 时使用 SVG 主色的半透明背景和右侧图案，选中态提高队色混合比例并保留边框强调，无 SVG 时保持普通样式。
- 右侧标题显示乐队名称与收录数量，下面展示相关 Live。

移动端：

- 不展示长左栏，改为可搜索的乐队选择器。
- 选择后在同一列展示乐队摘要和 Live 列表。
- 选择状态写入 `band_id` URL 参数。

### 7.6 Live 详情

详情头部：

- 返回操作使用左箭头和“返回”语义，不再使用危险色关闭式 `✕`。
- 标题桌面可自然换行，手机最多两行。
- 标题旁或元数据下方提供明确的“官方来源”外链。
- 登录用户显示收藏按钮；匿名用户点击收藏时打开现有登录框。

元数据使用响应式网格：

- 日期。
- 开场。
- 开演。
- 场地。
- 类型。
- 乐队。

桌面至少三列，手机两列；缺失值统一显示 `—`，不使用含义不明的空白。

setlist：

- `> 720px` 保留现有表格，增加粘性表头并保持成员详情交互。
- `<= 720px` 使用 `matchMedia` 只渲染移动端列表，不同时输出隐藏表格，避免重复读屏内容。
- 移动端每项展示编号、歌曲名、乐队图标/成员入口、其他成员和“短版/翻唱”标签。
- 成员详情仍复用现有弹层或详情组件。

## 8. URL 与状态设计

继续使用原生 History API，不在本轮引入 React Router。URL 采用查询参数：

```text
/?view=all&q=Roselia&year=2026&live_type=oneman&band_id=4&sort=date_desc
/?view=search&q=Roselia
/?view=browse&band_id=4
/?view=detail&live_id=123
/?view=favorites
```

规则：

- 首页使用无参数根路径。
- 初始化时先解析 URL，再应用权限兜底；匿名用户打开收藏或控制台 URL 时回首页并按现有规则提示登录。
- `popstate` 从 URL 恢复视图、查询和筛选。
- 详情刷新后直接通过 `live_id` 请求详情，不依赖上一页传入的标题和日期 fallback。
- 从详情返回时优先使用浏览器历史；没有站内历史时返回演出资料。
- 视图模式继续存放在 localStorage，不写入分享 URL。

## 9. API 与前端类型

### 9.1 扩展 `GET /api/lives`

保留现有 `page`、`page_size` 和响应结构，新增可选参数：

| 参数 | 类型 | 规则 |
|------|------|------|
| `q` | string | trim 后为空等同未传；最长 255；匹配 Live 标题、乐队、歌曲和场地 |
| `year` | int | `1900..2100` |
| `live_type` | string | `oneman / taiban / multi_act / festival / event / other` |
| `band_id` | int | `>= 1` |
| `song_id` | int | `>= 1` |
| `venue_id` | int | `>= 1` |
| `sort` | string | `date_desc / date_asc`，默认 `date_desc` |

所有已传条件使用 AND。合法但不存在的 ID 返回空分页结果；非法范围或枚举交给 FastAPI 参数校验。文本匹配沿用 catalog 搜索的 `ILIKE` 和 `%`、`_`、`\` 转义规则。

SQL 实现应复用同一组过滤条件生成 count 和 page 查询，所有值通过 psycopg2 参数传递，不拼接用户输入。排序只从固定枚举映射为预定义 SQL 片段。

### 9.2 扩展 `GET /api/catalog/stats`

在现有统计上增加：

```json
{
  "years": [2026, 2025]
}
```

- `years` 只返回实际存在的年份并按降序排列；界面不展示每年命中数量。
- Live 类型继续使用前端现有 `LIVE_TYPE_OPTIONS` 提供稳定 code 与中文标签。
- 乐队筛选项继续复用 `GET /api/catalog/bands?limit=100`，不在 stats 中重复返回。

### 9.3 前端状态与缓存

新增统一类型：

```ts
type LiveListSort = "date_desc" | "date_asc";

type LiveListFilters = {
  q: string;
  year: number | null;
  liveType: string | null;
  bandId: number | null;
  songId: number | null;
  venueId: number | null;
  sort: LiveListSort;
};
```

- `getLives` 接受页码、页大小和规范化后的 filters。
- Live 列表缓存键包含所有筛选字段和排序字段。
- 筛选改变时清空当前列表快照和卡片连续加载状态。
- 详情缓存、收藏缓存和乐观同步协议保持不变。

## 10. 无障碍要求

- 每个视图只有一个主 `h1`，区域标题按层级使用 `h2/h3`。
- 顶部使用 `header/nav`，页面内容使用 `main`，筛选抽屉和菜单提供明确名称与展开状态。
- 所有纯图标按钮必须有与动作和目标对应的 `aria-label`。
- 卡片详情入口、来源链接和收藏按钮必须能分别通过 Tab 到达。
- 筛选抽屉打开后管理焦点，关闭后将焦点返回触发按钮；Escape 可关闭。
- 错误和收藏同步状态使用现有 `aria-live` 思路，不反复播报普通加载变化。
- 文字、图标和交互状态达到 WCAG AA 对比度；选中态不能只依赖颜色。
