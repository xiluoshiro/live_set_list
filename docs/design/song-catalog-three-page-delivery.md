# 歌曲概览、歌曲详情与唱片详情：适配清单及交付标准

状态：交付基线，尚未验收。基于 2026-09-27 的仓库代码审查与现有 HTML 样例整理；下文“当前代码事实”指该次审查基线，不代表后续工作区的实时实现状态。本文不表示三页改版已经完成，也不证明当前数据库的资料完整度。

## 1. 范围与设计基线

目标浏览链路为“歌曲资料概览 → 歌曲详情 → 唱片详情”，同时允许从唱片曲目进入具体歌曲版本，再返回原浏览位置。

| 页面 | 设计基线 | 本次交付目标 |
| --- | --- | --- |
| 歌曲概览 | A 乐队目录 | 搜索、乐队筛选、歌曲组列表、首次发行及对应唱片、演奏次数、最近演出、排序与分页 |
| 歌曲详情 | D 首页延续风格 | 歌曲展示封面、完整标题、版本与归属、所选版本的收录唱片、歌曲组演奏次数及按年份分页的演出记录 |
| 唱片详情 | A/B/C 的共同数据需求 | 独立 URL、发行资料、多封面、按原分区与曲序展示完整曲目、正确进入歌曲版本 |

唱片 A 为推荐落地基线：左侧封面与发行资料，右侧完整曲目，多个分区依次展开。唱片最终外观选择不阻止公共数据适配；B 的“相关唱片”是条件项，C 的曲目折列是排版项。本期不要求同时上线三套唱片主题。

本地样例位于 `outputs/song-layout-concepts-2026-09-26/v2/`：`song-select-a.html`、`d-home-continuity.html`、`album-concepts.html`。这些文件和 JSON 快照仅用于视觉参考，正式页面从公共 API 读取数据，不依赖其中的固定 ID、封面映射或已知歌曲白名单。该输出目录未作为正式应用依赖交付，本文保留了不依赖样例文件的行为标准。

本文覆盖三页改版的增量目标。旧文档中的“左列表、右详情”“目录不显示次数”“唱片在歌曲页内展开”描述既有实现，不再作为本轮页面结构的验收条件。歌曲身份、归属、逐条演奏计数、专辑维护权限仍沿用[产品需求](../product/song-details-and-albums.md)、[现有实现设计](song-catalog-and-albums.md)与[封面规则](album-links-and-covers.md)。

## 3. 必须统一的数据口径

### 3.1 歌曲身份与版本

- 概览一行代表一个 `group_id`，多个版本不能重复占据列表行。
- `song_id` 表示具体版本，`album_track_id` 表示具体收录行，三种 ID 不混用。
- 概览选组后优先恢复仍有效的版本；有过滤条件时从 `matched_song_ids` 中选择，无有效历史选择时按 `version_order` 回退。唱片曲目和旧链接指定的 `song_id` 必须直接定位到该版本。
- 版本切换改变固定归属和所选版本的收录唱片，歌曲组的演奏次数及演出历史保持一致。
- 保留 `bands`、`members`、`mixed`、`pending` 四种归属。成员模式使用歌曲版本的固定成员资料，不从现场出演记录反推。
- Instrumental 是收录说明，复用关联歌曲版本；同一歌曲在唱片中的多次收录保留各自的曲序、分区和收录行 ID。

### 3.2 首次发行

首次发行日期定义为：**歌曲组内全部版本关联唱片中，最早的非空 `release_date`**。

1. 跨版本、跨乐队、跨 Disc 汇总，同一唱片按 `album_id` 去重。
2. 多张唱片在最早日期发行时全部返回，不随意取一张；按 `album_id` 稳定排列。
3. 没有任何已知日期时返回 `null` 和空唱片数组。它表示资料未知，不表示歌曲从未发行。
4. 乐队筛选只决定歌曲是否命中，不改变该歌曲组的首次发行日期和首发唱片集合。
5. 这是已有收录资料的计算结果，不给歌曲表新增发售日期，也不根据演出日期、发行标识文本或封面图片猜测日期。

### 3.3 演奏次数与最近演出

- 每条符合现有条件的 `live_setlist` 记录计一次；同场演出中两次演奏计两次，短版正常计入。
- 按 `song_group_id` 聚合，不累加各版本返回的 `performance_count`，不替换成 `COUNT(DISTINCT live_id)`。
- 概览次数、详情总次数、最近演出和年份选项共用 `VALID_PERFORMANCE_SQL` 的有效性口径：排除取消及按既有活动时钟尚未到达的日期；时钟未知时沿用现有排除行为。
- 最近演出日期取有效记录的最大 `live_date`。无有效记录时次数为 `0`，最近日期为 `null`。
- 切换访客时区不改变计数；本轮不改动有效演出的时间政策。
- 详情主统计为歌曲组全部年份次数；年份筛选后的记录数量由演出列表的 `pagination.total` 表达，二者不能互相覆盖。

### 3.4 乐队筛选与数量

- 同时覆盖 `song_bands` 和 `song_member_groups` 中的乐队关联，使用稳定 `band_id`，不比较拼接后的展示名称。
- 每支乐队内按歌曲组去重；同组属于多支乐队时可以分别计入，因此各乐队数量之和不要求等于全部歌曲数。
- “全部歌曲”保留 pending 及无乐队关联的歌曲，不伪造一个乐队来容纳它们。
- 目录数量随搜索及其他非乐队过滤变化，但不受当前页、页大小、排序和已选乐队影响。某乐队的数量必须等于相同条件下切换到该乐队时列表接口的总数。
- 歌曲归属乐队与现场实际演唱乐队是不同概念；目录计数使用前者。

### 3.5 歌曲展示封面

V42 已按歌曲版本独立维护封面，以下规则替代三页改版初期的组级选图方案。

1. 每个版本保存有序 `cover_urls`，第一张为默认图；Console 复用专辑的添加、预览、排序、设为默认和移除操作。
2. 版本优先自身默认图；未配置时，仅从该版本关联的唱片中按 `release_date ASC NULLS LAST, album_id ASC` 选第一张有封面的唱片默认图，再无图则返回 `null`。
3. 歌曲组概览使用 `version_label = ''` 的默认版本的最终封面，不受版本排序和乐队筛选影响。歌曲详情使用当前版本结果，切换版本时重置封面浏览位置。
4. 首发唱片没有封面时允许选用后续有图唱片；只有专辑回退图链接到实际来源唱片。自有封面不伪造专辑来源。
5. 自有多封面支持本地切换，单张省略切图控件。远端图片失败显示“封面无法显示”，允许切换其他图，后端不探测图片网站，不自动跨来源回退。
6. `album_url` 是来源页面，`cover_urls` 是图片地址，不能互换。专辑与歌曲分别维护，派生回退图不复制到歌曲数组。
7. 不增加图片尺寸字段、上传或代理服务。方形、竖版封面均保持原比例，不裁切。

### 3.6 唱片分区与归属

- `album_sections` 是通用收录分区，可能名为 `Disc 1`、`Disc 2`、`限定版`，也可能为空名称；不是物理介质类型表。
- 保留后端给出的分区顺序和分区内曲序，不能按分区名称的字典序重新排序。
- 单分区不强造第二个 Disc；多分区同时展开。曲目列表不再同时要求“切 Disc”和“翻曲目页”。
- 不用分区数量生成“2 Disc”之类物理盘数。总收录数量按收录行计数，不按不同歌曲组计数。
- 如标题区展示乐队链接，可汇总收录版本归属的稳定 ID；这种汇总不等于已维护的正式唱片发行艺人。当前模型没有独立的唱片发行艺人字段，不从曲目字符串制造该事实。

## 4. 目标 API 契约

本节是待实现目标。最终字段应同步到 Pydantic、前端类型、OpenAPI 和 [API 补充规则](../api.md)，不能仅在页面中临时拼接。现有公共响应字段保持兼容。

### 4.1 歌曲组目录

沿用 `GET /api/song-groups`。保留现有 `q / band_id / album_id / owner_mode / member_id / page / page_size`，新增 `sort`。

| `sort` 值 | 顺序 |
| --- | --- |
| `name` | 现有规范化名称升序、`group_id` 升序 |
| `plays` | 演奏次数降序、规范化名称升序、`group_id` 升序 |
| `recent` | 最近演出日期降序、空值最后，再按规范化名称及 `group_id` 升序 |
| `release` | 首次发行日期升序、空值最后，再按规范化名称及 `group_id` 升序 |

接口省略 `sort` 时保留现有名称排序，概览 A 显式请求 `plays` 作为页面默认值。未知排序值返回参数校验错误。`page_size` 沿用 `1..100`，前端按可用空间选择大小并完整传递给服务端。

搜索增加版本归属乐队名称匹配；歌名及版本名继续使用[既有规范化规则](../../backend/app/song_lookup.py)，不照搬样例的临时字符删除规则。名称、归属、专辑等过滤仍需共同命中同一个版本后再对歌曲组去重，不能分别从不同版本凑出一次命中。

每个 `GroupSummary` 在既有字段之外新增：

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `first_release_date` | `date \| null` | 第 3.2 节的日期 |
| `first_release_albums` | `AlbumSummary[]` | 最早同日唱片的去重集合；未知时 `[]` |
| `performance_count` | 非负整数 | 第 3.3 节的歌曲组次数 |
| `latest_performance_date` | `date \| null` | 无有效演出时为 `null` |
| `display_cover` | `{ source: "song", url, name } \| { source: "album", url, name, album_id, album_name } \| null` | 第 3.5 节的图片、名称及真实来源 |

目录响应增加 `facets: { total, bands: [{ band_id, band_name, song_count }] }`。`facets.total` 表示去掉当前乐队过滤后的全部歌曲组数；`pagination.total` 仍表示当前所有过滤条件下的列表总数。每个乐队计数遵守第 3.4 节，不能取乐队接口的 `live_count`。

先确定过滤命中的歌曲组，再按这些组的全部关联资料计算摘要，完成排序后分页。翻页时不能只对当前页计算首发、统计或重排。

### 4.2 歌曲组与版本详情

- 保留 `GET /api/song-groups/{group_id}` 和 `GET /api/songs/{song_id}`。
- 组详情增加与概览同一规则的 `display_cover`；版本详情增加 `cover_urls` 和自身 `display_cover`，`ownership`、`albums` 和组级 `performance_count` 继续沿用。
- 直接访问版本链接时先解析所属组，再显示完整组名和对应版本；不能用“先当组 ID 找，找不到再当版本 ID 找”的模糊回退。
- 不要求把目录中的所有版本详情嵌入每一行；页面首屏不逐行请求详情接口。

### 4.3 演出记录

扩展 `GET /api/songs/{song_id}/performances`：

- 新增可选整数 `year`；未传表示全部年份。无记录的有效年份返回空列表及总数 `0`。
- 响应增加降序、去重的 `available_years: int[]`，取该歌曲组全部有效记录的年份，不受已选年份或当前页限制。
- `pagination.total / total_pages` 按年份过滤后的记录计算；`page / page_size` 沿用现有契约。
- 保留每条记录的 `setlist_id`、Live 链接资料、日期、位置、短版和现场翻唱判定。
- 稳定顺序沿用 `live_date DESC, live_id DESC, absolute_order, setlist_id` 对应的数据库原始 ID 顺序；同场多次演奏仍是多行。

### 4.4 唱片详情与条件项

`GET /api/albums/{album_id}` 继续返回完整 `tracks`，不为排版增加分页或 Disc 切换端点。收录行保留 `album_track_id / song_id / group_id / section_name / track_order / edition_label / version_label`。

若采用乐队跳转，响应补充稳定 ID 与名称集合，沿用现有乐队详情入口，不解析 `band_name` 中的斜杠。若采用唱片 B，可新增 `GET /api/albums/{album_id}/related`，具体要求为：

- 匿名可读，不能调用或放开控制台唱片列表权限。
- 按收录版本归属乐队 ID 的交集寻找其他唱片，排除当前唱片并按 `album_id` 去重；没有有效归属则返回空集合。
- 默认最多返回 6 张，按发行日期降序、空日期最后、ID 稳定排序；无封面时仍允许返回并使用占位。
- 返回 `AlbumSummary` 所需数据；没有结果时页面收起推荐区域，不保留空栏。
- 仅选 A/C 时此项记为不适用，不阻止基础三页验收。

## 5. 数据、查询与现有基础设施

### 5.1 数据准备交付件

独立输出一次只读数据检查报告，注明数据来源、检查时间和范围；使用测试库或获准读取的本地库，不把远程环境作为前置条件。报告至少列出：

- 唱片总量、缺发行日期、缺来源页面、无封面 URL 的数量及对应 ID。
- 无关联唱片、全部关联唱片日期未知、没有可选展示封面的歌曲组数量及 ID。
- 多版本、多归属、同日首发、重复收录、空分区名称等用于验证边界的实际样例 ID；没有实际样例时在隔离测试库构造。
- 数据库 URL 非空与图片实际加载成功分别记录，不能用前者证明后者。

交付要求是缺失可见、页面能处理未知值，不要求把历史资料补到 100%。发现需要补录的数据时另列清单；若交付回填 SQL，应独立、可审查、可重复执行，不随页面初始化或数据库迁移自动抓取和填充。

### 5.2 模型与性能

- 当前范围没有必须新增的业务表；V42 增加 `song_list.cover_urls`，首次发行、最近演出、目录计数及最终展示封面仍由读取时派生。
- 不新增歌曲发布日期、物理盘类型、统计持久化表或新的运行时角色。
- 目录采用批量查询或聚合，SQL 往返次数不随本页歌曲行数线性增长；避免逐行调用 `read_song`、唱片详情或演出列表。
- 使用 `EXPLAIN (ANALYZE, BUFFERS)` 检查无过滤、乐队过滤、搜索及四种排序的代表性查询；记录数据规模、计划和实际耗时，不在缺少基准时承诺固定毫秒值。
- 仅在计划证实需要时新增索引；需要迁移时另加 Flyway 文件，不修改已执行的 V37/V40/V41。
- 唱片默认图调整、发行日期修改、收录关系调整、归属修改和有效演出变化均应使对应目录摘要失效。复用已有 `invalidateSongCatalog`、资料保存事件及 Live 缓存清理路径；新参数全部进入缓存键，旧请求不能覆盖新筛选结果。
- 现有 Nginx 配置已有 SPA 回退。新增独立唱片页主要需要应用路由适配，不以远程部署或生产验收作为本地交付前提。

## 6. 页面接入与本地视觉标准

本节定义数据适配最终需要支撑的可见结果，不要求把样例中的方案选择器或调试控件移入产品。

- 保留 `/songs` 概览和 `/songs/{song_id}` 版本直达语义；增加 `/albums/{album_id}` 独立页。页面刷新、复制链接和浏览器前进后退均有效。
