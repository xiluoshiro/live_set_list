# 巡演聚合实现设计

## 文档定位

本设计落实 [巡演聚合产品需求](../product/tour-aggregation.md)。产品目标、用户范围、文案口径和验收标准以需求文档为准；本文只定义技术实现。

当前状态：`T1 已实施；控制台、公共页面与巡演搜索分组仍待后续阶段实施`。

## 现有实现边界

当前系统的核心关系是：

```text
live_attrs 1 ── N live_setlist N ── 1 song_list
     │
     └── venue_list
```

- `live_attrs` 表示单场 Live，包含日期、标题、来源、时间、场地、类型和无 setlist 时的默认乐队。
- Live 列表、收藏、详情、批量详情预读和 setlist 都以 `live_id` 为主键。
- `live_type` 是单场 Live 分类，当前稳定枚举不能承担巡演聚合关系。
- 公共读取使用 `get_db_connection()`；控制台写入使用 `get_write_db_connection()`。
- 公共搜索由 `/api/catalog/search` 聚合 Live、乐队、歌曲和场地结果。
- 前端“演出资料”当前以 `all / favorites` 两种内部 tab 表达“全部 / 仅收藏”。

巡演实现必须增量扩展这些路径，不重写现有 Live/setlist 主模型。

## 核心技术决策

### 独立 Tour 实体

新增 `tour_attrs`，不向 `live_type` 增加 `tour`，也不把巡演仅作为 `live_attrs` 上的文本字段。

### 使用关联表

新增 `tour_lives` 保存 Tour 与 Live 的关系、场次顺序和场次标签。第一版对 `live_id` 增加唯一约束，保证一场 Live 最多属于一个巡演。

使用关联表而不是直接在 `live_attrs` 增加 `tour_id`，原因是：

- 场次顺序属于关系本身。
- 场次标签属于关系本身。
- 删除巡演时只需删除关系，不改变 Live 主数据。
- 将来若确认存在多归属需求，可以移除 `live_id` 唯一约束而不重构 Live 表。

### 巡演乐队显式维护

新增 `tour_bands`，不从 setlist 自动持久化巡演参与乐队。setlist 可能未录入，也可能包含嘉宾或联合出演，不能替代巡演级资料。

### 聚合字段查询时计算

不在 `tour_attrs` 重复保存 `start_date`、`end_date` 和 `live_count`。这些字段从关联 Live 聚合，避免编辑场次后产生漂移。

## Flyway V13 数据结构

新增 `backend/db/flyway/sql/V13__add_tour_aggregation.sql`。结构目标如下，最终 SQL 需按仓库 Flyway/owner 约定落地：

```sql
CREATE TABLE public.tour_attrs (
    id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tour_title text NOT NULL,
    url text,
    description text,
    CONSTRAINT tour_attrs_title_not_blank CHECK (btrim(tour_title) <> ''),
    CONSTRAINT tour_attrs_url_not_blank CHECK (url IS NULL OR btrim(url) <> '')
);

CREATE TABLE public.tour_bands (
    tour_id integer NOT NULL
        REFERENCES public.tour_attrs(id) ON DELETE CASCADE,
    band_id integer NOT NULL
        REFERENCES public.band_attrs(id) ON DELETE RESTRICT,
    display_order integer NOT NULL CHECK (display_order > 0),
    PRIMARY KEY (tour_id, band_id),
    UNIQUE (tour_id, display_order)
);

CREATE TABLE public.tour_lives (
    tour_id integer NOT NULL
        REFERENCES public.tour_attrs(id) ON DELETE CASCADE,
    live_id integer NOT NULL
        REFERENCES public.live_attrs(id) ON DELETE CASCADE,
    stop_order integer NOT NULL CHECK (stop_order > 0),
    stop_label text,
    PRIMARY KEY (tour_id, live_id),
    UNIQUE (live_id),
    UNIQUE (tour_id, stop_order),
    CONSTRAINT tour_lives_label_not_blank
        CHECK (stop_label IS NULL OR btrim(stop_label) <> '')
);
```

索引：

- 主键和唯一约束已覆盖 `tour_id`、`live_id` 和顺序查找。
- 当前数据规模不为 `ILIKE` 额外启用 `pg_trgm`；出现真实慢查询后再添加扩展和 GIN 索引。

### Owner 与权限

V13 必须显式处理对象 owner 和运行时权限：

- 新表和 identity sequence 的 owner 统一为 `live_project_owner`。
- `live_project_ro` 获得三张表的 `SELECT`，用于公共列表、详情和搜索。
- `live_project_super_ro` 获得三张表的 `SELECT / INSERT / UPDATE`；`tour_bands` 和 `tour_lives` 需要 `DELETE`，用于以完整集合替换关联关系。
- `live_project_super_ro` 获得 `tour_attrs` identity sequence 的必要权限。
- `live_project_user_rw` 不获得巡演业务表写权限；普通用户收藏路径不写巡演表。
- Flyway history 的 owner 不得修改。

如果不希望给 `live_project_super_ro` 广泛的业务表 `DELETE`，权限只授予 `tour_bands` 和 `tour_lives`，不授予 `tour_attrs` 删除权限。第一版不提供删除巡演接口。

### Schema migration 与业务数据分离

V13 只创建结构、约束、owner 和 grant，不硬编码当前运行库中的 Live ID 或巡演关系。

- 测试数据在 `backend/db/postgres/seed/base_seed.sql` 中加入独立、稳定的 Tour fixture。
- 当前运行库的巡演关系在 V13 上线后通过控制台或一次性受审计脚本录入。
- 不因标题包含 `TOUR` 在 migration 中自动匹配。
- 生产迁移继续遵守 migration release 与 app-only release 的既有分离流程。

## 后端 Schema

在 `backend/app/schemas/` 增加 Tour schema，公共引用结构保持轻量：

```python
class TourRef(BaseModel):
    tour_id: int
    tour_title: str

class TourBandItem(BaseModel):
    band_id: int
    band_name: str
    band_abbr: str

class TourSummary(BaseModel):
    tour_id: int
    tour_title: str
    url: str | None
    description: str | None
    bands: list[TourBandItem]
    start_date: date
    end_date: date
    collected_live_count: int
    stop_labels: list[str]

class TourStopItem(BaseModel):
    stop_order: int
    stop_label: str | None
    live_id: int
    live_date: date
    live_title: str
    live_type: str
    venue: str | None
    bands: list[int]
    url: str | None
    is_favorite: bool
    has_setlist: bool

class TourDetailResponse(TourSummary):
    stops: list[TourStopItem]
```

`LiveItem` 和 `LiveDetailResponse` 增加：

```python
tour: TourRef | None = None
```

保持嵌套 `tour` 对象而不是平铺 `tour_id / tour_title`，便于前端对可空关系做完整判断，也为后续增加巡演 URL 保留结构边界。

## 公共 API

### `GET /api/catalog/tours`

查询参数：

| 参数 | 类型 | 规则 |
|---|---|---|
| `page` | int | `>= 1`，超过末页时钳制 |
| `page_size` | int | 与现有列表一致，只允许 `15 / 20` |
| `q` | string | trim 后为空等同未传，最长 255 |
| `year` | int | `1900..2100` |
| `band_id` | int | `>= 1` |
| `sort` | string | `date_desc / date_asc` |

查询步骤：

1. 以 `tour_attrs` 为主表。
2. `JOIN tour_lives -> live_attrs`，因此不会返回零场次 Tour。
3. `q` 匹配 `tour_title`、`stop_label` 和关联 `live_title`，使用现有 `% / _ / \\` 转义规则。
4. `year` 使用 `EXISTS`，只要任一关联 Live 位于该年份即命中。
5. `band_id` 匹配 `tour_bands`，不从 setlist 推断。
6. 聚合 `MIN(live_date)`、`MAX(live_date)` 和 `COUNT(DISTINCT live_id)`。
7. 默认按 `MAX(live_date) DESC, tour_id DESC`；升序使用 `MIN(live_date) ASC, tour_id ASC`。
8. count 查询与 page 查询复用同一筛选条件生成器。

响应：

```json
{
  "items": [],
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total": 0,
    "total_pages": 1
  }
}
```

### `GET /api/catalog/tours/{tour_id}`

- Tour 不存在返回 `404`。
- 返回 Tour 摘要和完整 `stops`。
- `stops` 按 `stop_order ASC`，再以 `live_id ASC` 防御性稳定排序。
- `has_setlist` 使用 `EXISTS`，不加载 setlist 明细。
- 登录用户批量查询 stops 对应的收藏状态；匿名统一为 `false`。
- Tour 意外没有关联 Live 时视为数据异常，返回 `500` 并记录日志，不伪装成正常空详情。

### 扩展 `GET /api/catalog/search`

`CatalogSearchResponse` 增加：

```python
tours: list[TourSummary]
```

- Tour 分组匹配 `tour_title`；第一版公共聚合搜索不因场次标题命中而返回 Tour，避免搜索结果扩散过大。
- 每个分组仍独立应用 `limit`。
- 前端分组顺序为 `巡演 -> Live -> 乐队 -> 歌曲 -> 场地`。
- Live 搜索行为不变；同一关键词可以同时命中 Tour 和其场次。

### 扩展 Live 列表与详情

以下路径都必须返回同一 `tour` 语义：

- `GET /api/lives`
- `GET /api/me/favorites/lives`
- `GET /api/catalog/bands/{band_id}/lives`
- `GET /api/lives/{live_id}`
- `POST /api/lives/details:batch`
- catalog 搜索中的 Live 结果

实现时在 Live header/list 查询中 `LEFT JOIN tour_lives` 和 `tour_attrs`。`tour_lives.live_id` 唯一，关联不会扩大单场结果数。单详情和批量详情必须共用 `TourRef` 构造逻辑，防止预读缓存与实时详情字段不一致。

## 控制台 API

### `POST /api/console/tours`

请求体：

```json
{
  "tour_title": "Ave Mujica LIVE TOUR 2026「Exitus」",
  "url": "https://example.com/tours/exitus",
  "description": null,
  "band_ids": [9],
  "stops": [
    {"live_id": 45, "stop_order": 1, "stop_label": "福冈公演"}
  ]
}
```

规则：

- 要求 `editor+` 和有效 CSRF。
- `tour_title` trim 后非空，最长 255。
- `url` trim 后为空规范化为 `null`，非空最长 2048。
- `description` 可空，非空最长 4000。
- `band_ids` 至少一项、最多 100 项，必须全部存在；按请求顺序保存并拒绝重复。
- `stops` 至少一项、最多 500 项；`live_id`、`stop_order` 均不得重复。
- 所有 Live 必须存在且尚未属于其他 Tour。
- 在一个事务中写入 Tour、乐队和场次；任一步失败全部回滚。
- 写一条汇总审计日志，不为每个 stop 单独写日志。

### `PUT /api/console/tours/{tour_id}`

- 使用与创建相同的完整请求体和验证。
- 以请求中的 `band_ids` 和 `stops` 作为完整目标集合，在事务中替换当前关联。
- 校验 Live 冲突时排除当前 Tour 自己的现有关系。
- 更新成功后写一条包含 Tour ID、变更前后数量和操作者的汇总审计日志。
- 第一版不提供 `DELETE /api/console/tours/{tour_id}`。

错误语义：

- `404`：Tour、Band 或 Live 不存在。
- `409`：Live 已属于其他 Tour，detail 中返回冲突的 `live_id / tour_id / tour_title`。
- `422`：Pydantic 字段或集合验证失败。

## 前端类型与数据访问

在 `frontend/src/api.ts` 增加：

- `TourRef`
- `TourBandItem`
- `TourSummary`
- `ToursResponse`
- `TourStopItem`
- `TourDetailResponse`
- `getTours(filters)`
- `getTourDetail(tourId)`
- `createConsoleTour(payload)`
- `updateConsoleTour(tourId, payload)`

Live 类型增加 `tour: TourRef | null`。旧缓存数据不能假设该字段存在；读取缓存时使用 `item.tour ?? null`，发布后自然被新请求替换。

巡演列表缓存键包含 `page / page_size / q / year / band_id / sort`。Tour 详情使用独立按 ID 的 LRU 请求缓存，不混入 Live 详情缓存。控制台写成功后清理 Tour 列表、Tour 详情、公共搜索和受影响 Live 详情缓存。

## 前端页面状态

### App 状态

为适配当前 `TabKey`/History state 结构，新增：

```ts
type TabKey = ExistingTabKey | "tours" | "tour_detail";
```

- 全局导航仍只显示一个“演出资料”。
- 当 tab 为 `all / favorites / tours` 时，“演出资料”保持选中。
- `all / favorites` 继续承载场次与收藏范围。
- `tours` 承载巡演列表，不复用 favorites 语义。
- `tour_detail` 保存 `tourId`、来源 tab、巡演列表页码和滚动位置。
- 浏览器返回恢复原实体、筛选、页码和滚动位置。

当前应用尚未全面落地可分享 URL；巡演实现不单独引入一套不一致的路由器。等公共端 URL 状态改造统一实施时，目标路径为 `/tours` 和 `/tours/{tour_id}`。

### 组件拆分

建议新增：

- `TourArchiveSwitch.tsx`：场次/巡演实体切换。
- `TourListFilters.tsx`：巡演关键词、年份、乐队和排序。
- `TourCardGrid.tsx`：巡演卡片与分页/连续加载状态。
- `TourDetailPage.tsx`：巡演头部和场次列表。
- `TourAdminSection.tsx`：创建、查询和编辑巡演。

现有 `LiveDetailPage` 只增加 `tour` 元数据入口，不把巡演详情逻辑塞入其中。

### 列表与详情交互

- “场次 / 巡演”放在 PageTitle 下、业务筛选上方。
- 巡演卡片主要详情操作使用真实 `<button>`；官方来源使用独立 `<a>`。
- 登录用户在 Tour stop 中复用现有 Live 收藏按钮和乐观同步逻辑。
- Tour stop 打开 `LiveDetailPage` 时，把返回来源记为 `tour_detail`。
- Live 详情中的 Tour 名称打开 `TourDetailPage`，返回时恢复 Live 详情。
- `has_setlist=false` 显示“Setlist 待补充”，但仍允许打开 Live 详情。

## 控制台交互

控制台新增“巡演管理”模式：

1. 输入巡演标题、来源和说明。
2. 使用现有 band lookup 选择参与乐队并调整显示顺序。
3. 使用分页 Live lookup 搜索场次；候选显示日期、标题、场地和当前 Tour 状态。
4. 已属于其他 Tour 的 Live 在选择前置灰并显示所属 Tour，不等提交后才告知。
5. 新加入场次默认按 `live_date ASC, live_id ASC` 重排。
6. editor 可以修改 stop label、拖动/按钮调整顺序和移除关联。
7. 提交前显示完整确认页；创建和更新复用现有控制台确认交互。

写接口仍保留服务端 `409` 作为并发和绕过 UI 的最终保护。

## 查询与性能

- Tour 列表先对满足筛选的 Tour ID 做分页，再聚合乐队和 stop label，避免在全量聚合结果上分页。
- Tour 详情在固定 Tour ID 下分三次有界查询：header/聚合、bands、stops；收藏状态对 stop Live ID 批量查询。
- Live 列表增加的一对零或一 Tour join 不改变分页口径。
- 批量 Live 详情的 TourRef 与其他 header 字段在同一查询返回，不产生 N+1。
- 当前最多几十到数百条 Live，不增加物化视图或专用缓存服务。

## 安全、权限与审计

- 公共 Tour API 只读且匿名可访问。
- 控制台写入统一要求 `require_role("editor")` 和 `assert_valid_csrf`。
- SQL 值全部参数化；排序只从固定枚举映射到 SQL。
- 关联替换必须在单一事务完成。
- 审计日志记录 Tour ID、标题、band 数、stop 数、受影响 Live ID 和操作类型；避免把完整 description 重复写入日志。
- API 错误日志记录 ID 和数量，不记录 session cookie、CSRF token 或凭据。

## 后续演进

巡演聚合稳定后，可按真实需求依次评估：

- 巡演 setlist 差异、固定曲目、替换曲目和平均 setlist。
