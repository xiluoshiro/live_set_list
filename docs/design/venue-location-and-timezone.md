## 已确认的产品口径

1. 用户先知道场馆名称，再搜索和确认坐标。Venue 名称仍是新增、搜索和选择的入口，不建立“无名称坐标点转为场馆”的新业务类型。
2. 坐标是跨地图平台的统一定位依据；内部 `venue_id` 仍是场馆身份，坐标相同不代表同一 Venue。
3. 后续拟支持地图点选、调整坐标；目前以输入经纬度维护 WGS84 坐标。
4. 各地图平台分别保存可选的地点关联。打开地图时，有已确认的场馆匹配则优先打开该平台场馆详情，否则显示坐标点。
5. 不依赖 Google Place ID 作为主数据标识；设计应支持 Google Maps、Apple Maps、高德等独立适配。
6. 位置明确的实体场馆自动确定 Live 时区，普通 Live 表单不再要求手动填写 UTC 偏移。
7. 只公布城市或未公布 Venue 时，Live 使用固定 `+09:00`，不从地区记录继承时区。
8. 只有 online Venue 的 Live 可以依据主办方公告选择显式 IANA 时区；其他场景不开放手选。

本文同时记录已实现的阶段和后续设计。标为“已落地”的表、字段和接口已经存在；其余带“建议”措辞的内容仍是后续阶段方案。地图搜索供应商、账号和坐标到时区解析数据集仍属于接入验证项，产品规则不依赖其最终选择。

## 历史第三阶段方案：Venue 地理与时区资料持续治理闭环（非当前待办）

目标是把一次性回填升级为可长期运行的 `地区建档 → 地图核验 → Venue 保存 → 影响分析 → Live 复核 → 公共发布 → 质量检查` 闭环。以下五项目标按依赖顺序推进；前三项构成必须完成的主数据治理闭环，地图平台接入可独立启用。

### 目标一：统一地理主数据管理

- Console 支持国家／地区、一级行政区、城市三级记录的新增、修改和查询；`country_code` 遵守 ISO 3166-1 alpha-2，层级字段组合由后端和数据库共同约束。
- 地区修改使用 `revision` 并发控制，保存前展示引用 Venue、关联 Live、时区真正变化的 Live 以及将失效的地图关联；保存时推进引用 Venue 的 `location_revision`，但不改写历史 Live 快照。

- 验收：三级记录均可维护；过期提交返回 409；重复项返回 409；地区时区不变时不误报 Live 冲突；地区时区变化时列出复核明细；审计包含 before/after 和影响数量；沖縄県等无城市记录正常工作；既有数据无非预期改写。

### 目标二：Venue 地理资料维护工作台

- 将现有位置面板整合为字段级核验工作台，统一处理所在地、门牌地址、WGS84 坐标、有效时区、地图关联和 Live 影响；支持名称／地址搜索、地图点选或拖动及大型园区入口／中心点口径。

## 数据模型

### 1. 城市与行政区

建议新增轻量的 `geo_localities`，用于统一 Venue 所在城市与 Live 已公布城市的引用，按实际使用逐步维护，不预装全世界城市。

| 建议字段 | 语义 |
|---|---|
| `id` | 内部稳定城市／地区 ID |
| `country_code` | ISO 3166-1 alpha-2 国家／地区代码 |
| `admin_area` | 都道府县、省、州等一级行政区，可空 |
| `locality_name` | 实际城市／市区町村名称 |
| `timezone_id` | 经核验的 IANA 时区，可空 |
| `revision` | 修订号，用于并发和解析结果失效检查 |

城市按“国家／地区 + 一级行政区 + 当地城市名称”展示以减少同名歧义，但不能仅凭名称字符串自动判重或当作全球唯一键。第一期使用当地正式名，不要求先实现多语言名称系统。

一个已确认地区只有在能可靠对应单一时区时才填写 `timezone_id`。跨时区或范围过大的行政区应要求进一步细化地区；不能用城市中心点代替完整行政范围推定，也不能仅凭国家名称统一推定。

### 2. Venue 地理资料

建议在 `venue_list` 增加：

| 建议字段 | 语义 |
|---|---|
| `locality_id` | 可空，指向已确认城市／地区 |
| `address` | 可空，经过核对的地址 |
| `latitude` / `longitude` | 可空，统一 WGS84 坐标 |
| `timezone_id` | 可空，已确认精确位置对应的 IANA 时区 |
| `location_revision` | 地理资料修订号 |
| `location_verified_at` | 本次位置核验时间，可空 |

国家、行政区和城市通过 `locality_id` 获得，不在 Venue 重复维护另一套自由文本。精确位置的时区与城市时区发生冲突时提示并要求核验，不静默选择一个值。

约束和语义：

- 纬度范围 `[-90, 90]`，经度范围 `[-180, 180]`；两列同时为空或同时有值。`0` 是合法坐标，不能表示未填写。
- 使用明确的 `latitude` / `longitude` 字段传递，避免数组经纬顺序混淆。建议 `numeric(9,6)` / `numeric(10,6)`；存储精度不等于资料实际精度。
- 有坐标但尚未完成时区核验可以保存为待补资料；新建 Live 使用前应补齐，或有可用的已确认城市时区。
- 有场馆名称但没有坐标可以保存，允许先选择城市。地图缺失不阻止名称历史维护。
- 不为线上 Venue 填写虚构坐标或固定城市时区。已有 `undisclosed` Venue 可关联已公布城市，但不推测精确点。
- 坐标用于场馆位置，首期不承诺指向具体入口或适合所有交通方式的到达点。
- 同址更名不更新坐标身份；真实搬迁新建 Venue。录错坐标属于资料修正，不创建名称版本。
- 位置来源、原始坐标系、转换方法／版本、操作者和修改前后值记录在审计载荷中；不新增通用来源链接或自由备注管理功能。外部响应只记录获准保留的必要信息。

### 3. 多地图关联

建议新增 `venue_map_links`：

| 建议字段 | 语义 |
|---|---|
| `venue_id` / `provider` | 一个 Venue 在每个平台最多一条当前关联 |
| `provider_place_id` | 平台地点 ID，可空 |
| `provider_url` | 平台支持的详情 URL，可空；只接受适配器白名单 |
| `location_revision` | 关联确认时对应的 Venue 位置修订号 |
| `verified_at` | 匹配核验时间 |

地点 ID 和详情 URL 至少具备一个。平台支持何种方式由适配器决定，不要求所有平台都有同一种 ID。

只有经确认且修订号仍有效的关联可以优先展示；搜索候选不直接作为已确认记录保存。不同 Venue 可能对应同一个园区地点，所以不对 `(provider, provider_place_id)` 建全局唯一约束。

修改坐标后，旧关联失效，页面回退坐标点并提示重新核对。单纯地址文字修正可以保留已确认关联，但必须由服务层明确判定和记录，不能让陈旧的修订号绕过校验。

## 从名称到坐标的管理流程

1. 先搜索内部 Venue 的当前名和历史名，避免重复创建。
2. 新建时输入场馆名；编辑时使用当前场馆名作为外部搜索初值。可以补国家／城市缩小搜索范围。
3. 调用所选地图供应商搜索，显示候选名称、地址、位置与平台来源；同名结果不自动选第一条。
4. 编辑者选中候选，在地图上核对位置，可点选或拖动标记调整。地图候选名不自动覆盖内部正式名。
5. 适配层处理原始坐标系，得到统一坐标；解析国家、行政区、城市和时区，返回草稿。
6. 展示待保存的名称、所在地、坐标位置与时区。编辑者核对后提交，后端重新校验并写入审计。
7. 可分别关联其他地图平台的地点。该操作可以稍后进行，不阻止使用坐标链接。

Live 快捷新增 Venue 复用这套表单／服务。不能继续只新增名字后默认使用日本偏移；允许先存名称和城市，再补精确位置。

地图失败时保留已输入名称、城市和草稿；提供经纬度补录。不得以 `(0, 0)`、默认城市或 `+09:00` 冒充解析成功。拖动坐标后应废弃先前未完成的解析响应，避免异步结果覆盖新位置。

## 坐标系与地图链接

### 统一存储与平台适配

- 主数据使用 WGS84，输入必须携带源坐标系；不能把高德点选结果直接当 WGS84 写入。
- 适配器声明搜索结果／点选输入坐标系、链接所需坐标系和适用地区。不能仅按品牌假定所有接口及地区行为相同。
- 高德官方提供非高德坐标转高德坐标的接口；这不证明同一接口提供无损逆向转换。上线前验证点选结果转回统一坐标的可用方法、误差和使用许可。[高德坐标转换](https://developer.amap.com/api/webservice/guide/api/convert)
- 若某平台无法提供符合精度和使用条件的统一坐标转换，则该平台先只提供外链，不作为主坐标采集入口。不能把近似转换宣传为精确可逆。
- 平台原生坐标如需缓存，必须携带坐标系、位置修订号和有效期；它是派生数据，不替代主坐标。
- 时区解析使用统一坐标。更换底图不改变 Venue 坐标或已确认时区。

### 打开顺序

对用户选择的平台，依次使用：

1. 已确认、仍有效且平台支持的场馆详情关联。
2. 场馆精确坐标点，并附带名称作为标签。
3. 无精确坐标时，不显示“场馆位置”按钮；若有城市可提供明确标注的“查看城市范围”，不把城市标记成场馆。

Google Maps URLs 支持坐标查询及 `query_place_id`，链接本身不需要 API Key。[Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)

Apple 使用官方 Maps URL 能力；统一 URL 在较新系统中提供支持，需为目标浏览器／系统验证兼容链接。高德按 URI API 构造标记或详情链接。适配器应通过真实设备／浏览器验收后才声明支持详情能力。[Apple 统一 Maps URLs](https://developer.apple.com/documentation/mapkit/unified-map-urls)、[Apple 兼容 Map Links](https://developer.apple.com/library/archive/featuredarticles/iPhoneURLScheme_Reference/MapLinks/MapLinks.html)、[高德 URI API](https://lbs.amap.com/api/uri-api/summary)

外部页面打开后可能因该平台 POI 删除而失效，本站通常无法检测。页面始终保留显式“按坐标打开”入口，不承诺自动识别外部页面失败并回退。

公共读取只生成链接，不在每次 Live 浏览时搜索三家地图或发起坐标转换网络请求。未接入、无地区覆盖或转换不可用的平台不展示伪可用按钮。

### 数据来源与服务边界

统一存坐标不自动获得跨平台使用权。Google Places 对存储和展示有约束，Place ID 的长期保存例外不能推导为所有字段都能永久保存，更不能推导为 Google 返回的数据可以直接显示在其他底图上。[Places 政策](https://developers.google.com/maps/documentation/places/web-service/policies)

接入前逐项验证：搜索、地图点选、逆地理编码、坐标转换、时区查询的数据能否用于永久主数据以及跨地图展示。管理员点击确认也不会改变供应商条款。跨平台主坐标应来自允许该用途的数据来源；受限平台数据仅在授权范围内用于该平台功能。当前候选内容只在 Console 搜索和确认期间临时展示，审计不保存供应商返回的候选名称、地址或坐标；Google 搜索结果的品牌标识和展示许可尚未验收，因此不得仅凭配置 Key 宣称生产接入完成。

第一期至少选定一个可用的搜索／点选供应商并完成许可与坐标验证，其余供应商可先接外链。无需为了同时显示三种链接购买三套搜索服务。Key、预算、配额、服务端限制和前端域名限制分别配置；客户端不得持有服务端密钥。

当前服务端候选搜索按需读取以下可选环境变量，不配置时接口返回 `not_configured`，Console 明确回退手工关联，不把缺少凭据当成 Venue 保存失败：

- `GOOGLE_MAPS_PLACES_API_KEY`：Google Places API (New) 服务端 Key；调用 Text Search (New)，只请求候选所需字段。
- `APPLE_MAPS_SERVER_API_TOKEN`：Apple Maps Server API 的短期 Maps access token，不是私钥文件；生产环境必须另行建立安全的 token 刷新流程。
- `AMAP_WEB_SERVICE_API_KEY`：高德 Web 服务 API Key；中国大陆候选坐标按 GCJ-02 处理。

这些值只进入进程环境或生产 secret，不提交仓库，也不下发浏览器。Google、Apple、高德的正式上线仍分别受各自账号、配额、费用和数据使用条款约束。[Google Text Search (New)](https://developers.google.com/maps/documentation/places/web-service/text-search)、[Apple Maps Server API Search](https://developer.apple.com/documentation/applemapsserverapi/-v1-search)、[高德搜索 POI](https://lbs.amap.com/api/webservice/guide/api/search/)

## Live 所在地与时区

### 有效所在地

Live 建议增加可空的 `announced_locality_id`，专门表达尚无精确 Venue 时已公布的城市。

- `venue_id = NULL` 且城市已公布：保存城市，Venue 及名称版本仍同时为 `NULL`。
- 选择实体 Venue：城市来自 Venue，不另外保留相互冲突的 Live 城市值。
- 只公布城市不创建“某城市待定场馆”占位 Venue。
- 由场馆改回城市范围需要明确选择城市；表单可以预填旧城市，但不能在未确认时把它当作仍然有效的公告事实。
- 由城市补充到 Venue 后，清除独立城市输入；若不在原公布城市，需要按已公布所在地变更处理。
- 线上 Live 不因组织方办公城市推定时区。

### 自动确定顺序

| 场景 | 时区来源 | Live 表单 |
|---|---|---|
| 实体 Venue 有已确认位置时区 | `venue.timezone_id` | 只读显示“由场馆确定” |
| Venue 只有已确认城市，或地点模糊 Venue 关联城市 | 城市 `timezone_id` | 只读显示“由城市确定” |
| 无 Venue，但已公布城市 | `announced_locality_id` 的时区 | 只读显示“由城市确定” |
| 线上或完全未公布所在地 | 公告指定 IANA 时区 | 显示例外选择入口 |
| 城市／场馆资料不足或有冲突 | 待核验 | 指向资料修正，不静默降级到日本时间 |

城市有明确单一时区即可自动确定，不要求经纬度。无法唯一判断的城市条目先细化所在地或核验城市时区；这是资料问题，不是普通 Live 任意手填偏移的理由。

例外入口选择 IANA 时区，显示“活动时间按哪个地区的时间公布”，允许附简短依据。线上场次分别保存，不能给共用 ONLINE Venue 设置一个通用时区。若连活动时区也没有公布，新建流程提示缺少必要时间基准，不擅自按用户设备或服务器时区保存；支持完全未知时区并发布属于后续独立需求。

### Live 保存模型

建议增加：

| 字段 | 语义 |
|---|---|
| `announced_locality_id` | 无精确 Venue 时的已公布城市 |
| `timezone_id` | 本次排期采用的 IANA 时区快照；旧记录兼容期可空 |
| `timezone_source` | `venue` / `locality` / `explicit` / `legacy_offset` |
| `timezone_source_revision` | 来源地理资料修订号，可空 |

时区 ID、来源及修订号由后端推导；客户端传递所在地和仅适用于例外场景的时区选择。实体场馆的新写入不能通过旧 `timezone` 请求参数绕过推导。

保留 Live 当地日期与当地钟点的业务语义。开场／入场时间为 `NULL` 仍表示未公布，不能补成午夜或中午。兼容期保留现有 `timetz` 输出，已知时间的偏移由“日期 + 各自钟点 + IANA 时区”分别计算。

`timezone_offset_minutes` 只在旧记录回退和兼容阶段使用，不再作为新模型的唯一真值。IANA 记录时间全未公布时无需制造当天固定偏移；实现时需允许该兼容字段为空，先升级消费者再放宽数据库约束。API 新增明确时区标识与逐时间偏移；旧 `timezone` 单偏移字段在所有调用方迁移后退役，不要求它表达夏令时切换日两个不同偏移。

### 日期规则与夏令时

- 使用 Python `zoneinfo` 解析 IANA 时区，在 Windows 显式准备 `tzdata`。部署时管理 Python 与 PostgreSQL 时区数据版本及更新流程。[Python zoneinfo](https://docs.python.org/3.12/library/zoneinfo.html)
- Venue 坐标到时区的解析仅在位置维护时进行；Live 保存和读取不依赖地图在线服务。解析器可用服务或本地边界数据实现，选择前验证许可、覆盖、边界精度与历史局限。
- Google Time Zone API 不追溯地点历史上曾属于不同时间区的情况，不能据此盲目覆盖历史 Live。[Time Zone API](https://developers.google.com/maps/documentation/timezone/requests-timezone)
- 每个已公布钟点分别计算偏移，不直接复用“今天”的偏移；日期跨夏令时变化时重新解析。
- 春季跳时中不存在的当地时间拒绝保存并提示核实；秋季重复时间要求选择第一次／第二次并持久化该选择。仅调用 `replace(tzinfo=...)` 不足以完成校验，需要往返 UTC 验证及歧义检测。
- 首期钟点仍属于 `live_date` 当天，不顺带引入 `24:30` 或次日开场表达。超出这一模型的需求单独设计。
- 判断“今天”使用当前时刻在 Live 时区的当地日期；不能用演出日期的偏移换算今天。Python、SQL、前端预览必须使用同一语义。
- 时间规则更新后，对未来 Live 生成受影响清单并受审计刷新派生值；已结束记录不静默重写原始排期。明确的历史资料错误通过修正流程处理。

## 历史与变更语义

### 名称与地图

Live 的名称仍取已绑定的名称版本，地图详情可能显示平台当前名称。这是允许的差异；不要为了匹配地图名称修改历史 Live 的版本。

经核实的同一场馆坐标纠错可以改善所有历史页面的地图定位；真实迁址必须新建 Venue，因此旧 Live 不会被引导到新地址。

### 排期变更

现有 `announcement_only` 仅允许 Venue／时间等从空变为有值，偏移变化会触发变更分类。新规则需要先比较业务事实，再比较派生字段：

| 操作 | 建议处理 |
|---|---|
| 首次公布城市／Venue，之前没有冲突的已确认时间基准 | 公告补齐；自动派生时区不单独制造正式改期 |
| 从城市补充到同城 Venue，时区一致 | 公告细化，不是正式改期 |
| 新 Venue 与已公布城市不一致 | 已公布所在地变更，要求资料修正或正式改期 |
| 自动时区与已明确公告时区冲突 | 要求核对并选择修正／改期，不能覆盖确认事实 |
| 旧系统默认偏移与首次真实所在地冲突 | 人工核验旧偏移依据；不能仅凭旧值推定它已被公告，也不能自动认定它只是默认值 |
| 更改 Live 日期导致夏令时偏移改变 | 日期变更流程统一处理，避免重复确认 |
| 仅地图关联变化，坐标和时区不变 | Venue 资料审计，不触发 Live 排期变更 |

正式改期保存旧 `timezone_id`、旧来源、旧兼容偏移以及旧有效城市 ID／展示快照；即使旧开场／入场时间都是 `NULL` 也完整保留。新旧排期各自独立解析，历史不能实时 join 当前 Venue 时区。

### Venue 资料修正和合并

修改 Venue／城市时区先返回影响预览：未来／过去 Live 数、原时区、拟采用时区、钟点和 UTC 瞬间是否改变。保存主数据不自动批量修改既有 Live；后续显式应用修正，记录来源修订号。

编辑既有 Live 时，如果来源修订号变化，显示待处理差异；不能在只改标题时顺便覆盖其排期时区。提交遇到并发修订返回冲突并要求刷新预览。

Venue 合并继续要求管理员操作。新增校验包括国家／城市、坐标距离和时区差异；差异不允许以“名称相似”跳过。地图关联逐平台选择保留项，不静默覆盖；既有 Live 时区快照不因换成目标 Venue ID 自动改变。错误合并仍通过审计和明确修复流程处理。

## 接口与前端改造建议

### 管理接口

- 扩展 `GET /api/console/venues` 和详情响应，返回所在地、坐标、有效时区及缺失状态；城市筛选与分页总数使用相同条件。
- 扩展 Venue 创建和基础资料修改，保留现有角色、CSRF、事务锁和审计。
- 新增 `GET /api/console/localities?q=`，用于选择已核验城市；必要的城市创建／核验采用编辑者权限和审计。
- 新增地图搜索与位置解析接口，供搜索候选和点选后的草稿预览使用；读取／预览不修改 Venue。
- 新增 `POST /api/console/venues/{id}/location-preview`，返回拟更新的位置、时区和关联 Live 影响。
- 新增或扩展地图关联维护接口，按 provider 保存／取消已确认匹配。
- Live 预览返回 `effective_timezone_id`、来源、逐钟点偏移和冲突信息；最终写入在事务内重新检查来源修订号。

搜索与解析接口需要编辑者权限、超时和限流，不成为公开地图代理。前端只拿到必要展示字段；所有结果保存仍需业务校验，不能信任客户端计算的时区或偏移。

### 页面

- Venue 管理增加“所在地与地图”区域，复用现有表单、确认对话框、错误信息和分页，不另建风格不同的管理页面。
- 场馆搜索仍以名称为主，候选辅助显示国家／城市；地图只用于定位核对。
- 展示自动时区的可读名称／ID及所选 Live 日期适用偏移；“来自场馆／城市／活动公告”可以帮助编辑者判断，无需在公共页面展示数据库字段名。
- 只公布城市的 Live 明确显示“场馆暂未公布 · 城市名”；Venue 引用仍为空。
- 公共 Live 详情先提供地图选择菜单和“按坐标打开”；列表不加载地图 SDK。
- 移动端允许地图操作区与字段换行，核对弹窗在窄屏和高缩放下仍可操作。

### 全链路检查位置

除 Venue、Live 的 schema / API 类型与表单外，需要检查 `live_status.py`、`console_read.py` 的当地日期 SQL、`performance_groups.py` 的聚合日期排序，以及 lives、catalog、me、tours 等状态返回路径。日历、收藏、搜索、活动组、未录 Setlist 候选的日期判断都应确认口径；不得只修改前端展示。

## 实施顺序与准备工作

### 阶段一：数据与接入验证

1. 只读盘点当前 Venue 类型、使用量、已有 Live 偏移、时间未公布和历史排期情况；此设计未执行该盘点。
2. 按 Venue ID 制作回填候选，包含国家／城市、坐标、原始坐标系、时区和核验依据；名称／坐标相似只作为人工核对提示。
3. 优先核验未来 Live 使用的场馆。不能从 `+09:00` 反推城市，也不能批量用名称搜索第一条结果回填。
4. 选定至少一个允许用途且可访问的搜索／点选供应商和坐标到时区解析实现。用日本、中国境内、其他时区样本验证坐标往返、链接定位和时区结果。
5. 分别验证三种地图的坐标外链；可选 POI 详情能力以实际文档和设备结果为准。账号、费用、Key 和配额在接入前配置，不在设计阶段开通。

### 阶段二：加法迁移与 Venue 管理

1. 新增城市、地理字段和地图关联；沿用既有 Venue／名称版本引用。
2. 新对象纳入 owner、运行角色权限和测试 seed 契约，不修改 `flyway_schema_history` 所有权。
3. 先上线可空资料和位置管理；再通过受审计操作回填已核验记录，不把外部场馆事实硬编码到 schema migration。
4. 选择新迁移号前检查仓库实际最新版本；不得修改已执行的 V28／V29 等文件。

### 阶段三：Live 时区与历史

1. 先增加 Live／历史时区字段与兼容读取，保留旧偏移回退并显式标注 `legacy_offset`。
2. 已核验 Venue 对应的旧 Live 按实际日期计算并与原偏移比较，区分一致、冲突、缺少依据；冲突不自动覆盖。
3. 补历史时区时优先使用该历史记录自己的旧场馆与旧时间。无法推断时保留“旧时区未知”，不借用当前场馆补造历史。
4. 升级所有日期消费者、表单与 API，再启用后端强制推导和兼容字段可空；切换前盘点旧客户端使用情况。
5. 完成回填后再收紧“新实体 Live 必须有可确定时区”的约束。旧数据可分批核验，但不能以旧兼容路径绕过新记录规则。

### 阶段四：发布与验证

业务代码实现后，最终执行 `python scripts/run_checks.py functional` 并取得成功。新增测试遵循附近说明测试点的仓库技能；日期阶段测试从运行时或注入时钟派生，不硬编码当前日期。夏令时测试使用显式固定历史转换样本，不能依赖真实今天。

本地主库迁移独立执行备份、迁移、校验与健康检查，遵循本地主库技能；本文不授权远程访问或部署。回退保留新增资料，回退应用前核验其能否读取新记录及可空偏移，不能直接回滚到不兼容旧程序。

## 验收标准

| 场景 | 预期 |
|---|---|
| Live 详情中的场馆区域 | 场馆名称进入站内 Venue 详情；旁侧地图按钮展开外部地图选项，两个控件职责与点击区域独立 |
| Venue 详情直达与返回 | `/venues/{venue_id}` 可直接访问并正确恢复来源页；更名前后的 Live 均进入同一稳定 Venue |
| Venue 公开资料 | 展示当前名、历史名称、类型、所在地、地址、坐标、有效时区、地图入口及分页 Live，不暴露审计和修订控制字段 |
| 从场馆名搜索并点选 | 原正式名称保留，坐标和解析草稿可核对，旧响应不覆盖新点 |
| 同名异地场馆 | 明确展示地址／城市，不自动选中或合并 |
| 一个 Venue 对应三种地图 | 独立详情关联；缺关联的平台仍可按坐标打开 |
| 同园区多个 Hall | 允许共享坐标／平台地点，内部 ID 与名称历史独立 |
| 切换底图 | 主坐标不漂移；时区不因底图改变 |
| 修改坐标 | 旧平台匹配需要重新核对；时区变化显示影响预览 |
| 只公布城市 | Venue 两项引用仍为空，自动获得城市时区，不显示虚假场馆点 |
| 线上或完全未公布所在地 | 活动时区例外入口可用，逐场保存 |
| 时间均未公布 | 不制造钟点，依时区正确判断当地日期 |
| 改日期跨夏令时 | 各钟点偏移重新计算，重复／不存在时间有明确处理 |
| 首次公布场馆 | 无已确认事实冲突时是资料补齐；有冲突时要求处理 |
| 场馆资料修正／合并 | 不静默重写 Live 时区和历史排期 |
| 编辑标题时来源已变 | 提示差异，不顺便改排期 |
| 地图服务不可用 | 已保存 Live 读取和时区计算正常，草稿不丢失 |
| 历史 Live | 显示原名称版本，旧时区信息独立，不从当前 Venue 动态借用 |
| 窄屏与高缩放 | 表单、地图核对、例外入口均可见可操作 |

验收还需覆盖经纬度顺序、原生坐标误标、城市同名、冲突修订、无效平台链接和权限校验。地图部分以真实浏览器／设备定位为证据，jsdom 测试不能证明地图准确或样式可用。
