# React 列表 key 碰撞复盘

本文档记录 2026-07-22 巡演统计在相邻场次间反复切换后，“新增歌曲”行数不断变化的问题，以及对其他前端列表的同类风险审计。

## 1. 问题现象

目标巡演：`夢限大みゅーたいぷ 対バンライブ「えんかうんた～」`。

- 首次打开 Vol.5 对比 Vol.4 时，变化摘要显示“新增 5”。
- 切到 Vol.4、再回 Vol.5 后，新增歌曲区域会多出一行。
- 再切回 Vol.4，Vol.4 也会残留额外行。
- 错误数量取决于点击顺序，而不是 API 响应内容。

## 2. 根因

Vol.5 的 `added_songs` 中，`Dream Voyage`（`song_id=254`）出现两次。这是有效业务数据：同一首歌在同一场 Setlist 中可以出现多次，不能按 `song_id` 去重。

原组件却使用以下形式生成 React key：

```tsx
key={`added:${song.song_id}`}
```

两条 `Dream Voyage` 因而成为同一父节点下的重复 key。React reconciliation 无法再可靠区分这两个“出现次数”；当列表在 Vol.4 与 Vol.5 之间缩短、增长时，旧 fiber 可能被错误复用或遗留，最终造成 DOM 行数随点击顺序变化。

这里的关键错误不是“没有使用数据库 ID”，而是把歌曲实体 ID 误当成了歌曲出现记录 ID：

- `song_id` 唯一标识歌曲实体；
- 它不唯一标识某场 Setlist 或某次差异中的一次出现。

## 3. 修复

巡演差异中的新增、移除行改用“变化类型 + 出现序号 + song_id”作为 key；保留重复歌曲，不改变统计口径。

```tsx
key={`added:${index}:${song.song_id}`}
key={`removed:${index}:${song.song_id}`}
```

Live 管理的更新记录也发现同类风险：同一个 `live_id` 可以在一次会话中保存多次，而每次保存都是一条独立历史快照。现在由状态写入方为每次保存分配单调递增的 `history_entry_id`，历史表使用该记录 ID，而不是业务实体 `live_id` 作为 key。

## 4. 其他模块审计结果

本轮检查了 `frontend/src` 下全部 JSX `key`：

- 巡演统计 `added_songs` / `removed_songs`：允许同一歌曲重复，已修复。
- Live 更新历史：允许同一 Live 重复保存，已修复。
- 新增歌曲记录：写入时按 `song_id` 覆盖旧项，数组内已去重。
- Setlist 提交记录：成功后会从无 Setlist 候选中移除该 Live，同一会话不会重复加入历史。
- 巡演、活动组新增记录：只记录新建响应，数据库生成的实体 ID 唯一；更新不会加入该数组。
- 巡演/活动组场次、Live/歌曲/场地候选：写入前去重，或由接口与关系约束保证实体 ID 唯一。
- Setlist 预览 `absolute_order`：数据库存在 `(live_id, absolute_order)` 唯一约束，提交前按同一契约生成。
- 详情备注：后端只按两个独立布尔标记生成“短版”“翻唱”，不会产生重复标签。

因此没有把所有 key 机械地追加 index；只有“重复项具有业务意义”或“同一实体可产生多条历史记录”的列表改用出现/记录身份。

## 5. 回归测试

- 巡演统计测试覆盖 Vol.5 → Vol.4 → Vol.5 → Vol.4，逐次断言新增歌曲行数保持 `5 → 3 → 5 → 3`。
- Live 管理测试使用相同 `live_id` 的两条更新快照，断言两条记录都存在且 React 不报告重复 key。

## 6. 后续规则

新增或审查 React 列表时，应先回答“key 标识实体，还是标识这一次出现/这条记录”：

1. 同一实体在数组中可能出现多次时，不能只用实体 ID。
2. 可编辑、可排序的本地记录应在创建时分配稳定记录 ID。
3. 只读且顺序固定的重复出现可组合稳定字段与出现序号。
4. 回归用例应覆盖 A → B → A 的列表切换，不能只断言首次渲染。
5. 出现 `Encountered two children with the same key` 时必须作为功能正确性问题处理，不能只消除控制台日志。

## 7. 一句话结论

React key 必须唯一标识当前兄弟列表中的“记录实例”；数据库实体 ID 只有在数组按实体去重时才天然适合作为 key。
