# 非城市层级回填后场地管理 500 回溯（2026-09-13）

## 现象与影响

本地主库执行 V32 后的独立所在地回填后，控制台「场地管理 → 所在地与地图」显示 `Request failed: 500`。默认 `GET /api/console/localities` 第一页包含香港记录（`id=32`，`area_level=country`，`locality_name=NULL`），因此进入面板即会触发错误，并非只有选中某个特定场馆才会发生。读取关联东京／香港／新加坡所在地的场馆位置及公开场馆详情也存在同类响应校验风险。

## 直接原因

V32 允许 `geo_localities.locality_name` 在 `country`／`admin_area` 层级为 `NULL`，随后手工回填把东京、香港、新加坡三行改为该形态。控制台响应模型 `Locality` 却继承了新增城市请求模型 `LocalityCreate`，后者要求 `locality_name: str`；公开场馆详情响应模型也独立写死为 `str`。数据库查询成功后，FastAPI 对响应进行 Pydantic 校验时收到 `None`，抛出响应校验异常并返回 500。该异常不是数据库错误，不会被路由中只捕获 `psycopg2.Error` 的分支转换。

前端面板用 `Promise.all` 同时加载场馆位置、时区和所在地列表；其中任一请求返回 500，就整体进入错误状态。TypeScript 中 `GeoLocality.locality_name` 同样误写成必有字符串，但静态类型不会验证服务器运行时返回的数据。

## 为什么测试没发现

1. 集成测试在每条用例前恢复测试 seed；seed 清空 `geo_localities`，没有任何 `locality_name=NULL` 的样本。旧地理用例只通过「新增城市」接口创建非空城市名，虽然验证了 V32 的默认 `area_level=locality`，却没有覆盖 V32 新允许的另外两个层级。
2. 公开场馆详情的集成用例也只关联了城市名非空的记录；前端面板和公开详情测试的 API mock 同样全是普通城市。测试通过证明的是旧数据形态可用，不能证明新形态可用。
3. 上轮回填后执行了 SQL 后置条件、Flyway validate 和 owner 契约检查，但没有对主库回填结果再做 API 响应／页面加载验收。`functional` 测试库也不会自动复制主库回填数据，所以在回填前或后运行同一套旧测试都不会暴露此问题。这是验收设计遗漏，不是测试运行器随机漏跑。

## 修复机制

- 将新增城市的写入模型与所在地读模型分离：写入仍要求城市名；读取允许 `locality_name=NULL`，并显式携带 `area_level`。
- 同步修正公开场馆详情响应模型和前端 API 类型；界面继续复用既有「过滤空层级再拼接」的展示规则。
- 新增真实数据库集成用例，插入东京行政区、香港和新加坡国家／地区层级记录，验证默认所在地列表、控制台场馆位置、公开场馆详情均返回 200；补前端空城市名显示用例。

## 后续防复发约束

凡迁移或回填扩大某列的合法取值范围（尤其是引入 `NULL`、新枚举层级），同一变更应对照检查数据库约束、所有响应模型、前端类型和展示分支；集成测试必须至少有一条新形态的真实数据库记录，并经过实际 HTTP 响应校验。手工回填的验收清单还应加入受影响读接口的回填后 smoke test，不能只以 SQL／Flyway 校验替代应用层验收。
