# 社区 Live 数据库首页与个人工作台需求

## 背景

当前 LiveSetList 已具备公共 Live 列表、Live 详情、登录态恢复、服务端收藏、分页预读和 `editor+` 控制台录入能力。现有首页更接近“带收藏能力的数据表格”，还没有完整表达“社区 wiki / 社区数据库”的产品定位。

本需求的目标是把首页升级为社区数据库入口：匿名用户可以直接查询、浏览和发现资料；登录用户可以围绕收藏、关注和个人记录持续使用；有编辑权限的用户可以从首页进入数据补全与维护工作流。

## 外部参照

- setlist.fm：适合参考“搜索优先、数据规模、热门 setlist、近期编辑、活跃用户、热门艺人、即将到来的活动”等首页结构。
- MusicBrainz：适合参考“开放音乐百科、贡献入口、编辑指南、社区入口、最近新增数据”的数据库社区表达。
- Discogs：适合参考“用户生成数据库、个人收藏、想要清单、条目版本与资料完整性”的收藏型数据库体验。
- Last.fm：适合参考“登录后个人记录、推荐、重新发现、个人统计”的个性化首页体验。

参考链接：

- https://www.setlist.fm/
- https://musicbrainz.org/
- https://www.discogs.com/
- https://www.last.fm/

## 产品定位

LiveSetList 的首页不应是营销型落地页，也不应只是后台工具入口。它应首先回答三个用户问题：

1. 这里能查什么？
2. 最近新增或更新了什么？
3. 我登录后能获得什么个人价值，或者能贡献什么？

对应定位：

- 对匿名用户：一个可浏览、可搜索、可验证资料来源的 Live 数据库。
- 对登录用户：一个可以收藏、追踪、重新发现 Live 资料的个人首页。
- 对编辑用户：一个可以发现待补全资料并快速维护的贡献工作台。
- 对管理员：后续承接用户、权限、审核、日志和数据质量治理。

## 用户视角

### 匿名用户

匿名用户进入首页时，应能立刻看到：

- 全局搜索入口：搜索 Live、乐队、歌曲、场地。
- 数据规模：收录 Live、乐队、歌曲、场地数量，以及最近更新时间。
- 公共发现内容：最近新增 Live、最近编辑、热门 Live、按日期或类型浏览。
- 资料质量提示：哪些条目缺 setlist、缺来源 URL、缺成员信息。
- 登录引导：提示登录后可收藏、关注和贡献，但不阻塞公共浏览。

匿名用户可以：

- 浏览首页、全量 Live、Live 详情和公共搜索结果。
- 点击收藏、关注或贡献入口时被引导登录。
- 通过乐队、场地、年份、Live 类型等维度进入列表。

### 登录用户

登录用户进入首页时，除公共内容外，还应看到：

- 我的收藏摘要。
- 最近查看记录。
- 我关注的乐队 / 场地 / 歌曲的新增或更新。
- 收藏 Live 的资料更新提醒。
- 个人统计，例如收藏数量、最近查看、最近贡献。

登录用户可以：

- 收藏或取消收藏 Live。
- 关注乐队、场地或歌曲。
- 查看和自己相关的新增内容。
- 从个人区继续浏览收藏、历史记录和关注更新。

### editor+ 用户

`editor+` 用户进入首页时，还应看到贡献工作台：

- 新增 Live。
- 追加 setlist。
- 新增或补全歌曲。
- 新增或补全场地。
- 待补全条目列表。
- 我的最近提交或最近编辑。

贡献工作台应优先展示最需要维护的数据，而不是只提供一个空白录入表单。

### admin 用户

`admin` 用户后续可在首页或用户菜单中看到：

- 用户管理入口。
- 权限管理入口。
- 审核 / 日志入口。
- 数据质量概览。

管理员能力不是首页一期的重点，但页面结构应预留入口。

## 首页信息架构

首页建议拆成四个主区域。

### 1. 全局搜索区

目标：让用户第一时间开始查询。

内容：

- 搜索框。
- 搜索类型提示：Live、乐队、歌曲、场地。
- 搜索建议或最近热门关键词。
- 空结果、加载、错误状态。

初期可以只支持 Live 名称搜索；后续扩展为聚合搜索。

### 2. 数据概览区

目标：建立数据库感和可信度。

内容：

- Live 总数。
- 乐队总数。
- 歌曲总数。
- 场地总数。
- 最近更新时间。
- 待补全条目数量。

这些指标可以逐步补齐。第一阶段可以只展示已有接口能低成本获得的数据。

### 3. 公共发现区

目标：让用户不搜索也能发现内容。

内容：

- 最近新增 Live。
- 最近编辑。
- 热门 Live。
- 即将到来或近期活动。
- 乐队浏览。
- 按场地浏览。
- 按年份 / 日期浏览。
- 按 Live 类型浏览。

第一阶段可以先展示最近 Live 和现有全量列表入口。

### 4. 登录后个人区

目标：让登录状态带来明确价值。

内容：

- 我的收藏。
- 收藏 Live 最近更新。
- 最近查看。
- 关注更新。
- 我的贡献。
- `editor+` 快捷录入。

未登录时，这一区域应替换为轻量登录引导，而不是空白。

## 功能需求

### 公共浏览

- 匿名用户可访问首页、Live 列表、Live 详情。
- 匿名用户可使用公共搜索。
- 公共页面不应依赖登录态完成首屏加载。
- Live 详情应继续展示来源 URL、日期、类型、乐队、setlist 和成员信息。

### 搜索与筛选

- 支持从首页搜索 Live。
- 后续支持搜索乐队、歌曲、场地。
- 支持从搜索结果跳转到 Live 详情或筛选后的列表。
- 支持按乐队、场地、年份、日期、Live 类型浏览。

### 收藏与个人区

- 收藏能力仅登录后可用。
- 匿名用户点击收藏时弹出登录。
- 登录用户首页展示收藏摘要和入口。
- 登录用户可以看到收藏相关更新。
- 最近查看可以先做本地存储，后续再服务端化。

### 关注与更新

- 支持关注乐队、场地或歌曲。
- 首页展示关注对象的新增 Live 或资料更新。
- 初期可先只设计入口，等搜索和实体页稳定后再实现。

### 贡献工作台

- `editor+` 用户可从首页进入贡献工作台。
- 工作台应展示待补全条目。
- 工作台应提供新增 Live、追加 setlist、补歌曲、补场地入口。
- 录入完成后应刷新公共列表和相关概览。

### 数据质量

- Live 条目应能表达资料完整度或缺失状态。
- 缺失类型至少包括：缺 setlist、缺来源 URL、缺场地、缺成员信息。
- 后续可展示最近编辑、修改历史、审核状态和修正入口。

### 站点基础支持与说明

社区数据库不仅要能查询数据，也要让用户知道项目边界、数据来源、反馈路径和维护方式。首页和全站底部应逐步补齐基础站点支持能力。

基础支持内容包括：

- 关于本站：说明 LiveSetList 的定位、维护者、项目边界和资料完整性限制。
- 联系作者 / 维护者：提供可用联系方式或外部入口，例如 GitHub Discussions、GitHub Issues、邮箱或项目主页。
- 报告 bug：提供应用问题、前端显示问题、接口错误和登录异常的反馈入口。
- 报告资料错误：允许用户围绕具体 Live 反馈 setlist、日期、场地、来源 URL、成员信息等资料问题。
- 数据来源说明：说明资料可能来自公开来源、用户整理和维护者录入，并要求关键资料保留来源 URL。
- 版权与数据授权说明：区分站点代码、用户提交内容、整理后的结构化数据、外部来源链接和第三方商标 / 艺人名称的使用边界。
- 隐私说明：说明登录、收藏、反馈表单、错误监控和访问统计可能涉及的数据。
- 行为准则 / 贡献规范：说明提交资料、反馈问题、参与讨论时的基本要求。
- 更新日志 / 站点状态：后续可用于说明数据导入、功能上线、维护窗口和已知问题。

第一阶段后可先落一个轻量页脚和静态说明页，不要求一次性建设站内反馈系统、评论系统或审核后台。

### 工具和 SDK 候选

可优先复用成熟服务和 SDK，避免过早自建外围系统。

- Bug 反馈和功能建议：优先使用 GitHub Issues 或 GitHub Discussions 外链；后续再评估站内工单。
- 讨论 / 评论：可评估 giscus，将页面讨论托管到 GitHub Discussions；适合后续资料页讨论，但不适合作为第一阶段必做项。
- 联系 / 反馈表单：可评估 Formspree React；适合轻量联系表单，但需要明确隐私说明和防刷策略。
- 错误监控：可评估 Sentry，前端使用 `@sentry/react`，后端使用 `sentry-sdk` 接入 FastAPI。
- 访问统计：可评估 Plausible、Umami 或 PostHog。若只需要基础访问统计，优先选择更轻量、隐私负担更低的方案；若需要功能开关、实验和会话回放，再评估 PostHog。
- 搜索：阶段 2 先评估 PostgreSQL 全文 / 模糊搜索；如果后续需要更强搜索体验，再评估 Meilisearch 或 Algolia React InstantSearch。
- 反垃圾 / 防刷：反馈表单、公开注册、匿名资料纠错开放后，可评估 Cloudflare Turnstile。

### 权限与可见性

- 匿名用户：公共浏览、公共搜索。
- viewer：收藏、个人区、关注。
- editor：viewer 能力 + 贡献工作台。
- admin：editor 能力 + 用户 / 权限 / 审核 / 日志入口。

受限入口可以在 UI 上隐藏或置灰，但后端仍必须保持权限校验。

## 分阶段目标

### 阶段 1：首页壳与信息架构

目标：把默认页面从纯表格改为社区数据库入口。

交付：

- 新首页布局：搜索区、数据概览、最近 Live、现有列表入口。
- 保留现有演出资料、收藏范围切换和控制台能力。
- 匿名用户默认看到公共首页。
- 登录入口不阻塞浏览。
- `editor+` 控制台入口仍按权限展示。

验收：

- 未登录打开首页能理解这是 Live 数据库。
- 可以从首页进入全量 Live 列表和 Live 详情。
- 登录、收藏、控制台不发生回退。
- 首屏不是营销页，也不是单一后台表格。

#### 阶段 1 详细范围界定

阶段 1 是首页改造的最小可用版本，重点是信息架构和入口重组，不追求一次性完成搜索、统计、关注、数据质量治理等完整能力。

核心判断标准：用户首次打开页面时，应先感知到“这是一个可浏览的社区 Live 数据库”，再进入表格列表；已登录和有编辑权限的用户仍能沿用现有收藏与控制台能力。

##### 范围内

- 首页首屏结构调整
  - 显示站点名称和一句数据库定位说明。
  - 显示一个搜索入口的 UI 壳，但第一阶段可以不接入真正的跨实体搜索。
  - 显示数据概览区域。
  - 显示最近 Live / 最新收录区域。
  - 保留进入全量列表的明确入口。
- 公共浏览能力保留
  - 匿名用户仍可查看公共首页。
  - 匿名用户仍可查看 Live 列表。
  - 匿名用户仍可打开 Live 详情。
  - 首屏加载不应依赖登录成功。
- 现有登录能力保留
  - 顶部登录入口保留。
  - 登录态恢复逻辑保留。
  - 登录后用户菜单保留。
  - 退出登录能力保留。
- 现有收藏能力保留
  - 登录用户可继续收藏 / 取消收藏 Live。
  - “我的收藏”入口保留。
  - 匿名用户点击收藏仍触发登录引导。
  - 收藏页已有缓存、预读、会话对账逻辑不应回退。
- 现有控制台能力保留
  - `editor+` 用户继续看到控制台入口。
  - 低权限用户不能进入控制台。
  - 控制台写入成功后仍能清理列表缓存并刷新相关数据。
- 首页轻量数据概览
  - 可展示已能从现有分页响应获得的 Live 总数。
  - 乐队数、歌曲数、场地数、待补全数可以显示为“后续补充”或暂不展示，避免前端伪造统计。
  - 最近更新时间可以先不做精确值，除非后端已有可靠字段。
- 最近 Live 区域
  - 优先复用 `GET /api/lives?page=1&page_size=15|20`。
  - 最近 Live 可直接取现有列表第一页。
  - 点击条目进入现有 Live 独立详情视图。
- 导航与页面层级
  - 从当前单层 tab 结构，调整为“首页 / 演出资料 / 乐队浏览 / 联系我们 / 控制台”或等价结构。
  - “演出资料”承载现有表格 / 卡片列表及收藏范围切换。
  - “首页”承载新的数据库入口和摘要信息。

##### 范围外

- 不新增公开注册。
- 不新增关注乐队 / 场地 / 歌曲能力。
- 不新增真正的全局搜索 API。
- 不新增聚合搜索结果页。
- 不新增乐队、场地、歌曲实体详情页。
- 不新增数据质量计算 API。
- 不新增最近编辑流。
- 不新增审核、回滚、举报、讨论能力。
- 不新增推荐算法。
- 不修改数据库 schema。
- 不重写控制台录入流程。
- 不把所有统计指标都做成真实实时数据。

##### 阶段 1 子目标

1. 首页入口成型
   - 新增“首页”视图。
   - 默认 tab / 默认视图从“演出资料”调整为“首页”。
   - 首页首屏包含搜索壳、定位说明、Live 总量和最近 Live。

2. 列表能力迁移为二级入口
   - 现有 Live 表格移入“演出资料”视图。
   - 分页、独立详情、批量收藏、预读行为保持不变。
   - 从首页可以一键进入演出资料。

3. 登录与收藏入口整合
   - 未登录首页展示轻量登录引导。
   - 登录后首页展示“我的收藏”摘要入口。
   - 收藏完整列表仍由“我的收藏”视图承载。

4. `editor+` 入口整合
   - editor 及以上用户在首页看到“进入控制台”或“贡献入口”。
   - 普通 viewer 不看到控制台入口。
   - 控制台本身仍复用现有实现。

5. 空状态和错误状态补齐
   - 首页最近 Live 加载中有明确状态。
   - Live 列表为空时有明确状态。
   - 加载失败时给出重试或返回列表的路径。

##### 第一阶段不建议新增的后端能力

阶段 1 原则上应尽量复用现有 API：

- `GET /api/lives`
- `GET /api/lives/{live_id}`
- `GET /api/me/favorites/lives`
- 现有 auth 和 console API

如果实现首页概览时确实需要新增后端接口，应只考虑一个小范围只读接口，例如 `GET /api/home/summary`，并限制在以下字段：

- `live_count`
- `recent_lives`

乐队数、歌曲数、场地数、待补全数可以留到后续阶段，避免阶段 1 过早牵扯统计口径和性能问题。

##### UI 文案边界

阶段 1 首页文案应克制，避免做成营销页。

建议表达：

- “浏览和整理 BanG Dream! 相关 Live 资料”
- “查看 Live、setlist、出演成员与来源链接”
- “登录后可收藏 Live；editor 可补充资料”

避免表达：

- 夸大社区规模。
- 声称已有完整审核或可信度体系。
- 声称支持还未实现的全局搜索、关注、推荐。

##### 验收清单

- 匿名访问时默认进入首页，而不是直接看到单一表格。
- 首页能展示最近 Live，并可打开详情。
- 首页能进入演出资料列表。
- Live 列表分页行为保持不变。
- 登录按钮、登录弹窗和登录态恢复保持可用。
- 登录后收藏按钮、我的收藏页、批量收藏保持可用。
- editor+ 用户仍可进入控制台。
- viewer 和匿名用户不能进入控制台。
- 页面在无数据、加载中、请求失败时有可理解的状态。
- 不出现宣传了但无法点击或无法完成的核心功能。

##### 验证要求

阶段 1 会修改 `frontend/src/**`，属于业务代码变更，完成后必须从仓库根目录运行：

```powershell
python scripts/run_checks.py functional
```

如果阶段 1 最终只产生需求文档或设计文档变更，没有修改业务代码，则只需运行：

```powershell
git diff --check
```

### 阶段 1.5：站点基础支持与可信度说明

目标：补齐社区数据库常见的基础站点入口，让用户知道如何联系维护者、报告问题、理解数据来源和版权边界。

交付：

- 全站底部或等价区域展示基础入口。
- 增加关于本站、数据来源 / 版权说明、隐私说明的静态内容入口。
- 增加联系作者 / 维护者入口。
- 增加报告 bug 的外部入口，优先链接到 GitHub Issues 或等价渠道。
- 增加报告资料错误的入口壳，先可链接到外部反馈渠道，不要求站内闭环。
- 明确后续可选 SDK / 服务的接入候选和边界。

验收：

- 匿名用户能从首页找到联系、反馈、版权 / 数据来源说明。
- 用户能区分“应用 bug”和“资料错误”的反馈路径。
- 站点不声称已有审核、评论、举报或站内工单能力。
- 新入口不会阻塞公共浏览、登录、收藏和控制台。

#### 阶段 1.5 详细范围界定

阶段 1.5 是站点可信度和基础支持能力的最小可用版本，重点是入口、说明和外部渠道整合，不新增复杂社区治理系统。

##### 范围内

- 新增全站页脚或等价支持入口区。
- 新增静态“关于本站”内容。
- 新增静态“数据来源与版权说明”内容。
- 新增静态“隐私说明”内容，覆盖登录、收藏、反馈、错误监控、访问统计的基本数据边界。
- 新增“联系维护者”入口。
- 新增“报告 bug”入口，优先外链 GitHub Issues 或预留配置化外链。
- 新增“报告资料错误”入口壳，优先从 Live 详情或页脚进入外部反馈渠道。
- 在需求或设计中记录 Sentry、Formspree、giscus、Plausible / Umami / PostHog、Turnstile、Meilisearch / Algolia 等候选工具的适用边界。

##### 范围外

- 不自建站内工单系统。
- 不新增评论区或讨论区。
- 不新增举报审核流。
- 不新增编辑历史、回滚或审核后台。
- 不开放匿名直接修改资料。
- 不强制接入第三方分析、错误监控或反馈表单 SDK；接入前需单独确认隐私和部署配置。
- 不新增数据库 schema，除非后续决定把反馈、资料错误或审计记录站内化。

##### 验证要求

如果只新增静态文档、页脚链接或外部入口配置，可用：

```powershell
git diff --check
```

如果修改 `frontend/src/**` 或接入 SDK，则必须从仓库根目录运行：

```powershell
python scripts/run_checks.py functional
```

### 阶段 2：公共搜索与浏览

目标：让数据库真正可查。

交付：

- 增加全局搜索 API 或聚合搜索 API。
- 支持按 Live 名、乐队、场地、歌曲搜索。
- 增加按乐队、场地、类型、年份浏览入口。
- 首页搜索结果能跳转到 Live 详情或列表筛选页。

验收：

- 用户能从首页搜索到一场 Live。
- 用户能从乐队或场地入口浏览相关 Live。
- 空结果、加载、错误状态完整。

### 阶段 3：登录后个人首页

目标：让登录用户有持续回访理由。

交付：

- 首页登录后展示我的收藏摘要。
- 增加最近查看记录。
- 增加收藏 Live 最近更新区域。
- 收藏页从单独 tab 升级为个人区的一部分。

验收：

- 登录后首页内容明显不同于匿名首页。
- 收藏不只是列表页功能，而是首页第一屏可见。
- 退出登录后个人区隐藏，公共内容仍可浏览。

### 阶段 4：贡献工作台

目标：把 `editor+` 控制台从录入页面升级为数据库维护工作台。

交付：

- 首页对 `editor+` 展示贡献入口。
- 增加待补全条目列表。
- 控制台入口按任务拆分：新增 Live、追加 setlist、补歌曲、补场地。
- 记录我的最近提交或最近编辑。

验收：

- editor 登录后能从首页直接找到最需要维护的数据。
- 录入动作完成后，首页最近新增或待补全状态能刷新。
- 普通 viewer 看不到 editor+ 入口。

### 阶段 5：数据可信度与社区治理

目标：让社区数据库更可信。

交付：

- Live 详情展示资料完整度或缺失状态。
- 增加最近编辑流。
- 增加来源 URL、备注、修改记录展示。
- 预留审核、回滚、举报、讨论能力。

验收：

- 用户能判断一条 Live 是否完整可信。
- 维护者能发现最近被改了什么。
- 错误数据有明确修正路径。

### 阶段 6：个性化与社区活跃

目标：从数据库进一步演进为社区。

交付：

- 关注乐队 / 场地 / 歌曲。
- 基于收藏和关注的新增提醒。
- 活跃贡献者、最近贡献、贡献统计。
- 可选：用户公开资料页、贡献榜、评论或讨论。

验收：

- 登录用户首页能看到和自己有关的更新。
- 社区贡献行为可见但不过度游戏化。
- 数据库浏览、个人收藏、社区维护形成闭环。

## 推荐优先级

优先完成阶段 1、阶段 1.5 和阶段 2。阶段 1 决定首页定位，阶段 1.5 补齐社区站点的基础可信度和反馈路径，阶段 2 决定数据库是否真正可查。阶段 3 再增强登录价值；阶段 4 以后再把现有控制台升级为社区维护体系。
