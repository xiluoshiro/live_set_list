# 公共 Live 与收藏 Live 统计需求

## 文档定位

本文定义 LiveSetList 公共统计功能的产品目标、统计范围、指标口径、页面形态、阶段拆分和验收标准。

- 本文是产品需求，不定义具体路由、响应 JSON、SQL 或前端组件拆分。
- 具体接口、查询复用、缓存和页面实现应在进入开发前另写设计文档。
- 首页、公共浏览与个人工作台的总体定位仍由 [社区 Live 数据库首页与个人工作台需求](homepage-community-database.md) 维护。

当前状态：`S1 已实现基础版`。

## 背景

LiveSetList 已经能够按关键词、年份、Live 类型和乐队浏览 Live，也已经具备服务端收藏。当前首页只有 Live、乐队、歌曲、场地等基础数量，用户仍难以回答以下问题：

1. 某一年收录了多少场 Live，主要是什么类型？
2. 某一年哪些歌曲出现最多？
3. 某支乐队最近常唱什么，哪些歌曲已经很久没有在已收录 Live 中出现？
4. 一首歌第一次和最近一次在资料库中出现是什么时候？
5. 全部 Live 与我收藏的 Live，在曲目、乐队、年份和场地上有什么差异？

统计功能的目标不是制作运营后台，也不是用小样本制造“全网热度榜”，而是把已有 Live 和 setlist 数据组织成新的公共发现入口。

## 产品结论

### 1. 统计以公共资料为主

- 匿名用户默认查看“全部 Live”统计。
- 统计结果必须能继续进入相关 Live、乐队或筛选结果，不能停留在孤立图表。
- 页面文案统一使用“本站已收录”“在已收录 Live 中出现”等口径，不把资料库样本描述成整个企划或现实演出活动的完整统计。

### 2. 只保留一个范围切换

统计页顶部提供：

- `全部 Live`
- `收藏 Live`

未登录用户选择“收藏 Live”时进入现有登录流程。登录后，“收藏 Live”表示当前用户收藏 Live 与其他筛选条件的交集。

不增加“热门收藏”“全站用户收藏”等第三种范围，也不公开其他用户的收藏统计。

### 3. 全部与收藏必须使用同一套统计能力

接口和统计引擎应是通用的。两种范围只改变候选 Live 集合，之后的年份、乐队、Live 类型、歌曲和场地统计使用相同口径。

概念顺序：

```text
选择范围（全部 / 当前用户收藏）
  -> 应用 Live 条件（年份 / 乐队 / Live 类型）
  -> 得到候选 Live 集合
  -> 对候选集合聚合 Live、setlist、歌曲、场地统计
```

“收藏 Live”不能单独复制一套查询和响应结构；否则同一指标容易在两个范围中产生定义漂移。

## 外部站点参考

### setlist.fm

[艺人 Tour Statistics](https://www.setlist.fm/stats/bruce-springsteen-2bd6dcce.html) 将演唱总次数、年份和歌曲排行组织在同一统计入口，并明确说明同一 setlist 中重复演唱也会计入表演次数。

[单曲 Song Statistics](https://www.setlist.fm/stats/songs/bruce-springsteen-2bd6dcce.html?songid=43d68fbb) 展示：

- 总演唱次数。
- 首次演唱日期和场地。
- 最近演唱日期和场地。
- 逐年演唱次数。
- 其他艺人的翻唱次数。

[Average Setlist](https://www.setlist.fm/stats/average-setlist/thirty-seconds-to-mars-5bd6e3e8.html?tour=63d7eeef) 进一步展示平均 setlist、常见开场曲、主段压轴曲、整场压轴曲和安可段数量。

适合 LiveSetList 借鉴：按年份的歌曲次数、首次/最近出现、开场/压轴/安可位置，以及统计结果进入具体歌曲或 Live 的路径。

### OARSA

[OARSA Song Statistics](https://www.oarsa.org/features/top10.php) 同时展示：

- 最常演唱与较少演唱歌曲。
- 最常作为开场、压轴和安可的歌曲。
- 从首次出现后计算的演唱覆盖率。
- 最长未演唱列表。

适合 LiveSetList 借鉴：不要只做“最多”，还要提供稀有曲、久未出现和 setlist 位置等反向发现入口。

### Metlists

[Metlists Statistics](https://www.metlists.com/statistics.htm) 将年度演出数量、逐年歌曲次数、首次/最近演唱、从未演唱和“多久没唱”集中到歌曲档案中。

适合 LiveSetList 借鉴：把“某年最常唱”“最近一次”“长期未出现”“重新出现”组织成歌曲生命周期，而不是彼此无关的榜单。

### Last.fm

[Last.fm Listening Reports](https://www.last.fm/user/LastfmSupport/listening-report/year) 使用周、月、年时间范围切换，结合总量、Top Track、月份趋势和与上一周期比较。

适合 LiveSetList 借鉴的是时间范围切换和摘要层级；收听时长、连续收听、用户排行榜不适用于当前 Live 数据模型。

## 统一筛选模型

### 范围

| 条件 | 值 | 说明 |
|---|---|---|
| Live 范围 | `all / favorites` | 默认 `all`；`favorites` 要求当前登录用户 |

### 第一阶段筛选条件

| 条件 | 说明 |
|---|---|
| 年份 | 只显示数据库中实际存在的 Live 年份 |
| 乐队 | 使用与演出资料列表一致的 Live—乐队归属规则 |
| Live 类型 | 使用当前稳定 code 与中文标签 |

筛选条件按 AND 组合。切换“全部 Live / 收藏 Live”时保留年份、乐队和类型选择，便于直接比较两个范围。

歌曲、场地可以作为统计结果的下钻条件，第一阶段不要求放入顶部筛选栏。

## 统计口径

### Live 次数与歌曲出现次数必须分开

一首歌可能在同一场 Live 中出现多次，因此至少区分：

- `出现 Live 数`：包含该歌曲的不同 Live 数量。
- `setlist 条目数`：该歌曲在 setlist 行中出现的总次数。

歌曲排行默认按“出现 Live 数”排序；setlist 条目数作为辅助值。任何页面都不能只显示含义不明的“演唱次数”。

### 年份来自演出日期

“2025 年统计”表示 `live_date` 位于 2025 年的候选 Live，不表示 2025 年录入、编辑或发布的数据。

### 乐队归属保持一致

- Live 已有 setlist 时，从 `live_setlist.band_member` 得到参与乐队。
- Live 完全没有 setlist 时，才允许回退 `live_attrs.default_band_ids`。
- 统计页、演出资料筛选和乐队浏览必须共享这一规则。

乐队筛选还需要区分 Live 级与歌曲条目级语义：

- Live 级统计先选出该乐队参与的 Live。
- 歌曲统计只计算 `band_member` 中包含该乐队的 setlist 行，不能把同一场多乐队 Live 中其他乐队演唱的歌曲一并计入。
- `song_list.band_id` 表示歌曲目录归属，`live_setlist.band_member` 表示该次 Live 条目的实际出演关系；按乐队统计现场歌曲时以后者为准。
- 一条 setlist 行若明确包含多个乐队，全球歌曲次数只计一次，按乐队拆分时可分别计入对应乐队；界面需要说明分组合计可能大于全球总数。

### 当前资料覆盖不等于现实全量

所有排行和趋势必须附带候选 Live 数与覆盖日期。例如：

> 基于本站已收录的 23 场 2025 年 Live。

年份缺失或数据偏向特定乐队时，不得把统计描述成整个企划的活动趋势。

## 第一阶段核心功能

### 1. 概览

展示当前范围和筛选下的：

- Live 数。
- 有 setlist 的 Live 数与覆盖率。
- 参与乐队数。
- 出现歌曲数。
- 场地数。
- 最早和最晚 Live 日期。

首页仍只保留轻量总数和统计页入口，不把完整图表塞入首页。

### 2. 按年份的 Live 分布

展示每年收录 Live 数，可进一步按 Live 类型分段。

呈现形式：

- 桌面：年份柱状图，可选类型堆叠。
- 移动端：横向条形列表。
- 点击某一年：应用年份筛选并刷新同页其他统计。

年份不连续时明确显示空档，不使用会暗示连续活动趋势的平滑折线。

### 3. 某年演唱最多的歌曲

用户选择年份后展示：

- 歌曲名。
- 所属乐队。
- 出现 Live 数。
- setlist 条目数。
- 在候选 Live 中的覆盖率。
- 最近一次出现的 Live 日期。

默认 Top 10，支持查看全部。点击歌曲后展示贡献该统计的 Live 列表。

如果同时选择了乐队，只统计该乐队实际参与演唱的 setlist 行，不统计候选 Live 中其他乐队的歌曲。

该功能是第一阶段最高优先级的歌曲统计。

### 4. 歌曲首次与最近出现

每首已在 setlist 出现的歌曲可计算：

- 首次出现日期和 Live。
- 最近出现日期和 Live。
- 总出现 Live 数。
- 分年份出现次数。

第一阶段可先在统计结果抽屉或详情区域展示，不要求同时建设完整歌曲实体页。

### 5. 久未演唱

“好久没唱”不能简单用当前日期减去歌曲最近日期。资料库可能没有及时收录现实中的最新演出，而且不同乐队的演出频率不同。

推荐同时展示：

- `最后出现日期`。
- `距该乐队最新已收录 Live 的天数`。
- `此后该乐队又有多少场已收录 Live 未出现该歌曲`。
- `历史出现 Live 数`。

第一阶段规则：

- 选择具体乐队后才展示“久未演唱”，避免把不同活跃周期的乐队直接混排。
- 默认排除只出现过 1 次的歌曲，用户可显式选择包含一次性曲目。
- 全部 Live 范围文案使用“在本站收录中久未出现”。
- 收藏 Live 范围文案使用“在我的收藏 Live 中久未出现”，不得暗示现实演出情况。

### 6. 从未出现的歌曲

展示已存在于 `song_list`、但没有任何候选 setlist 行的歌曲。

该指标的含义是“未在当前统计范围内出现”：

- 全部 Live：未在本站已收录 setlist 中出现。
- 收藏 Live：未在我的收藏 Live 中出现。

不能称为“从未现场演唱”，因为资料库并不保证覆盖现实中的全部 Live。

## 第二阶段候选方向

### 1. 回归歌曲

寻找同一首歌相邻两次出现之间的最长间隔，展示：

- 上一次出现日期与 Live。
- 回归日期与 Live。
- 间隔天数。
- 中间经过的同乐队 Live 数。

可形成“时隔 N 天重新出现”的发现卡片。

### 2. 新出现歌曲

按年份展示第一次进入本站已收录 setlist 的歌曲。文案必须使用“本站首次收录出现”，不能直接声称“Live 首披露”或“歌曲首演”。

### 3. 常驻曲与稀有曲

借鉴 OARSA 的覆盖率，但分母必须清楚：

```text
歌曲覆盖率 = 从该歌曲首次出现起，该歌曲所属乐队的 Live 中包含该歌曲的场数
             / 同期该乐队已收录且有 setlist 的 Live 数
```

需要设置最小样本门槛，例如同期至少 5 场 Live，避免两场中出现一次就显示为 50% 的强结论。

### 4. 开场、压轴与安可

基于 `absolute_order` 和 `segment_type` 统计：

- 最常作为主段开场的歌曲。
- 最常作为主段压轴的歌曲。
- 最常作为整场最后一曲的歌曲。
- 最常出现在安可段的歌曲。
- 各 Live 的安可曲数分布。

进入开发前必须先确认 `M / EN / OP / WEN / RH` 等现有段落值的业务含义，并明确短版、返场和特殊段落如何参与排序。

### 5. Setlist 长度与结构

- 平均、中位、最短和最长 setlist 条目数。
- 不同 Live 类型的 setlist 长度比较。
- 每年出现的不同歌曲数。
- 翻唱、短版和其他成员参与条目数。

平均值必须和中位数同时展示，避免少量超长 setlist 拉高结论。

### 6. Setlist 相似度

按歌曲集合计算两场 Live 的重合率，可用于：

- 同一乐队相邻两场 Live 的曲目变化。
- 同一巡演内 setlist 稳定度。
- 与某场收藏 Live 最相似的其他 Live。

当前没有结构化巡演字段，因此第一版只能按乐队和日期比较；巡演统计应等待独立字段或实体设计。

### 7. 歌曲组合

- 最常同场出现的歌曲组合。
- 常见连续曲序。
- 从未同场出现但各自频率较高的歌曲组合。

该方向计算和解释成本较高，放在数据量扩大后的后续阶段。

## 页面形态

### 导航

公共导航增加“数据统计”，位置建议在“演出资料”与“乐队浏览”之间；移动端侧边栏同步增加入口。

### 页面结构

1. `PageTitle`：数据统计 + 资料覆盖口径说明。
2. 范围切换：全部 Live / 收藏 Live。
3. 筛选栏：年份、乐队、Live 类型、清除条件。
4. 概览卡：Live、歌曲、乐队、场地、setlist 覆盖率。
5. Live 分布：按年份和类型。
6. 歌曲洞察：年度最多、首次/最近、久未出现、从未出现。
7. 后续增强：回归歌曲、开场/压轴/安可、setlist 结构。

### 交互要求

- 切换范围或筛选后，所有统计区域使用同一候选 Live 集合刷新。
- 统计条目能够下钻到贡献该数字的 Live 列表。
- 筛选状态可写入 URL，支持刷新、前进后退和分享。
- 图表必须同时提供精确数字；不能只依赖颜色或悬浮提示。
- 移动端优先使用条形列表和表格卡片，不强制横向滚动查看图表。

### 状态要求

- 收藏范围未登录：显示登录入口。
- 收藏为空：说明尚无收藏，并提供返回全部 Live 的操作。
- 某筛选无结果：保留筛选栏并提供清除条件。
- setlist 样本不足：隐藏不可靠排行并明确说明样本门槛。
- 单项统计失败：其他已成功区域仍可展示，并提供局部重试。

## 通用接口能力要求

后续接口设计应满足以下产品契约：

### 输入

- 范围：全部 Live / 当前用户收藏 Live。
- Live 条件：年份、乐队、Live 类型。
- 统计模块：概览、时间分布、歌曲排行、歌曲活跃度、setlist 结构等。
- 排序、数量上限和分页。

收藏范围必须通过当前 session 确定用户，不能接受任意 `user_id` 查询他人收藏。

### 输出

每个统计响应至少需要表达：

- 实际使用的范围和筛选条件。
- 候选 Live 数。
- 覆盖日期范围。
- 指标值及其明确单位。
- 排名或时间序列。
- 可用于下钻的 `live_id / song_id / band_id / venue_id`。
- 统计计算时间；不得把它写成资料“最近更新时间”。

### 复用原则

- 全部和收藏只替换候选 Live 集合。
- 各模块共享 Live—乐队归属、年份、Live 类型和 setlist 口径。
- 概览接口保持轻量；歌曲排行和高级统计不应被首页每次加载强制请求。
- 第一阶段允许实时查询；数据量明显增长后再评估缓存、物化视图或预计算。

## 当前数据能力与限制

### 不新增字段即可实现

- Live 按年份、类型、乐队、场地统计。
- 歌曲出现 Live 数和 setlist 条目数。
- 某年最常出现歌曲。
- 歌曲首次、最近出现及逐年次数。
- 久未出现、回归间隔和从未出现。
- setlist 长度、开场/压轴/安可候选统计。
- 全部 Live / 收藏 Live 使用同一套聚合。

### 当前不能可靠实现

- 最近录入、最近编辑和资料增长趋势：核心资料表没有可靠的 `created_at / updated_at`。
- 现实中的歌曲首演：缺少完整历史和官方首演字段。
- 基于发行时间的“发行后多久首演”：缺少歌曲发行日期。
- 巡演统计：缺少结构化 tour 实体或字段。
- 城市、国家和地图统计：场地目前只有名称，没有结构化地理信息。
- 公开热度榜：当前收藏用户样本过小，且收藏只代表站内用户行为。

## 分阶段目标

### 阶段 S1：通用范围与年度歌曲统计

交付：

- 新增公共“数据统计”入口。
- 支持全部 Live / 收藏 Live 范围切换。
- 支持年份、乐队和 Live 类型筛选。
- 展示概览、年度 Live 分布和 Live 类型分布。
- 展示某年演唱最多歌曲。
- 展示歌曲首次、最近出现和逐年次数。
- 展示选择乐队后的久未出现歌曲。
- 所有统计支持下钻到相关 Live。

### 阶段 S2：歌曲生命周期与 setlist 结构

交付：

- 从未出现歌曲。
- 回归歌曲和最长间隔。
- 新出现歌曲。
- 常驻曲与稀有曲。
- 开场、主段压轴、整场压轴与安可统计。
- setlist 长度与结构统计。

### 阶段 S3：高级关系发现

交付候选：

- Setlist 相似度。
- 常见歌曲组合与连续曲序。
- 巡演统计，但依赖巡演实体设计。
- 收藏范围与全部范围的并排比较。

## S1 验收标准

- 匿名用户可以查看全部 Live 统计。
- 未登录选择收藏范围时进入现有登录流程。
- 登录用户切换全部 / 收藏后，年份、乐队和类型条件保持不变。
- 同一指标在全部和收藏范围使用相同字段、排序和单位。
- 用户能查看某年出现 Live 数最多的歌曲，并进入贡献该统计的 Live。
- 选择乐队后能查看歌曲最后出现日期和此后缺席的已收录 Live 数。
- 页面明确区分“本站收录统计”和现实全量演出结论。
- 页面不把 `MAX(live_date)` 标为“最近更新”。
- 无结果、收藏为空、样本不足和局部失败均有明确状态。
- 业务代码落地后按仓库约定运行 `python scripts/run_checks.py functional`，并做浏览器级页面验证。

## 非目标

- 不在 S1 建设运营后台或管理员监控看板。
- 不公开用户收藏排行榜。
- 不把收藏解释为用户亲自参加过的 Live。
- 不根据当前小样本生成推荐算法或预测下一场 setlist。
- 不为了统计功能引入公开注册、评论、讨论或贡献榜。
- 不在产品需求文档中提前锁死接口路由和数据库实现。
