## 2. 已确认范围

- 公共导航在“巡演资料”与“数据统计”之间新增“歌曲资料”。采用更宽的左列表、右详情布局；左侧每项代表歌曲组，右侧显示所选版本详情和所属歌曲组演奏次数，并提供版本切换；左侧不显示演奏次数。具体宽度、栏宽比例与其他展示细节后续讨论。
- 控制台歌曲功能拆成“新增歌曲”和“歌曲管理”两个独立页面入口，参照现有“新增演出／演出管理”的导航、表单、确认和保存流程；不继续把新增和修改混在同一页。
- 歌曲版本可同时包含整队和固定成员归属，使用乐队、成员或混合模式；未回填资料保持 pending。
- 乐队模式绑定一个或多个稳定 `band_id`，以乐队集合为固定基准，不额外关心各乐队阵容变化。限定三支乐队但不限定成员的版本使用此模式。
- 固定合唱阵容、独立编曲的版本与普通版属于同一个歌曲组；组内可保留具体版本、归属基准和专辑关联，不能因这些差异拆成互不关联的歌曲组。
- 成员模式在歌曲建立时指定固定成员基准，可跨乐队；建立后不随现场出演或乐队版本变化而改变。成员记录用于固定版本归属；现场翻唱仍只比较乐队交集，不比较成员集合是否相同，也不维护歌曲成员变化时间线。
- 未审核的旧资料允许 pending；乐队和成员关系同时非空时使用 mixed。当前批次之外的资料不强制补齐。
- 歌曲无发售日期；仅展示关联专辑。专辑发售日期只有未知（NULL）或完整年月日两种状态。
- Instrumental 仅作为专辑收录标识，关联并跳转到对应非 Instrumental 的 song_id，不创建新 song_id。
- 专辑手动维护页面链接 `album_url` 和有序封面数组 `cover_urls`；第一项为默认封面，前台支持切换。图片通过外链展示，规则见 5.4。
- 专辑不细分类型，只保留可选自由文本“发行标识”，如 `10th single`、`2nd album`、`best album`、`mini album`、`special disc`。
- 碟号和发行版统一记录为专辑子项名称，不再细分类别；曲序在子项内排列，不参与演出统计排序。
- 统计仅保留演奏次数，每条 `live_setlist` 记录一次。不另计演出场数、短版次数或返场次数。
- 短版仅在对应关联歌单条目后标注，例如“Live 1 · M1 · 短版”。
- 不加入歌曲创作人员、歌曲官方链接、歌词、时长、BPM 等扩展资料；专辑页面链接按 5.4 单独维护。
- 建立成员 ID，控制台入口暂置于乐队管理；首次按 8.1 的固定 67 人顺序编号，不再动态按 Live 或版本日期排序。
- 批量新增歌曲的既有归属推导，在框架搭建完成、进入数据回填阶段时处理，不在本阶段直接保留为最终规则。

## 3. 当前实现

| 对象 | 当前约定 |
| --- | --- |
| 歌曲组与版本 | song_groups 保存歌曲身份，song_list 保存版本；空版本名是默认项 |
| 历史歌单 | live_setlist.song_group_id 关联歌曲组；旧 song_id 只保留来源证据 |
| 专辑 | album_tracks 关联具体版本；album_sections 保存统一的碟号／发行版子项 |

| 次数 | 同组版本共享有效 setlist 次数和关联歌单；每条 setlist 计一次 |
| 历史出演 | 保留逐次出演资料，不从歌曲版本反写出演事实 |

## 4. 歌曲身份与翻唱基准

### 4.1 归属模式

| 模式 | 固定基准 | 现场比较 |
| --- | --- | --- |
| 乐队 | 一个或多个 `band_id` 的去重集合 | 任一实际出演成员所在的 setlist 乐队命中基准乐队，即不判为现场翻唱 |
| 混合 | 整队归属与固定成员乐队上下文的并集 | 按任一乐队交集判定 |
| 成员 | 建立时固定的成员 ID 及其对应乐队分组 | 取固定分组的 band_id，按任一交集匹配；不要求出演人员命中某个固定 member_id |

歌曲成员基准不是“发行阵容历史”。歌曲建立后不提供日常成员增减 / 阵容版本更新流程。录入错误的修正属于显式数据纠错，应有审计和影响提示，不伪装成阵容演进。

乐队更名或换员不改变乐队模式歌曲身份。成员姓名修正不改变 member_id，成员转团也不自动替换固定基准中的人。

迁移未完成且基准为空时，自动翻唱判定为“尚未确定”，不能当成“没有翻唱”。已有人工翻唱标记仍可展示。

### 4.2 存储建议：关系表保存，JSON 用于交换和展示

乐队模式建议新增 `song_bands(song_id, band_id, display_order)` 关系，以 `band_ids: [1, 2, 3]` 交换；至少一支、不能重复。集合顺序仅影响展示，不改变基准身份。旧 `song_list.band_id` 是当前实现事实，不能继续当成未来多乐队存储结构。迁移期可允许空集合，回填完成后收紧。

推荐新增稳定成员表与歌曲成员关联表，API 可以保留按乐队分组的 JSON 形状。原因是成员 ID 已成为正式实体，需要引用完整性、去重和关联查询。

概念关系（非最终 SQL）：

```text
members(member_id, display_name)
song_members(song_id, member_id, context_band_id, display_order)
```

- `song_members` 表达歌曲固定基准，`member_id` 外键指向成员。
- `context_band_id` 保存建立成员基准时的对应乐队，是翻唱判定所需数据；回填完成后必须明确，不能每次根据成员当前所在乐队重写。
- 推荐歌曲内按 member_id 去重；同一人参与多个乐队仍是一个人。多重分组如何展示可后续确定。
- 成员模式翻唱判定使用固定分组中的 band_id 集合；成员 ID 及其顺序用于版本身份与展示，不用于现场翻唱的集合相等比较。

API 示例可采用显式字段，避免 JSON object 的字符串 key 与数字 ID 混淆：

```json
{
  "owner_mode": "members",
  "member_groups": [
    {"band_id": 1, "member_ids": [101]},
    {"band_id": 2, "member_ids": [205, 206]}
  ]
}
```

若希望直接保存 `{band_id: [member_id]}`，PostgreSQL 应优先考虑 `jsonb`，而不是名字作为键的 JSON。它适合小型固定结构，但数组内成员 ID 的外键、重复和成员存在性需要额外校验，不能依赖 JSON 格式合法就保证业务合法；对象键顺序也不应承担显示顺序。参见 [PostgreSQL JSON 类型文档](https://www.postgresql.org/docs/current/datatype-json.html)。

### 4.3 已确认的现场翻唱判定

1. 读取该条 setlist 的歌曲组，再取 version_label 为空的默认版本。
2. 默认版本的整队归属和成员固定乐队上下文取并集，得到基准集合 B。
3. 从该条 setlist 的实际出演成员记录取得所属 band_id，得到现场集合 P；不取整场 Live 的乐队列表，也不把成员当前参加过的所有乐队展开为现场乐队。
4. 当 `P ∩ B` 非空时，不是现场翻唱；交集为空时，判为现场翻唱。不要求全部基准乐队到场，不要求成员 ID 一致；增加其他乐队、换员或缺席均不单独改变这一结果。
5. 不额外排除 guest / support 等实际出演成员：按已确认的“任一成员”规则，只要其 setlist 所属乐队命中就满足条件。
6. 基准尚未回填或实际出演资料不足时返回“尚未确定”，不能把数据缺失直接解释为翻唱或非翻唱。

例如基准为 A / B / C，现场只有 A 的一名成员，或 A 与 D 共同出演，均不是现场翻唱；现场只有 D 的成员才是现场翻唱。成员模式记录 A 下的成员甲，现场 A 下的成员乙出演，也满足乐队交集，不判为现场翻唱。

旧 `song_list.is_cover` 的人工歌曲属性与这里的现场判定分开处理；它不能作为覆盖上述交集规则的捷径。歌曲属性按审核表保存，现有兼容展示保留；这不改变本节已确认的计算规则。

## 5. 专辑及特殊版本

### 5.1 专辑资料

| 字段 | 规则 |
| --- | --- |
| 专辑 ID | 稳定引用标识，不按名称自动合并 |
| 名称 | 必填，允许不同专辑同名，候选使用日期与发行标识消歧 |
| 发行标识 | 可空自由文本，保留内部写法；不解析类型或数字，不自动编号 |
| 发售日期 | 可空 DATE；NULL 表示未知，否则必须是合法完整年月日，可为已公布的未来日期；不保存只有年或年月的精度 |
| 专辑页面链接 | `album_url`，可空的 HTTPS 页面地址；未补录时为 NULL |
| 封面链接 | `cover_urls`，有序 HTTPS 图片地址数组，默认空数组；第一项为默认封面，规则见 5.4 |

歌曲与专辑为多对多关系。没有专辑不等于歌曲未发行；不从关联专辑计算歌曲首发时间。游戏先发不需要虚构专辑，数字发行可以作为一条正常专辑资料。日期未知时显示“发售日期未知”，不补造月日。

### 5.2 专辑曲目与顺序

- 碟号和发行版使用同一种专辑子项，不进一步分类或拆成独立专辑。
- 关联到专辑子项与版本：`album_track → album_id + section_id + song_id`。收录记录可保存可选自由文本标识（如 Instrumental）；Instrumental 与对应非 Instrumental 曲目共用 song_id，点击进入该 song_id 的版本详情。
- `track_order` 用于同一专辑子项内的歌曲顺序，使用正整数并在子项内唯一；不知道官方曲号时仍可维护本站展示顺序，不冒称官方 Track No.。
- 歌曲详情的关联专辑不展示曲序；演出列表按 Live 时间及 setlist 顺序排列，与专辑曲序无关。
- 删除一条关联不删除歌曲、专辑或历史歌单；修改专辑资料应在全部引用处生效。
- 一首歌在同一专辑重复出现可用不同收录记录表达，不以 `(album_id, song_id)` 唯一约束禁止真实情况。

### 5.3 歌曲组与特殊版本

已确认：固定合唱阵容、独立编曲的版本归入同一歌曲组。以下“具体条目 / 版本”不等于另建独立歌曲组；歌曲组表达共同歌曲身份，版本表达特定演出基准及收录差异。

建议先判断“是否需要独立保存固定归属及专辑收录版本”，再决定是否建立独立歌曲条目。不要把每个发行后缀直接当成新歌曲，也不要把具有不同演出身份的版本挤到同一条记录。

| 情况 | 建议归类 |
| --- | --- |
| 同一歌曲在单曲、专辑、精选集重复收录 | 同一歌曲，多条专辑关联 |
| Instrumental / off vocal | 仅作为专辑收录标识，指向对应非 Instrumental 的 song_id；不新建歌曲版本或独立 song_id |
| 独立编曲或固定合唱阵容的特殊版 | 归入同一歌曲组，组内保留具体版本、固定归属与专辑关联，右侧可以切换版本 |
| 正式发行的限定 cover 版 | 独立歌曲条目 / 版本，保留翻唱属性与自身固定基准；不要改写原条目 |
| 单场临时嘉宾合唱、短版、返场重演 | 仍是一次 setlist 出演及备注，不自动创建歌曲版本 |

采用“歌曲组”把普通版与固定合唱、独立编曲等特殊版连接起来。实现上建议`song_list.id` 作为专辑关联的具体版本，历史歌单以 `song_group_id` 关联稳定歌曲组。版本名称采用可选自由文本，不扩展为复杂枚举。已有歌曲不按同名自动合组；分组需要资料确认。左列表按歌曲组展示，右侧提供组内版本切换，显示歌曲组的有效 setlist 数量；切换版本不改变次数和关联歌单。

Instrumental 只改变专辑收录记录的展示，不改变跳转目标和歌曲身份；在同一专辑中普通收录与 Instrumental 收录可以各占一行并共用 song_id。

“限定 3 bands 合唱版”需要区分：

- 固定成员组合：可以使用成员模式保存准确基准。
- 只限制三支乐队、允许各自成员变化：已确认使用乐队模式，保存三个 band_id，无需虚构乐队；同时包含整队和固定成员时使用混合归属。

多乐队和同组版本需要重新设计原 `(song_name, band_id)` 唯一规则；成员 / 乐队集合、版本判别字段与歌曲组共同参与身份设计，最终约束在实现设计中确定。专辑发行标识与曲目版本标识是不同语义，不能复用一个字段。

### 5.4 专辑页面与多封面

专辑保存两个业务字段：`album_url` 为来源页面地址，`cover_urls` 为有序图片地址数组。页面链接尚未补录时允许为空；没有封面时使用空数组。首期手动录入，浏览器直接加载外部图片。

数组第一项就是默认封面，不增加默认 ID 或下标。后台支持添加、移除、调整顺序和设为默认；设为默认将所选项移到第一位，并保持其他项的相对顺序。删除默认项后，新的第一项自动成为默认。

歌曲的收录专辑卡片显示默认封面；展开专辑详情可切换其他封面并访问专辑页面。只有一张时省略切换控件；没有图片时保留现有文字资料。浏览时的切换只影响当前显示，不修改后台顺序。

同一专辑的歌曲共用封面数组；不同专辑分别维护。不建立歌曲独立封面、封面名称或封面与碟号／发行版子项的绑定。

后台统一保存专辑资料与封面数组，沿用修订校验、确认差异和草稿保护。图片加载失败不影响资料读取、其他图片切换或来源链接，也不自动修改默认项。

数据校验、增量迁移、界面复用和验收范围见[专辑页面链接与多封面实现方案](../design/album-links-and-covers.md)。本期不包含上传、图床、服务端图片代理或来源页面自动解析。

## 6. 歌曲资料页与详情

### 6.1 列表

导航顺序：演出资料 → 巡演资料 → **歌曲资料** → 数据统计 → 乐队浏览 → 联系我们。

- 建议地址 `/songs`；匿名可用，登录不是浏览前提。
- 已确认：左侧每项是歌曲组；点击后在右侧显示组内所选版本详情，右侧提供版本切换并显示所属歌曲组演奏次数。左侧不显示次数，同组版本共用次数和关联歌单。归属摘要、翻唱标记等列表字段是否展示后续确定。
- 搜索词匹配歌名；归属筛选明确区分乐队模式和成员模式，不把成员所在乐队当成歌曲所属乐队。
- 建议保留关键词、乐队和排序控件；乐队筛选对乐队模式按集合中包含所选 band_id 匹配；迁移完成前成员模式的筛选待正式身份规则确定，不伪造完整候选。
- 左侧按组分页，排序后续确定；不沿用旧方案直接按某个 song_id 的次数排序，若使用次数排序需明确聚合口径。
- 数据分页查询，每页数量后续确定。
- 复用项目主题、导航与筛选控件。主体采用更宽的横向内容区，为左侧列表和右侧详情提供空间；具体最大宽度、两栏比例、滚动方式和窄屏适配后续讨论。

### 6.2 详情与返回

建议选中歌曲时使用 `/songs/{song_id}`，在同一左列表、右详情框架内呈现，支持直接定位。打开 song_id 时定位对应歌曲组和版本；切换版本更新归属和专辑，次数与关联歌单仍属于同一歌曲组。详情内容顺序建议为：歌曲组名称与版本切换 → 固定归属 → 歌曲组演奏次数 → 关联歌单 → 关联专辑。最早 / 最近收录演出可从列表首尾获得，不必另占多张统计卡。

- 关联歌单按每条 setlist 展示，如“2026-01-01 · Live 1 · M1”，短版追加“短版”；同一 Live 中两次出现也展示两条。
- 单条可展开当前出演、备注，并进入对应 Live；可支持按年份筛选。
- 专辑展示默认封面、名称、发行标识、发售日期；展开详情支持多封面切换和专辑页面链接。歌曲的收录专辑摘要不显示歌曲发售日期、碟号或曲序。
- 搜索、Live 逐曲展开、统计和巡演歌曲引用均可进入同一详情，并保留目标版本。专辑中的 Instrumental 点击后进入其关联的非 Instrumental 版本。
- 保留现有 Live 行点击展开行为，在展开区加资料入口，避免按钮内嵌套链接。
- 返回时恢复来源筛选和分页；从 Live 来时保留原展开上下文。
- 支持直接打开、刷新、浏览器前进后退；请求竞态不得覆盖当前歌曲。
- 无演奏或无专辑时显示短空状态，不把无专辑解释为未发行。

迁移过程中不凭空补造成员模式基准、专辑与特殊版本。单条 setlist 的实际成员只在“本次出演”下展示，不能误标为歌曲固定成员。

## 7. 演奏次数与 Live 数据有效性

### 7.1 唯一统计粒度

`performance_count = 所属歌曲组 song_group_id 的有效 live_setlist 记录数`。同组各版本显示相同次数。查询可以直接数 setlist 行；连接成员、乐队等一对多表时先按 setlist_id 去重或独立聚合，避免 JOIN 放大。

- 一条记录一次，不因多人或多乐队合作加倍。
- 两条记录两次，无需另设“同场重演”特例。
- 短版同样一次，不单独统计，只标记对应条目。
- 不显示或维护歌曲演出场数指标。
- 专辑收录次数、专辑内曲序不影响演奏次数。
- 现有全站统计字段是否同步删除属于兼容处理，不因新页面收敛指标就未经评估破坏其他调用方。

### 7.2 未来、取消与延期

已确认：未来 Live 和取消 Live 不应有歌单；若存在，视为错误数据，不能作为正常关系显示并计入统计。歌单只在当日 / 已完成状态录入；已有歌单后不允许修改演出日期，不提供先移动日期再隐藏歌单的正常流程。

延期调整必须指定明确的新日期，保持同一 live_id，记录旧安排；不支持以旧日期作为“延期未定”的有效新安排。是否曾改期不影响计数，按当前有效日期阶段和取消状态判断。

写入加固要求与实现建议：

1. 歌单新增、替换、追加均校验目标 Live 不是未来或取消。
2. 已有歌单时，拒绝修改 live_date，包括改为另一个过去日期；拒绝改为取消，避免产生违反上述不变量的状态。日期锁定应覆盖普通资料修改和正式改期入口，不能仅在 UI 隐藏。
3. 延期操作要求明确的新日期；同日仅改开演时刻等是否属于延期的细节，在 Live 状态实现设计中处理，不扩展为禁止编辑全部演出资料。
4. 建议以事务及同一 Live 锁协调歌单写入与日期 / 状态修改，防止并发绕过。
5. 迁移前只读审计历史异常，单独报告；不自动删改歌单。读统计防御性排除明确错误记录。
6. 日期校验建议复用演出 / 场馆时区的现有计算入口，避免访问者时区影响写入结果；与 live_status.py 的具体对接在实现设计中明确。

当前 console_write.py 对 schedule 字段变更进行分类并写入改期历史；本需求还要求核对并补齐“已有歌单锁定日期”和“延期必须新日期”的全入口校验，不能把目标规则写成已实现能力。旧有未定期延期若存在，应作为历史数据问题整理，而非继续开放为常规流程。

### 8.3 管理交互

- 控制台“歌曲”导航分组同时提供“新增歌曲”和“歌曲管理”，对应演出分组的新增 / 管理结构。此处为管理工具布局，不套用公共歌曲资料页的左右分栏要求。
- 新增页直接展示空白新增表单；支持新建歌曲组及首个版本，或选择已有歌曲组新增版本。选择已有组仅用于确定新版本归属，不进入修改已有歌曲的模式。
- 管理页先查询、筛选、分页选择已有具体版本，选中并加载后才显示编辑区；候选必须能区分歌曲组、版本与固定归属。未选中时不展示可提交的编辑表单。
- 新增使用“清空数据／提交插入”，管理使用“恢复原值／保存修改”；新增确认展示拟插入资料，修改确认展示差异，复用演出页确认方式。无修改时不提交保存。
- 新增与管理的选中 ID、原始快照、草稿与提交状态隔离；管理中有未保存修改时，切换版本或离开页面沿用演出管理的放弃修改确认，取消后保留原草稿。
- 新增成功留在新增页，沿用演出新增的“提交后清空”选择；不自动转入编辑刚建歌曲。管理成功保留当前选中版本并更新原值和 revision，失败保留草稿。
- 新增记录与修改记录分开显示，操作记录中的编辑入口打开歌曲管理并定位具体 song_id；不能因为分页刷新而丢失选中歌曲的完整名称。
- 保留歌曲查询、分页选中、草稿、差异确认与 editor+ / CSRF / 审计。
- 候选显示歌名和归属摘要；已选项移出候选页仍保留完整标签。
- 新建时选择固定基准；已建歌曲不提供阵容时间线编辑。数据纠错与普通字段编辑区分。
- 专辑管理维护最小资料，专辑曲目列表维护顺序；歌曲页关联专辑时不要求碟号。
- 名称、关系和专辑排序冲突由服务端校验；一次关系保存原子完成。
- 歌曲 / 专辑修改使相应详情缓存失效；歌单变化更新相关演奏次数。

## 9. 接口与代码适配建议

建议能力（不是已存在 API）：

| 能力 | 建议入口 | 说明 |
| --- | --- | --- |
| 歌曲组列表 | `GET /api/song-groups` | 按组搜索、过滤、分页、排序；左侧不显示演奏次数 |
| 歌曲组与版本 | `GET /api/song-groups/{group_id}` | 返回组内版本及可定位的 song_id，供右侧切换 |
| 歌曲详情 | `GET /api/songs/{song_id}` | 固定归属、关联专辑、演奏次数；不返回歌曲发售日期 |
| 关联歌单 | `GET /api/songs/{song_id}/performances` | 每条 setlist 一项，返回 live_id、setlist_id、曲序、短版、实际出演与分页 |
| 歌曲维护 | 扩展现有 Console songs 接口 | 分阶段空值、固定基准、身份消歧和关系保存 |
| 成员管理 | Console 乐队管理下新增候选 / 维护能力 | 明确 ID 与名字、历史出演映射 |
| 专辑维护 | 新增 Console albums 接口 | 发行标识自由文本，专辑内曲序 |

调用链：用户进入歌曲资料 → `App.tsx` 导航 → `api.ts` → 歌曲只读 router → 歌曲及 setlist 聚合 → 列表 / 详情。Console 写入经现有角色、会话、CSRF 校验后，在数据库事务中保存并审计。

需同步检查：`schemas/console.py`、`schemas/catalog.py`、`routers/console_read.py`、`routers/console_write.py`、`routers/catalog.py`、`routers/lives.py`、`routers/tours.py`、router 注册、数据库角色与权限；前端 `api.ts`、`ConsoleInsertPanel.tsx`、`SongAdminSection.tsx`、`StageLedgerContent.tsx`、`CatalogPanels.tsx`、`StatisticsPanel.tsx`、巡演歌曲入口、缓存与导航状态。

部分读取路径直接执行 `int(song_band_id)`，迁移允许空值后必须一并适配，不能伪造 `0` 避免报错。已有歌曲筛选和唯一约束都假设单乐队；特殊版本规则确定前不要编造最终索引。

## 10. 验收与待讨论问题

| 场景 | 验收要求 |

| 乐队换员 | 歌曲仍绑定原 band_id 集合，不因换员判为翻唱 |
| 限定三支乐队 | 乐队模式可选择三个 band_id，各队换员不改变基准集合 |
| 成员模式实际出演换人 | 固定成员基准不变；实际出演成员所属乐队命中任一固定分组乐队，不判为现场翻唱 |
| 任一乐队命中 | 基准 A / B / C，现场仅 A 或 A / D 均不是现场翻唱；仅 D 才是 |
| 迁移期空归属 | 可保存待回填资料，读接口不崩溃，不默认判为非翻唱 |
| 回填完成后空归属 | 已审核项必须满足对应归属模式；表外 pending 保留，允许合法 mixed |
| 多人合作的一条 setlist | 演奏次数加一；每条记录独立展示 |
| 同场两条同曲 | 演奏次数加二，不引入场数或返场专门指标 |
| 短版 | 次数正常计入，只在对应条目后标记 |
| 未来 / 取消已有歌单 | 识别为错误数据，写入及状态修改防止产生新错误，不自动删数据 |
| 同一 Live 正式改期 | 必须指定新日期，ID 不变；已有歌单后拒绝修改日期 |
| 专辑未知日期 | NULL 可保存；有值必须完整年月日，不接受部分精度 |
| Instrumental 收录 | 不生成新 song_id，点击定位对应非 Instrumental 版本 |
| 专辑曲序改变 | 只影响专辑子项内展示；碟号和发行版共用子项名称 |
| 数字 / 游戏先发 | 歌曲无发售日期，不因无专辑显示未发行 |
| 自由发行标识 | 示例和非枚举文本均能保存，不拆分类别 |
| 歌曲资料入口 | 位于巡演资料与数据统计之间；宽版左侧歌曲组列表，右侧切换版本并显示歌曲组次数；左侧无次数，选择、直接定位与返回均可用 |
| 控制台歌曲双页 | 新增与管理入口独立，新增不修改已有条目；管理先选中再编辑，确认、恢复原值、未保存保护与演出管理一致 |
| 固定特殊版 | 固定合唱 / 独立编曲与普通版归入同组；专辑关联具体版本，setlist 关联歌曲组，默认项提供现场基准 |
| 成员 ID 映射 | 同名不同人不误合，并保留同人跨乐队的稳定身份 |
