# 巡演聚合产品需求

## 文档定位

本文定义 LiveSetList “巡演”聚合能力的产品目标、概念边界、用户页面、交互规则、阶段范围和验收标准。

- 本文是产品需求，不定义数据库表、具体路由、SQL 或 React 组件拆分。
- 具体数据结构、接口、迁移、权限和测试方案见 [巡演聚合实现设计](../design/tour-aggregation.md)。
- 公共首页、演出资料、搜索和个人区的总体定位仍由 [社区 Live 数据库首页与个人工作台需求](homepage-community-database.md) 维护。

当前状态：`T1 数据结构与公共读取、T2 控制台维护已实现；T3~T4 尚未开始`。

## 背景

当前 LiveSetList 以单场 Live 为核心：用户可以浏览演出资料、打开 Live 详情、查看 setlist、按乐队和类型筛选，并收藏单场 Live。

真实资料中已经存在多场属于同一官方巡演的情况，例如：

- 同一巡演按福冈、大阪、爱知、东京和 FINAL 等场次展开。
- 同一巡演跨年份或存在追加公演。
- 本站可能只收录某一巡演中的一部分场次。
- 某些标题包含 `TOUR`，另一些巡演名称并不包含稳定的英文关键词。

如果继续只展示单场 Live，用户无法快速回答：

1. 这些场次是否属于同一个巡演？
2. 本站已经收录了这个巡演的哪些场次？
3. 每一场的日期、场地和 setlist 有什么不同？
4. 从某一场 Live 如何回到它所属的巡演？

巡演聚合的目标是为单场 Live 增加稳定的上层组织关系，而不是替代现有 Live 和 setlist 页面。

## 产品结论

### 1. 巡演是独立资料实体

“巡演”与单场 Live 是不同层级：

- Live 表示某一天、某一场地发生的一场演出。
- Tour 表示具有统一名称和官方活动身份的一组巡演场次。
- 巡演不是 Live 类型，不加入 `oneman / taiban / multi_act / festival / event / other` 枚举。
- 巡演也不是任意多日活动的通用分组；`2DAYS LIVE`、音乐节和周年活动不能仅因具有多场就自动视为巡演。

第一版规定一场 Live 最多属于一个巡演。未来只有出现真实的一场多归属需求时，才放宽该规则。

### 2. 允许不完整收录

本站不承诺已经收录巡演的全部官方场次：

- 即使当前只收录一场，只要它具有明确的巡演身份，也可以建立巡演实体。
- 页面统一展示“已收录 N 场”，不展示“共 N 场”。
- 不根据当前关联数量计算“完整度”或“完成率”。
- 不把本站最早和最晚的已收录场次描述成官方巡演的绝对起止日期。

### 3. 巡演关系由编辑者明确维护

- 不根据 Live 标题中的 `TOUR`、城市名、共同前缀或日期自动落库。
- 系统可以在控制台提供标题相似候选，但最终关联必须由 `editor+` 用户确认。
- 场次展示名称可以使用“福冈公演”“大阪追加公演 DAY1”“FINAL DAY2”等简短标签，由编辑者维护。

## 用户与核心场景

### 匿名用户

匿名用户可以：

- 在“演出资料”中切换到“巡演”。
- 按关键词、乐队和年份浏览巡演。
- 打开巡演详情并查看本站已收录的场次。
- 从巡演场次进入现有 Live 详情和 setlist。
- 从单场 Live 详情返回所属巡演。
- 在公共搜索中找到巡演。

匿名用户不需要登录即可完成以上浏览。

### 登录用户

登录用户除公共浏览外，可以在巡演详情中继续收藏或取消收藏具体 Live。

第一版不提供巡演收藏，也不把“仅收藏”解释成巡演收藏或“包含收藏场次的巡演”。收藏语义继续严格限定为单场 Live。

### editor+ 用户

`editor+` 用户可以：

- 创建巡演资料。
- 维护巡演名称、官方来源和参与乐队。
- 搜索并关联现有 Live。
- 调整场次顺序和场次标签。
- 从巡演移除错误关联的 Live。
- 看到 Live 已属于其他巡演时的明确冲突提示。

所有写操作继续使用现有角色校验、CSRF 防护和审计日志。

## 信息架构

### 演出资料实体切换

“巡演”放在现有“演出资料”内部，不新增同级全局导航项：

```text
演出资料

[ 场次 ]  [ 巡演 ]
```

- “场次”保留当前卡片/表格、全部/仅收藏、关键词、年份、Live 类型、乐队和日期排序。
- “巡演”显示巡演卡片列表，使用独立的关键词、乐队、年份和日期排序。
- 用户切换实体后，页面标题和结果总数必须明确当前展示的是场次还是巡演。

### 巡演列表

巡演卡片至少展示：

- 巡演名称。
- 参与乐队。
- 本站已收录场次的最早日期和最晚日期。
- “已收录 N 场”。
- 前几项场次标签；空间不足时可以收起为摘要。
- 进入巡演详情的明确操作。

排序默认按本站已收录场次中的最晚日期倒序，再按巡演 ID 倒序稳定排序。

筛选规则：

- 关键词匹配巡演名称、关联场次标题和场次标签。
- 乐队筛选匹配巡演显式维护的参与乐队。
- 年份筛选表示“至少一场已收录 Live 位于该年份”。跨年巡演可以同时出现在多个年份筛选结果中。
- 多个筛选条件使用 AND。

### 巡演详情

巡演详情头部展示：

- 巡演名称。
- 官方来源外链；没有来源时不渲染空链接。
- 参与乐队。
- 本站已收录日期范围。
- “已收录 N 场”。
- 可选的简短说明。

场次列表按编辑者维护的顺序展示，每一项至少包含：

- 场次标签。
- Live 日期。
- 原始 Live 标题。
- 场地。
- Live 类型。
- 是否已有 setlist。
- 当前用户对该 Live 的收藏状态。
- 进入 Live 详情的操作。

从 Live 详情返回时，应优先回到原巡演详情及原滚动位置。

### Live 详情反向入口

属于巡演的 Live 在现有详情元数据中增加：

```text
巡演：Ave Mujica LIVE TOUR 2026「Exitus」
```

巡演名称是可操作入口。没有巡演关系的 Live 不显示该字段，不显示占位符。

### 公共搜索

公共搜索增加“巡演”结果分组：

- 搜索巡演名称时，优先看到巡演实体，然后仍可看到命中的单场 Live。
- 巡演结果展示名称、参与乐队、已收录场数和日期范围。
- 点击巡演结果进入巡演详情。
- 单场 Live、乐队、歌曲和场地分组的现有行为保持不变。

## 页面状态与文案

### 数据口径

统一使用：

- “本站已收录”。
- “已收录 N 场”。
- “已收录日期范围”。

避免使用：

- “巡演共 N 场”。
- “完整巡演”。
- “巡演完成度”。
- 未经验证的官方开始、结束或总场次数。

### 空状态

- 没有任何巡演资料：“当前还没有已整理的巡演资料”。
- 筛选无结果：“没有符合当前条件的巡演”。
- 巡演没有场次：正常产品流程不允许保存；若出现历史异常数据，应显示错误状态而不是伪造空巡演。
- 加载失败：显示可理解的错误和重试入口，不能回退成空结果。

### 响应式与无障碍

- 桌面端巡演列表可以使用多列卡片；移动端使用单列。
- 实体切换、筛选和详情入口必须使用真实按钮或链接。
- 巡演卡片不能让整体详情操作吞掉内部收藏按钮和外部来源链接的独立交互。
- 场次列表在移动端不能依赖横向滚动才能看到日期和名称。
- 加载、错误、当前选中实体和当前巡演标题应有可识别的语义。

## 数据维护规则

- 巡演名称保存官方或通用名称，不把城市、公演日或 DAY 编号写入巡演名称。
- 城市、公演日、追加公演和 FINAL 信息写入场次标签或保留在原 Live 标题中。
- 参与乐队是巡演级显式资料，不从某一场 setlist 自动反推并永久保存。
- 场次顺序默认按日期和 Live ID 生成，但编辑者可以调整。
- 一个巡演至少关联一场 Live 后才能保存。
- Live 已关联其他巡演时不能静默移动，必须先明确处理原关联。

## MVP 验收标准

- 匿名用户可以从“演出资料”切换到“巡演”，无需登录。
- 巡演列表能准确展示名称、参与乐队、已收录日期范围和“已收录 N 场”。
- 年份筛选以“任一已收录场次落在该年”为准。
- 巡演详情按稳定顺序展示场次，并能进入现有 Live 详情。
- 属于巡演的 Live 详情能返回巡演；不属于巡演的 Live 不出现空字段。
- 公共搜索能同时返回巡演和单场 Live，分组语义清晰。
- editor 可以创建巡演并维护场次关系；重复归属返回明确冲突。
- 未收录全部官方场次时，任何页面都不会暗示资料完整。
- 现有 Live 列表、收藏、setlist、乐队浏览和统计行为不回退。
- 业务代码完成后通过 `python scripts/run_checks.py functional`，并在桌面和 390px 移动视口完成真实浏览器验收。

## 非目标

第一版不做：

- 巡演地图、路线图、国家/城市筛选和地理距离。
- 自动识别或自动合并巡演。
- 通用活动系列、音乐节届次或任意 Live 集合。
- 巡演收藏、关注和更新提醒。
- 官方总场数、完成率和缺失场次计算。
- 多场 setlist 差异、固定曲目、替换曲目和平均 setlist。
- 巡演删除、合并、拆分和复杂审核流。

多场 setlist 对比是巡演实体稳定后的优先后续能力，但不与第一版聚合页面同时实现。
