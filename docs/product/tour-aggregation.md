# 巡演聚合产品需求

## 文档定位

本文定义 LiveSetList “巡演”聚合能力的产品目标、概念边界、用户页面、交互规则、阶段范围和验收标准。

- 本文是产品需求，不定义数据库表、具体路由、SQL 或 React 组件拆分。
- 具体数据结构、接口、迁移、权限和测试方案见 [巡演聚合实现设计](../design/tour-aggregation.md)。
- 公共首页、演出资料、搜索和个人区的总体定位仍由 [社区 Live 数据库首页与个人工作台需求](homepage-community-database.md) 维护。

当前状态：`T1~T3 已实现；T4 部分完成，公共搜索巡演分组、生产数据整理和发布批次浏览器验收仍待执行`。

## 背景

当前 LiveSetList 以单场 Live 为核心：用户可以浏览演出资料、打开 Live 详情、查看 setlist、按乐队和类型筛选，并收藏单场 Live。

真实资料中已经存在多场属于同一官方巡演的情况，例如：

- 同一巡演按福冈、大阪、爱知、东京和 FINAL 等场次展开。
- 同一巡演跨年份或存在追加公演。
- 本站可能只收录某一巡演中的一部分场次。
- 某些标题包含 `TOUR`，另一些巡演名称并不包含稳定的英文关键词。

如果继续只展示单场 Live，用户无法快速回答：

1. 这些场次是否属于同一个巡演？
2. 本站已经收录了这个巡演的哪些场次？
3. 每一场的日期、场地和 setlist 有什么不同？
4. 从某一场 Live 如何回到它所属的巡演？

巡演聚合的目标是为单场 Live 增加稳定的上层组织关系，而不是替代现有 Live 和 setlist 页面。

## 产品结论

### 1. 巡演是独立资料实体

“巡演”与单场 Live 是不同层级：

- Live 表示某一天、某一场地发生的一场演出。
- Tour 表示具有统一名称和官方活动身份的一组巡演场次。
- 巡演不是 Live 类型，不加入 `oneman / taiban / multi_act / festival / event / other` 枚举。
- 巡演也不是任意多日活动的通用分组；`2DAYS LIVE`、音乐节和周年活动不能仅因具有多场就自动视为巡演。

第一版规定一场 Live 最多属于一个巡演。未来只有出现真实的一场多归属需求时，才放宽该规则。

### 2. 允许不完整收录

本站不承诺已经收录巡演的全部官方场次：

- 即使当前只收录一场，只要它具有明确的巡演身份，也可以建立巡演实体。
- 页面统一展示“已收录 N 场”，不展示“共 N 场”。
- 不根据当前关联数量计算“完整度”或“完成率”。
- 不把本站最早和最晚的已收录场次描述成官方巡演的绝对起止日期。

### 3. 巡演关系由编辑者明确维护

- 不根据 Live 标题中的 `TOUR`、城市名、共同前缀或日期自动落库。
- 系统可以在控制台提供标题相似候选，但最终关联必须由 `editor+` 用户确认。
- 场次展示名称使用“Live 名称减去巡演名称”的短标题规则自动计算；`stop_label` 仅作为兼容字段保留，当前控制台不展示或维护。

## 用户与核心场景

### 匿名用户

匿名用户可以：

- 从主导航进入“巡演资料”。
- 按关键词、乐队和年份浏览巡演。
- 打开巡演详情并查看本站已收录的场次。
- 从巡演场次进入现有 Live 详情和 setlist。
- 从单场 Live 详情返回所属巡演。
- 从主导航、巡演列表或单场 Live 的反向入口找到巡演；公共搜索中的巡演实体分组尚未实现。

匿名用户不需要登录即可完成以上浏览。

### 登录用户

登录用户的收藏语义继续属于单场 Live；“演出资料”、单场 Live 入口和巡演详情的场次快捷入口都复用同一套 Live 收藏状态与同步逻辑。

第一版不提供巡演实体收藏，也不把“仅收藏”解释成巡演收藏或“包含收藏场次的巡演”。巡演详情中的星标只操作对应单场 Live。

### editor+ 用户

`editor+` 用户可以：

- 创建巡演资料。
- 维护巡演名称和可选的参与乐队。
- 搜索并关联现有 Live。
- 场次顺序固定按 Live 日期、开演时间和 ID 生成，ID 只用于完全同时间时保持稳定。
- 新建巡演未指定参与乐队时，确认页明确提示将自动聚合乐队且统计包含全部 Setlist，但不阻止创建。
- 从巡演移除错误关联的 Live。
- 候选搜索不显示已属于其他巡演的 Live；若提交时发生并发占用，显示明确冲突提示。
- 创建成功后在页面底部查看本次会话的新增巡演记录；创建或更新成功后编辑区恢复为空白新建状态。

所有写操作继续使用现有角色校验、CSRF 防护和审计日志。

## 信息架构

### 独立巡演资料页签

“巡演资料”作为主导航中的独立页签，与“演出资料”并列：

- “演出资料”承载单场 Live、演出活动组、全部/仅收藏和现有筛选；活动组不等同于巡演。
- “巡演资料”承载巡演卡片列表，使用独立的关键词、乐队、年份和日期排序。
- 巡演详情打开后，“巡演资料”导航项保持选中。
- 两个资料列表统一采用“筛选 → 总计/分页 → 详细内容”的信息顺序和同一组 `pager` / 卡片间距。

### 巡演列表

巡演卡片至少展示：

- 巡演名称。
- 参与乐队；未显式设置时聚合全部已收录场次的乐队。
- 本站已收录场次的最早日期和最晚日期。
- “已收录 N 场”。
- 与“演出资料”一致，点击整张卡片进入详情；不再额外提供标题按钮或“查看巡演”按钮。

排序默认按本站已收录场次中的最晚日期倒序，再按巡演 ID 倒序稳定排序。

筛选规则：

- 关键词匹配巡演名称、关联场次标题和场次标签。
- 乐队筛选优先匹配显式参与乐队；未显式设置时匹配全部已收录场次聚合出的乐队。
- 年份筛选表示“至少一场已收录 Live 位于该年份”。跨年巡演可以同时出现在多个年份筛选结果中。
- 多个筛选条件使用 AND。

### 巡演详情

巡演详情头部展示：

- 巡演名称。
- 来源外链取日期最早场次的 Live 链接。
- 参与乐队；未显式设置时聚合全部已收录场次的乐队。
- 本站已收录日期范围。
- “已收录 N 场”。

场次导航按 Live 日期、Live ID 稳定排序，只展示从原始 Live 标题开头精确移除巡演名称并 trim 后的短标题；若不匹配或结果为空则保留原标题。所有短标题用竖向分隔条隔开并尽可能压在同一行，空间不足时才按完整标题换行。短标题是唯一的 Live 详情入口，点击后直接在巡演页内渲染现有 Live 详情与表格。

详情增加“场次详情 / 巡演统计”子页签。巡演显式指定参与乐队时，统计只纳入 `band_member` 命中任一指定乐队的 Setlist；未显式指定乐队时继续纳入全部 Setlist。巡演统计默认按相邻且均有可纳入 Setlist 的场次比较；至少有三场可比较时，还可选择任意不同的起始场与目标场按需比较，不改写默认相邻结果。同一歌曲的 `absolute_order` 变化优先记为顺序变化，已归入顺序变化的歌曲不再参与更换识别；其余同一 `segment_type + sub_order` 的不同歌曲在接口中记为更换，剩余差异记为新增或移除。场次变化使用左侧场次时间线与右侧歌单差异面板：时间线按日期展示场次，并在相邻场次入口标记“无变化”或变化项数；默认选中最近一次有变化的比较，没有变化时选中第一组。右侧展示新增、移除和顺序变化数量并按类型分组；接口中的每项位置更换按一项新增和一项移除展示，不单设“同位置更换”分类；无变化只显示“歌单未发生变化”。任意场次比较复用同一差异面板，切回时间线条目即恢复对应相邻比较。场次名均可点击并切回“场次详情”中的对应 Live；移动端上下排列，不依赖横向滚动。

“已收录日期”元数据、“场次详情 / 巡演统计”标签和公演短标题导航之间使用一致的垂直节奏；当前两段间距均为 `14px`。

### Live 详情反向入口

属于巡演的 Live 在现有详情元数据中增加：

```text
巡演：Ave Mujica LIVE TOUR 2026「Exitus」
```

巡演名称是可操作入口。没有巡演关系的 Live 不显示该字段，不显示占位符。

### 公共搜索（待实现）

规划为公共搜索增加“巡演”结果分组；当前 `/api/catalog/search` 仍只返回 Live、乐队、歌曲和场地：

- 搜索巡演名称时，优先看到巡演实体，然后仍可看到命中的单场 Live。
- 巡演结果展示名称、参与乐队、已收录场数和日期范围。
- 点击巡演结果进入巡演详情。
- 单场 Live、乐队、歌曲和场地分组的现有行为保持不变。

## 页面状态与文案

### 数据口径

统一使用：

- “本站已收录”。
- “已收录 N 场”。
- “已收录日期范围”。

避免使用：

- “巡演共 N 场”。
- “完整巡演”。
- “巡演完成度”。
- 未经验证的官方开始、结束或总场次数。

### 空状态

- 没有任何巡演资料：“当前还没有已整理的巡演资料”。
- 筛选无结果：“没有符合当前条件的巡演”。
- 巡演没有场次：正常产品流程不允许保存；若出现历史异常数据，应显示错误状态而不是伪造空巡演。
- 加载失败：显示可理解的错误和重试入口，不能回退成空结果。

### 响应式与无障碍

- 桌面端巡演列表可以使用多列卡片；移动端使用单列。
- 实体切换和筛选必须使用真实按钮或链接；巡演卡片详情入口与演出卡片保持相同交互。
- 巡演卡片不能让整体详情操作吞掉内部收藏按钮和外部来源链接的独立交互。
- 场次列表在移动端不能依赖横向滚动才能看到日期和名称。
- 加载、错误、当前选中实体和当前巡演标题应有可识别的语义。

## 数据维护规则

- 巡演名称保存官方或通用名称，不把城市、公演日或 DAY 编号写入巡演名称。
- 城市、公演日、追加公演和 FINAL 信息保留在原 Live 标题中；暂不在前端维护场次标签。
- 参与乐队可以不设置，此时 `tour_bands` 保持空集合，显示和筛选按全部已收录场次的有效乐队动态聚合。
- 显式选择参与乐队时，每个所选乐队都必须至少出现在一场已选 Live 中。
- 场次顺序固定按 Live 日期和 Live ID 生成，不提供人工上移或下移。
- 一个巡演至少关联一场 Live 后才能保存。
- Live 已关联其他巡演时不能静默移动，必须先明确处理原关联。

## MVP 验收标准

- 匿名用户可以直接进入“巡演资料”，无需登录。
- 巡演列表能准确展示名称、参与乐队、已收录日期范围和“已收录 N 场”。
- 年份筛选以“任一已收录场次落在该年”为准。
- 巡演详情按稳定顺序展示场次，并能在当前页面切换现有 Live 详情。
- 登录用户可在巡演详情直接收藏或取消收藏单场 Live；不引入巡演实体收藏。
- 巡演统计保留相邻变化时间线，并可按需比较任意两场已有 Setlist 的场次。
- 属于巡演的 Live 详情能返回巡演；不属于巡演的 Live 不出现空字段。
- 公共搜索巡演分组落地后，能同时返回巡演和单场 Live，且分组语义清晰；当前该项不作为已完成验收结果。
- editor 可以创建巡演并维护场次关系；重复归属返回明确冲突。
- 未收录全部官方场次时，任何页面都不会暗示资料完整。
- 现有 Live 列表、收藏、setlist、乐队浏览和统计行为不回退。
- 业务代码完成后通过 `python scripts/run_checks.py functional`，并在桌面和 390px 移动视口完成真实浏览器验收。

## 非目标

第一版不做：

- 巡演地图、路线图、国家/城市筛选和地理距离。
- 自动识别或自动合并巡演。
- 通用活动系列、音乐节届次或任意 Live 集合。
- 巡演收藏、关注和更新提醒。
- 官方总场数、完成率和缺失场次计算。
- 固定曲目、平均 setlist 和更高阶统计；相邻场次的新增、移除与顺序变化已经落地。
- 巡演删除、合并、拆分和复杂审核流。

当前已经落地相邻场次 Setlist 变化统计；更高阶的全巡演固定曲目、平均结构和官方完整度仍属于后续能力。
